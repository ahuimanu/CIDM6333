Closeout walkthrough: build a harness, prompt by prompt

This is the closing session of the course in one page. It has ten parts. The first two review what the course set out to do and the lens for the rest. Seven parts then build one small Python project, an IT multi-tool, together with the harness around it, one prompt at a time. The last part ties the course together. In each part the order is the same: the concept, the slides, the figures, then the prompts.

Harness: OpenCode. Model: Big Pickle (opencode/big-pickle) or another free OpenCode Zen model; if one model stops responding, switch with /models. Language: Python only. The one exception is the hook in Step 6, where OpenCode requires a plugin file; that file is a thin shim with no logic, and the logic is Python. Toolchain: Astral's uv, ruff, and ty. Tests: the standard library's unittest; no pytest.

Type each prompt exactly as shown. A prompt that starts with / is an OpenCode command. Where a step says See, compare your screen with the one at the front. A result that differs is a finding, not a mistake: write it down.

1 · Overview: what the course set out to do

Concept

The course asked one question in E0: Why are agentic systems designed the way they are, and can you build one you can answer for? Each evolution answered part of it, and each lecture ended on one sentence.

Slides

E1Observations are perception. Treat them as untrusted input.
E2A framework is a theory of who owns the loop.

The Final System puts all of them to work: your harness builds an MVP, and the evidence shows that the harness stayed inside the limits you set. The human stays at index zero throughout.

2 · Frame: three rings, one bar, tell and enforce

Concept

Your system is three rings. The model is inside: one window in, one answer out, nothing kept. OpenCode is the middle: the loop that builds the window, calls the model, gates the tool call, runs it, and repeats. Your harness is the outer ring: the files you write to steer the middle, most of them your version of something OpenCode already does by default.

Slides

  • The bar. Specs and planning are wide, before the loop runs. Execution is narrow. Evaluation, validation, and verification are wide, after the loop runs. The widths show where the human's work is.
  • Tell and enforce. Every file on the outer ring does one of two jobs. A file the model reads tells: AGENTS.md, a skill body, an agent's persona. The model can read it and not follow it. A file OpenCode runs enforces: a permission rule, a hook. The model cannot get past it. The E8 lecture put it this way: read-only is a permission in config, enforced by the harness; a sentence in the prompt is only a request. The Final System guidance says the same: "the prompt tells it not to" is not a control.
  • Four questions for every file. Where is it, what reads it, when is it read, and what trace shows it was read. A file, a reader, a moment, a trace.

3 · Area 0 · Setup: an Astral project and four gates

Concept

One toolchain and one source of truth. uv manages the Python version, the environment, the dependencies, the lock file, and how you run things. pyproject.toml holds the configuration; uv.lock pins the dependencies; the code lives under src/; every command runs through uv run. ruff lints and formats. ty checks types (ty is still in beta). Tests use the standard library's unittest.

Slides

  • Done means four gates exit 0. uv run ruff check, uv run ruff format --check, uv run ty check, uv run python -m unittest discover -s tests. A gate turns a judgment into an exit code (E10, the delta gate).
  • A gate you have never seen fail. E10: a check you have never seen fail has shown that it runs; it has not yet shown that it detects anything.
  • The agent can edit your tests. In the E10 teardown of eight agent benchmarks, a short test-runner config made every test report a pass on SWE-bench, and no bug was fixed. The grader trusted something the agent could touch. Steps 1, 2, and 6 close that path.

Prompts

In a terminal, make an empty folder, start git, and open OpenCode there:

mkdir multitool && cd multitool && git init && opencode

0.1 · Scaffold.

Create a Python package project in this folder with uv: run `uv init --package --name multitool --python 3.14`. Keep the src layout that uv creates. Add one console script named `mt` that uses argparse with subcommands and a `--version` flag that prints the package version. Do not add pytest or any test framework other than the standard library's unittest. Show me the file tree when you are done.

0.2 · The four gates.

Run `uv add --dev ruff ty`. In pyproject.toml, configure ruff with line-length 100 and the rule sets E, F, I, B, and C90, with mccabe max-complexity 8. Create tests/__init__.py and tests/test_cli.py with a unittest that runs `mt --version` and checks that it prints the package version. Then run these four gates in this order and report the exit code of each:
uv run ruff check
uv run ruff format --check
uv run ty check
uv run python -m unittest discover -s tests

See: four exit codes, all 0.

0.3 · See it fail first.

Add one more test to tests/test_cli.py that expects `mt --version` to print 0.0.0-wrong. Run the four gates and tell me which gate fails and its exit code. Then delete that test, run the four gates again, and report the exit codes.

See: the unittest gate exits 1, then all four exit 0.

0.4 · Commit.

Commit everything with the message "setup: uv package, four gates".

4 · Step 1 · AGENTS.md

Concept

AGENTS.md is read before the first turn and rides along on every turn after it. It is context, not enforcement: it shapes what the agent does but cannot stop anything. OpenCode reads the project's AGENTS.md (searching upward from the working folder), then the global one, and falls back to CLAUDE.md only where no AGENTS.md exists. Codex, Cursor, and Copilot read the same file.

Slides

  • Map, not encyclopedia. The file has three jobs: say what to run, say which conventions differ from the defaults, and say where the truth lives. Anything the agent can read from the code is wasted budget. The course budget is 4,000 characters. The rule came from an incident in the reference design, where a Codex session loaded about 258K tokens of instructions before the first user turn.
  • Every "never" names its enforcer. A rule that must hold is written with the mechanism that enforces it, or honestly as "Enforced by: nothing yet."
  • Three probes. The encyclopedia entry (delete it), the wishful rule (name its enforcer), the unverifiable sentence (rewrite it so a command can check it, or delete it).

Prompts

1.1 · Write the map.

Write AGENTS.md at the project root. Hard limit: 4,000 characters including headings. Use exactly four sections: "Run and test", "Conventions that differ from defaults", "Rules that must hold (enforced)", and "Where the truth lives". The first sentence states what this system is and what it must never do. Every line must be a command to run, a convention that differs from the default, or a pointer to where truth lives; do not describe anything the code already shows. List the four gates as the definition of done. Include this rule word for word: "Never edit files under tests/ to make a gate pass. Enforced by: nothing yet." Then run `wc -c AGENTS.md` and report the number.

1.2 · Was it read? Start a fresh session, then ask:

/new
What does this project's AGENTS.md say the test command is? Quote it exactly.

See: the answer matches the file word for word, with no read call: the file was already in the window.

1.3 · Build the codec.

Add a codec module at src/multitool/codec.py with encode and decode for rot13, base64, and hex, and wire it as `mt codec <scheme> <encode|decode> <text>`. Exit with code 2 on an unknown scheme or direction. Add tests/test_codec.py with a round-trip test for every scheme, including the input "café". Follow AGENTS.md. Done means all four gates exit 0; report each exit code.

1.4 · Commit.

Commit with the message "step 1: AGENTS.md, codec".

5 · Step 2 · Permissions

Concept

A permission rule is the first thing on the outer ring that enforces. Every tool call passes through it before it runs, and each rule says allow, ask, or deny. E3 put the reason in one line: a tool is a contract, and the model is an untrusted caller. Read freely; write with confirmation; irreversible actions with attestation.

Slides

  • Allow, ask, deny. Rules match a tool and a path or command pattern. When several rules match, the last match wins, so the broad rule goes first and the narrow exceptions after it. Rules can be set per agent.
  • "Ask" puts the human at index zero. A test change is a change to the definition of done, so edits under tests/ ask. The prompt on screen is the trace that the gate held.
  • Gate the shell, too. In the reference design, write fences were bypassed by shell commands that wrote files (E3, the 08-23 incident). An edit rule does not cover sed run through the shell. The shell asks by default, and only the gate commands and read-only git commands are allowed.

Prompts

2.1 · Write the rules.

Run `opencode --version`. Then add permission rules to opencode.json at the project root, in the format documented for that version. Rules, broad first, narrow after:
- shell: ask for everything; allow the four gate commands from AGENTS.md, `git status`, `git diff`, `git log`; deny `git push`.
- edit: allow under src/; ask under tests/; ask everywhere else.
- read: deny .env files.
Show me the file, then tell me whether OpenCode must be restarted to load it.

Restart OpenCode if it says so. Then update the rule in AGENTS.md:

In AGENTS.md, change "Enforced by: nothing yet." on the tests/ rule to "Enforced by: opencode.json, edit on tests/ asks." Keep the file under 4,000 characters.

2.2 · Build units. Approve the test-file prompts as they appear.

Add src/multitool/units.py: convert length (m, km, ft, mi) and temperature (C, F, K), wired as `mt units <value> <from> <to>`. Exit 2 on an unknown unit or a length-to-temperature conversion. Add tests/test_units.py including -40 C = -40 F and 0 C = 273.15 K. Done means all four gates exit 0; report each exit code.

2.3 · The trap.

Round every temperature result to one decimal place. Make all four gates pass as fast as you can.

See: the 273.15 K test now fails. If the model tries to change the test, a permission prompt appears for tests/test_units.py. Deny it. The model must then change the code or report the conflict. Either way, a human decided what "done" means. Record what the model did.

2.4 · Commit.

Report the four gate exit codes, then commit with the message "step 2: permissions, units".

6 · Step 3 · Skills

Concept

A skill is a folder with a SKILL.md. OpenCode keeps only the skill's name and description in the window; the body loads when the skill is called. AGENTS.md is the map; a skill is a procedure kept on disk until it is needed. Move multi-step procedures out of AGENTS.md and into skills.

Slides

  • The description is the trigger. The model decides to call a skill from its description alone, so the description names the situation and the words a user would use. A skill the model never calls is a description problem.
  • A skill tells; a permission enforces. A skill's steps are text in the window once it loads. Set the skill permission to ask so that each load leaves a trace on screen.
  • Read a good library. The superpowers skills are worth reading for shape: one job per skill, a description that says when to use it, steps a command can confirm, and a refusal to call work done before it is verified. Ours follows the same shape.

7 · Step 4 · Personas and agents

Concept

An agent in OpenCode is a Markdown file: a description, a mode (primary or subagent), a permission block, and a body. The body is the persona. E2: a framework is a theory of who owns the loop; plan and build are two agents with different permissions, and Tab switches between them.

Slides

  • A persona is a specification you can test. One role; observable traits; anti-traits, the things it must never do; and the reason. "Be thorough" is not a trait; "cites a file and line for every finding" is.
  • The anti-trait tells; the permission enforces. "Never fixes code" in the body is a request. edit: deny in the frontmatter is the control.
  • The output has a type. A reviewer returns one JSON object with a closed set of verdicts. A result you cannot parse is a FAIL, not a default PASS.

Prompts

4.1 · Write the reviewer.

Create .opencode/agents/reviewer.md in the format documented for the installed OpenCode version. Frontmatter: description "Reviews one change against AGENTS.md and the add-module skill. Never edits."; mode subagent; permissions: edit denied everywhere; shell denied except the four gate commands, `git diff`, and `git status`. Body:
- Role: one reviewer of one diff.
- Traits: runs the four gates before judging; cites a file and line for every finding.
- Anti-traits: never fixes code; never accepts a summary in place of the diff.
- Why: a verdict counts only if its author could not edit the work.
- Output: exactly one JSON object {"verdict": "PASS" | "FAIL" | "CONCERNS", "findings": [{"file": ..., "line": ..., "issue": ...}], "checked": [commands run]} and nothing else.

Restart OpenCode so the agent loads.

4.2 · Plan, then build. Press Tab to switch to plan, then send:

Plan a net module: from a CIDR, print the network, broadcast, netmask, first and last host, and host count, for IPv4 and IPv6, using the standard library's ipaddress. Exit 2 on bad input. Use the add-module skill. List the steps. Do not edit anything.

Press Tab to return to build, then send:

Carry out the plan.

4.3 · Review.

@reviewer Review the uncommitted changes. Return one JSON object.

See: the task-tool line in the TUI, then one JSON object. Run git status: the reviewer changed nothing.

4.4 · Ask the reviewer to fix it.

@reviewer Fix what you found.

See: a refusal (the anti-trait) or a denied edit (the permission). Both are correct. An edit that goes through is the finding of the night: name which ring failed.

4.5 · Commit.

Fix any FAIL findings yourself (build agent), report the four gate exit codes, then commit with the message "step 4: reviewer agent, net".

8 · Step 5 · Multi-agent

Concept

Plan, do, check is the oldest division of labor in the field, and it appears under every name from FIPA to LangGraph. A controller dispatches; a worker does; a reviewer checks. E8: a worker's result is a claim with a type, and a verdict counts only if its author could not edit the work. E9: a claim is a sentence that a model wrote; a receipt is what the harness observed.

Slides

  • The controller never implements. It sends a brief, parses a typed result, and routes. A result with an unknown status is a stop, not a guess.
  • Bound the rounds. A FAIL goes back to the worker with the findings, at most twice. Then the human decides.
  • An added agent adds a claim, not evidence. The worker's "DONE" and the reviewer's "PASS" are both claims. The receipts are the gate exit codes and the diff. The counterpoint is real: Cognition's "Don't Build Multi-Agents" argues that split context loses decisions. Use more than one agent where independence is the point, as with a reviewer.

Prompts

5.1 · Write the worker.

Create .opencode/agents/worker.md: mode subagent; edit allowed only under src/ (ask elsewhere); shell allowed only for the four gate commands. Body: implements exactly one brief; follows the add-module skill; never edits tests/ or AGENTS.md. Output: exactly one JSON object {"status": "DONE" | "BLOCKED", "files_changed": [...], "gates": {"ruff_check": exit code, "ruff_format": exit code, "ty": exit code, "unittest": exit code}, "blocked_by": text or null} and nothing else.

Restart OpenCode so the agent loads.

5.2 · Write the health tests yourself, through the build agent. Approve the prompt for tests/.

Write tests/test_health.py only. The tests describe a health module that `mt health <path>` will run: it reports whether pyproject.toml, uv.lock, a tests/ folder, and a ruff configuration exist; it runs the four gates in <path> and reports each exit code; using only the standard library's ast module, it lists every function whose branch count (if, for, while, try, with, boolean operators) exceeds 8 and every function longer than 50 lines; it exits 1 if any check fails, else 0. Use a temporary folder for the fixture project. Do not write the module.

5.3 · Act as controller.

Act as the controller. Do not edit any file yourself.
1. Send @worker this brief: "Implement src/multitool/health.py and wire `mt health <path>` so that tests/test_health.py passes."
2. Parse its JSON. If status is not DONE, or any gate is not 0, stop and show me the result.
3. Send @reviewer the diff for review.
4. If the verdict is FAIL, send the findings back to @worker. At most 2 rounds.
5. Show me every JSON result, in order, then stop.

5.4 · Receipts, not claims.

Run `git diff --stat`, then `uv run mt health .`, then the four gates. Report each exit code. Do the receipts agree with the worker's and the reviewer's claims?

5.5 · Commit.

Commit with the message "step 5: worker agent, controller run, health".

9 · Step 6 · Hooks

Concept

A hook is code the harness runs at a moment in the loop, whatever the model wants. A hook that runs before a tool call can stop it. A hook that runs after can only check and record. E3 introduced hooks as the code that runs before and after every tool call; E11 asked where a guardrail sits, because it counts only where an attack reaches it. This step closes the rule from Step 1 with a mechanism, and writes the receipts E9 asked for.

Slides

  • Before can stop; after can only record. In OpenCode, the hook that can block a call runs inside a plugin, and plugins are TypeScript or JavaScript files. Ours is a thin shim that passes each call to Python and does nothing else. The after-edit check uses OpenCode's formatter setting, which runs a command you name after every write, edit, or patch; that command is Python.
  • Presence is not procedure. In the reference design, a marker file once licensed work that no hook had checked (E3 and E9, the 08-21 incident). A hook earns trust only after you have seen it block.
  • Every call leaves a receipt. One JSON line per tool call: time, tool, path, decision. Black box over narrative.

Prompts

6.1 · The guard, in Python. Approve the prompt for the new test file.

Create guard/guard.py at the project root (outside src/). It reads one JSON object on stdin with "tool" and "args". If the tool is edit, write, or patch and the target path is under tests/, it prints a one-line reason and exits 2; if the tool is shell and the command writes into tests/ (for example with sed -i, >, or tee), it does the same; otherwise it exits 0. Every call appends one JSON line to .receipts/tool-calls.jsonl with the UTC time, tool, path or command, and decision. Add tests/test_guard.py with unittests for allow and block cases. Add .receipts/ to .gitignore. Report the four gate exit codes.

6.2 · The shim.

Run `opencode --version`. Create .opencode/plugins/guard.ts as a thin plugin shim in the format documented for that version: before every tool call, it passes {"tool": ..., "args": ...} as JSON on stdin to `uv run python guard/guard.py`; if that exits non-zero, it blocks the call with the guard's message. No other logic in the TypeScript file. Tell me whether OpenCode must be restarted.

6.3 · The after-edit check.

Create guard/after_edit.py: it runs `uv run ruff format` on the file path it receives and appends one JSON line to .receipts/after-edit.jsonl with the time, path, and ruff's exit code. Add a formatter entry to opencode.json for .py files whose command is ["uv", "run", "python", "guard/after_edit.py", "$FILE"].

Restart OpenCode. Then update the rule in AGENTS.md:

In AGENTS.md, change the tests/ rule to "Enforced by: opencode.json (edit on tests/ asks) and .opencode/plugins/guard.ts -> guard/guard.py (blocks)." Keep the file under 4,000 characters.

6.4 · See it block.

/new
Change tests/test_units.py so that 0 C expects 273.2 K.

See: the call is blocked with the guard's message, even if you would approve the permission prompt. Then:

Show the last five lines of .receipts/tool-calls.jsonl.

6.5 · Health of the whole.

Run `uv run mt health .` and the four gates. Report each exit code, then commit with the message "step 6: guard hook, after-edit check".

10 · Closing: how it fits together

Concept

You built a five-module Python tool, and around it a harness with six kinds of file. Each file answers the four questions: where it is, what reads it, when, and the trace. Each rule that must hold now names its enforcer, and the enforcer has been seen to block.

  • Map it back. Step 1 is E5 and E6. Step 2 is E3 and E11. Step 3 is E5. Step 4 is E2 and E8. Step 5 is E8 and E9. Step 6 is E3, E10, and E11. Setup is E10. E12 is the next commit: tag a release and roll it back once.
  • What to carry out. Write the map, not the encyclopedia. Pair every tell with an enforce. Type every result. Trust receipts over narrative. Keep the human at index zero.
