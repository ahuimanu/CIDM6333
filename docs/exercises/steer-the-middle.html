In-class exercise: Steer the middle

CIDM 6333 · In class, follow along at the screen, each student in their own repository · 60 minutes · Harness: OpenCode · Model: Big Pickle (opencode/big-pickle) or any OpenCode Go model (opencode-go/…) Builds on: everything from E0 to E7, and the codec you built at the screen in the previous Evolution. Feeds: Sortie 8 (controller, worker, reviewer) and the Final System, where the harness that builds your MVP is the outer ring of the figure for this exercise.

Figure for this exercise: Figure 17 · Steer the Middle. The lecture walks the figure from the inside out. This exercise walks it from E0 to E8 in your repository. Figures 09, 14, and 15 are the E8 and E5 items up close.

Files for this exercise (all on the course site; the steps fetch them with curl): codec-spec.md · codec.py · codec-check SKILL.md · reviewer.md · worksheet.md

How to submit: push the exit ticket to your own repository (under your name) in the CIDM6333 organization on GitHub. The repository is the submission. Do not upload files to Canvas. A commit that is on a laptop and not pushed is not submitted.

Why this exercise

Figure 17 draws your system as three rings. The model sits inside the inner ring, where it takes one window in, gives one answer out, and keeps nothing. OpenCode is the middle ring, in other words the loop that builds the window, calls the model, gates the tool call, runs it, and repeats. Your harness is the outer ring, the files you write to steer the middle. Most rows of the table below pair something OpenCode already does by default with the file you write to replace or extend it, and the other two rows are additions. Each row gives the Evolution in which the file was introduced.

OpenCode has You write Introduced
a default prompt AGENTS.md E5
built-in tools (read, edit, shell, webfetch) .opencode/tools/<name>.ts, a shim that calls your Python; a Python MCP server in opencode.json E3, E4
default permissions opencode.json → permission E3
the skill tool, empty .opencode/skills/<name>/SKILL.md E5
built-in commands (/init, /undo, /help) .opencode/commands/<name>.md E2
built-in agents (build, plan, general, explore, scout) .opencode/agents/<name>.md E2, E8
compaction the handoff file; instructions and references in opencode.json E6
nothing: no store between sessions recall.py, memory.jsonl E7
an event bus .opencode/plugins/<name>.ts E10, not this Evolution

In this Evolution you walk that table from E0 to E8. For each row you locate the file in your repository, state what reads it and when, make it fire, and record the trace. If you cannot fill a row, record that as a finding. If you fill a row for the first time in this Evolution, that file is the one to commit.

The last row you build is new to your repository: a reviewer agent that cannot edit. The E8 lecture argues that a reviewer which can change the code it judges will pass its own fix. This one file carries that argument into your harness. The deny in its permission block enforces the rule, the anti-trait in its persona states the rule to the model, and the verdict it returns is a typed claim that cites a location.

What this exercise tests

This exercise tests one statement about the outer ring: every item on it has a file, a reader, a moment it is read, and a trace that it was read. For the reviewer the statement is more specific. The reviewer returns one ReviewResult, it changes no file, and when asked to fix the code it refuses or the permission block refuses for it.

If a row has no trace, or the reviewer edits, you have a finding for the Sortie 8 card. Write down what came back, verbatim.

How the exercise runs

The instructor drives at the screen. You do each step on your own laptop as it is shown, then compare your screen with the one at the front. There is nothing to print. This page stays open beside OpenCode, and you can replay it alone afterwards. Each step has three parts: do, see, record. Record on the worksheet, one line per step.

Steps (60 minutes)

0–5 · Set up

In your repository root:

opencode --version
mkdir -p evolution-08/exercise .opencode
cd evolution-08/exercise
curl -fsSL https://ahuimanu.github.io/CIDM6333/exercises/codec-spec.md -o codec-spec.md
curl -fsSL https://ahuimanu.github.io/CIDM6333/exercises/steer-the-middle-worksheet.md -o worksheet.md
cd ../..

If your codec from the previous Evolution is in the repository, copy it to evolution-08/exercise/codec.py. If it is not, or it has no --selftest, fetch the reference version:

curl -fsSL https://ahuimanu.github.io/CIDM6333/exercises/codec.py -o evolution-08/exercise/codec.py
python3 evolution-08/exercise/codec.py --selftest

See: PASS rot13 and PASS base64, exit code 0. Record: the OpenCode version, the model id, and whether the codec is yours or the reference.

5–9 · E1 · The loop, and its one trace

Do: open OpenCode in the repository root. Type /new, then:

What is in this repository? Name three files and say what each one is for.

See: the TUI shows the loop at work, one tool-call line per call (glob, read, read…), then an answer. Those lines are the middle ring. The model did not read the files. The loop ran read and put the text in the next window.

Record: how many tool calls ran before the answer, and the name of the first tool.

9–13 · E2 · Plan and build are two agents

Do: press Tab. The agent name in the TUI changes from build to plan. Send:

Plan how to add a hex scheme to evolution-08/exercise/codec.py so that it meets codec-spec.md. List the steps. Do not edit anything.

See: plan reads the files and writes steps. It cannot edit, because OpenCode's built-in plan agent denies edits outside ~/.opencode/plan/. The pattern from E2 (plan, then do) is two agent definitions with different permissions. Press Tab again to return to build.

Record: the number of steps in the plan, and whether step 4 of the spec (round trip) appears in them.

13–20 · E3 · Tools as contracts, and the gate

Do: create or edit opencode.json in the repository root so that it contains at least this:

{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "edit": "ask",
    "shell": { "*": "ask", "git diff*": "allow", "git log*": "allow", "git status*": "allow", "python3 evolution-08/exercise/codec.py --selftest": "allow" },
    "skill": { "*": "ask" }
  }
}

Every edit, and every shell command that is not on the allowlist, will now ask. The permission prompt is the trace that the gate held. Then /new and send:

Run the codec self-test and tell me the result. Do not change any file.

See: the model calls shell with the self-test command. Because that exact command is on the allowlist, it runs without asking. Any other command asks. The tool call line shows the command, and the answer quotes PASS.

Record: the command the model ran, verbatim, and whether a permission prompt appeared.

The contract is in Python and the shim is in TypeScript. The codec's command line is the contract. It takes positional arguments and encode or decode, exits 0 on success, exits 2 on a bad scheme or direction, and offers --selftest as the evidence. OpenCode's custom-tool file format is TypeScript, so a tool of your own is a ten-line .ts shim that declares the schema and calls the Python. All logic stays in codec.py.

If there is time (optional, 3 minutes): create .opencode/tools/codec.ts:

import { tool } from "@opencode-ai/plugin"
export default tool({
  description: "Encode or decode text with the course codec (rot13, base64).",
  args: {
    scheme: tool.schema.string().describe("rot13 or base64"),
    direction: tool.schema.string().describe("encode or decode"),
    text: tool.schema.string().describe("the text"),
  },
  async execute(args) {
    return (await Bun.$`python3 evolution-08/exercise/codec.py ${args.scheme} ${args.direction} ${args.text}`.text()).trim()
  },
})

Restart OpenCode, /new, and send Use the codec tool to rot13-encode the word Pickle. The model sees the tool's name, description, and schema every turn. The schema is the contract, and the Python does the work. If the file does not load, skip it. The permission step above is the part this exercise depends on.

20–23 · E4 · MCP: locate, do not build

Do:

grep -n '"mcp"' opencode.json || echo "no mcp block"

See: either the mcp block from the E4 teardown, with a server in it, or no mcp block. An MCP server's tools reach the model the same way a custom tool does. The difference is who wrote the descriptions (Figure 06).

Record: the server name, or none. Either is a complete row.

23–31 · E5 · Rules and a skill

Do, part one. Open AGENTS.md. Its first sentence must state what the system is and what it must never do. If it does not, write that sentence now. Add one line:

- Codec: evolution-08/exercise/codec.py. Spec: evolution-08/exercise/codec-spec.md. Run `python3 evolution-08/exercise/codec.py --selftest` before saying any codec change is done.

Run wc -c AGENTS.md. Stay under 4,000.

Do, part two. If .opencode/skills/ is empty, build one skill:

mkdir -p .opencode/skills/codec-check
curl -fsSL https://ahuimanu.github.io/CIDM6333/exercises/codec-check-SKILL.md -o .opencode/skills/codec-check/SKILL.md

Its name is codec-check and must match the folder. Its body gives the steps: run the self-test, read the spec, report each spec line as met or not met with the evidence, and count the lines met.

Do, part three. /new, then:

Check the codec against its spec and report.

See: a permission prompt for the codec-check skill (you set permission.skill to ask). Allow it. The model loads the body only now. Until this turn it saw one line, the name and description. Then it runs the self-test (allowed) and reads the spec.

Record: wc -c AGENTS.md, whether the skill prompt appeared, and how many of the ten spec lines the report marked as met.

31–35 · E6 · What rides along

Do: add the spec to opencode.json as an instruction file:

"instructions": ["evolution-08/exercise/codec-spec.md"]

(Inside the top-level object, beside permission.) Then /new and send:

Without reading any file: which schemes must the codec support, and what is the round-trip rule? Name your source.

See: the answer comes with no read tool call, because the spec is joined to AGENTS.md and rides every turn. That is the trade E6 described. A file in instructions costs its length on every turn and is never missed. A file the model must read costs nothing until asked, and the model can skip it.

Record: whether a read call ran (it should not), and the source the model gave.

35–39 · E7 · One record, soon stale

Do: if you have evolution-07/lab/recall.py, file one dated fact:

printf '# Codec status\n\nAs of 2026-10-22 the codec supports rot13 and base64. Hex is not implemented.\n' > evolution-08/exercise/m-codec.md
uv run --no-project --python 3.14 evolution-07/lab/recall.py add evolution-08/exercise/m-codec.md --retain-until 2026-10-29

If you do not have recall.py, write the same file and skip the add. Record no retriever.

See: the record id. The record is true now. In ten minutes, after you add hex, it is stale, and nothing in the loop knows. That is the memory drawer from E7 (Figure 14): a memory record is a claim with a date, and the loop does not open the drawer by itself.

Record: the record id, or no retriever.

39–55 · E8 · A reviewer that cannot edit

Do, part one. Create the reviewer:

mkdir -p .opencode/agents
curl -fsSL https://ahuimanu.github.io/CIDM6333/exercises/reviewer.md -o .opencode/agents/reviewer.md

Open it. The frontmatter is the mechanism. It sets mode: subagent and edit: deny, and it allows shell only for git diff, git log, git status, and the self-test. The body is the persona from the E8 lecture, with one role, observable traits, anti-traits, and the reason behind them. The last line asks for exactly one ReviewResult JSON object. Restart OpenCode so the agent loads.

Do, part two. In build, /new, send:

Add a hex scheme to evolution-08/exercise/codec.py so that it meets every line of evolution-08/exercise/codec-spec.md, including selftest coverage. Run the self-test. Do not commit.

See: permission prompts for each edit (allow them), then the self-test with PASS hex. If the model declares done without running the self-test, record that as a finding. The rule is in AGENTS.md, the model read it, and nothing in the loop made it obey.

Do, part three. Send:

@reviewer Review the uncommitted change to evolution-08/exercise/codec.py against evolution-08/exercise/codec-spec.md. Return one ReviewResult JSON object.

See: the task-tool line in the TUI. The primary agent hands the brief to the reviewer, which runs in its own window and returns one message. The message is a JSON object with verdict (PASS, FAIL, or CONCERNS), findings (each with a location), and checked. Run git status. It lists codec.py as the only changed file, and the worker made that change before the review.

Do, part four. Send:

@reviewer Fix the problem you found.

See: either a refusal (the anti-trait) or a denied edit (the permission). Both are the right outcome. If an edit goes through, record it as the main finding of this exercise. A reviewer that can fix the code passes its own fix (E8 lecture, slide 11, row five).

Record: the verdict, the number of findings and whether each has a location, what git status shows, and what happened on "fix it."

55–60 · Close

The memory record from the E7 step says hex is not implemented. That record is now wrong, and the retriever will still score it if asked. Evict it or supersede it:

uv run --no-project --python 3.14 evolution-07/lab/recall.py evict --today 2026-10-30

(The record's retain_until is 2026-10-29, so a --today past that date removes it and logs the eviction. Skip this if you have no retriever.)

Fill the last worksheet column: for each row, was the file in your repository before this exercise? Then commit:

git add -A
git commit -m "E8 exercise: steer the middle; reviewer agent; hex scheme"
git push

Exit ticket (each student, own repository)

  • opencode.json with permission and instructions, and .opencode/tools/codec.ts if you did the optional step.
  • AGENTS.md with the codec line, under 4,000 characters.
  • .opencode/skills/codec-check/SKILL.md (or your existing skill) and .opencode/agents/reviewer.md.
  • evolution-08/exercise/: codec.py with hex and a passing --selftest, codec-spec.md, worksheet.md filled in, m-codec.md, and the reviewer's ReviewResult pasted into review.json.
  • If you have a retriever: memory.jsonl and memory-ledger.jsonl after the eviction.

For Sortie 8 and the Final System: the reviewer in this exercise judged one diff against one spec. Sortie 8 makes the controller do the dispatching, parse the result with no default branch, and route FAIL back with a bound on rounds. The Final System's V&V has to show the same four facts for every outer-ring file: where it is, what reads it, when, and the trace.

Data rules

  • No keys, tokens, passwords, or .env contents in AGENTS.md, any skill, any agent file, or the memory store. Read a file before you send it.
  • Big Pickle is a free model on OpenCode Zen, and Zen's terms say data from the free period may be used to improve the model. Write "the Chase" rather than a classmate's name in any record you send, or use a Go model.
  • The codec, the self-test, and the retriever run on the laptop. The probes send AGENTS.md, the spec, the skill text, and the diff to the model.
