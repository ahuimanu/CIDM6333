From working to operated

  • Working means it ran for you. Operated means someone else can release it, see it, and take it back.
  • A release you have never rolled back is a release you cannot vouch for.
  • Two rules the spine returns to
  • The release is a thing, not a moment: an artifact with a version and a hash. Rollback reinstalls it; no rebuild.
    Secrets are injected at run time. Never in the image, the log, the repository, or the model's context.
  • Tonight's claim, which Sortie 12 will try to disprove
  • A release rolls back in one governed command; the ledger names the released hash; a planted canary secret appears in no image, log, or commit.
    Falsifiers: a manual step; a hash mismatch; the canary found; no attestation event.
04

Serving an agent: a service or a job

  • Decide which one you are shipping before you choose a framework
  • Service (request/response)
  • Job (run to completion)
  • Choose, and write it down
  • A caller sends a request and waits. FastAPI fronts your loop.
    Each request has a time budget; the loop halts inside it
    A retried POST must not run twice: idempotency key
    Long answers stream
    /health reports status and version
  • A trigger starts a run; nobody waits on a socket.
    Budget is turns and dollars, not a request timeout
    Output is an artifact: branch, report, or ledger entry
    The result must say what it did
    Exit code is the only status the scheduler sees
  • Most course systems are jobs wrapped as a service for the demo. Pick one in an ADR; state the lifecycle.
    The mistake: a service with job semantics. A ten-minute POST; a client that times out and retries.
  • A request that outlives its caller becomes an orphan. Decide who owns the halt: loop budget or server timeout.

Containers, secrets, limits

  • Image, config, secret, limit, log: each has a wrong place and a check the Chase can run
  • Concern · Wrong place · Right place · The Chase's check
  • Image / artifact · Built from a dirty tree; tagged latest; rebuilt for rollback · Built from a clean commit; version and hash recorded at release · Hash in the release event equals the hash of what is running
  • Config · Constants in code; a limit stated in a Markdown file · Environment or one config file, read at startup and logged (values, not secrets) · Change the limit without a rebuild; /health or the log shows it
  • Secrets · ENV or COPY in a Dockerfile; .env committed; key echoed in a trace · Injected at run: docker run --env-file (untracked), OS keychain, CI secret store · grep the image history, logs, and git log for the canary: zero hits
  • Rate limits and budgets · The provider's limit is the only limit · Per-run turn and dollar budget; per-key requests per minute; a 429 with Retry-After · Exceed the budget on purpose; the run halts and the ledger says why
  • Logs and traces · Full prompts with user data; tool arguments that carry the key · Structured events; redaction before write; the key never enters the model's context · Search the trace store for the canary and for a real user field
  • FastAPI's container guidance: one process per container; exec form of CMD; --proxy-headers behind a TLS proxy (fastapi.tiangolo.com/deployment/docker).
  • A secret in any image layer is in every copy forever. Deleting it in a later layer does not remove it.

Two ways to ship the same release

  • Tonight's lab offers both; the Sprint asks for one of them to be flown end to end
  • No container: a versioned wheel
  • Container: an image
  • uv version --bump patch → pyproject says 0.1.1
    uv build → dist/myagent-0.1.1-py3-none-any.whl
    Install into a deploy environment: uv venv deploy-env, then uv pip install the wheel.
    Rollback: reinstall the prior wheel from the release record; check its SHA-256 first.
    Works on every laptop; no daemon.
  • docker build -t myagent:0.1.1 . (or podman build)
    The tag is a pointer; the image ID or digest is the release. Record the ID in the release event.
    Rollback: start the prior image by ID.
    Needs Docker or Podman; the lab does not require it.
  • A version number is a name. The hash is the release. Record it at release; check it at rollback.

Unattended runs: who attests a job nobody watched?

  • Scheduling and background agents (21.3): the five controls every vendor now ships in some form
  • Stored trigger
  • Isolated environment
  • Narrow write path
  • Human merge
  • Record and read
  • The prompt and schedule are written ahead of time by an authorized person. The firing proves storage, not consent.
  • One branch with a known prefix (copilot/, claude/, codex/). No push to a protected branch; no agent merge.
  • A person with write access reviews the diff and merges. CI on the agent's branch may wait for approval.
  • A run log exists. Green means the run exited, not that the task succeeded. Somebody reads the transcript.
  • Fresh VM or runner per run; network limited by default; secrets held outside the sandbox.
  • Nobody watched the run. Its record must answer: what changed, under whose authority, who accepted it.

Nygard's stability patterns, applied to an agent

  • Release It!, 2nd ed. (Pragmatic Bookshelf, 2018), 'Stability Antipatterns' and 'Stability Patterns': six that fit a loop with tools
  • Timeouts
  • Circuit Breaker
  • Steady State
  • Every model call and tool call has one. Do not retry at once after a timeout. Queue or halt.
  • After N failures, stop calling the provider or tool and fail the run with a reason. Breaker state in /health.
  • Everything that accumulates must be purged by something: traces, the idempotency store, memory rows, old wheels. No manual clean-up.
  • Fail Fast
  • Governor
  • Force Multiplier (antipattern)
  • Check key, model route, and budget before the first turn. A run that cannot finish should not start.
  • Slow automation down in the unsafe direction so a human can intervene: deletes, deploys, mass writes need a person.
  • Automation that amplifies one wrong decision across the fleet. A scheduled background agent multiplies whatever its prompt gets wrong.
  • The Governor is the course's pattern since E3: a write needs a confirmation event; an irreversible act needs a human.

The Heavy lane and the release ceremony

  • Lite ran gates 1–2 all term. The Final System runs 1–5. Gates 3–5 are the ones a release adds.
  • Gate 3 · Docs
  • Gate 4 · BDD
  • Gate 5 · Human
  • Release notes vs. changelog
  • The README, runbook, and release notes describe the release that exists. A pasted command that fails is a gate failure.
  • Scenarios for the external contract: what a caller of /runs or the CLI can rely on. Executed, not just written.
  • A person attests: Completed, Completed — Partial, or Dropped. The attestation is a ledger event. The agent never records it.
  • The changelog lists every change, for maintainers. Release notes tell a user how to upgrade and roll back.
  • Chapter 21.5: docs gate; BDD for external contracts; human attestation; release notes vs. changelog; the distribution invariant; MX mode.

Worked example: the runbook is one page

  • The Sprint asks for docs/runbook.md. Someone who has never seen your system uses it at 2 a.m.
  • Section · What it says · How the Chase tests it
  • What runs where · Artifact type, where it runs, which port, which environment variable names · Start it from a clean shell with only these steps
  • Release · The one command, what it records, where the hash goes · Run it; find the release event and the hash
  • Health · The route or command; the expected output, with the version · Compare output with the release event
  • Rollback · The one command; the time you measured; what it refuses to do · Run it after a bad release; time it; compare hashes
  • Limits and budgets · Per-run turns and dollars; request rate; what happens when exceeded · Exceed one on purpose
  • Secrets · Where each secret comes from at run time; how to rotate it; the canary check · Run the canary search
  • Known gaps · What the runbook does not cover (e.g. in-memory idempotency store lost on restart) · Check the gap is real and stated

Teardown: Copilot cloud agent, read for mechanism

  • GitHub's PR-native background agent: the review is the gate
  • Mechanism
  • Design choice
  • Cost
  • Failure mode
  • A task arrives from an issue, a panel, or a PR comment. The agent works in an ephemeral Actions environment prepared by .github/workflows/copilot-setup-steps.yml. It pushes to one copilot/ branch and opens a draft PR.
  • Put the human gate where developers already look: the pull request. Only write-access users can start it. It cannot mark its PR ready, approve, or merge. Workflows on its PR wait for a person.
  • Actions minutes plus AI credits per session; a 59-minute ceiling. Review load moves to the humans: every task ends in a PR someone must read.
  • #9 Metagaming the gate: a PR that passes the repo's checks without doing the task. #1 if a workflow can skip a check. The defense: a reviewer who reads the diff.
  • Commits are authored by Copilot, co-authored by the assigning developer, and signed. Attribution answers who asked, not who checked.

Reference design: the distribution invariant and the backfilled releases

  • What ships must be what was declared, and a release that is not recorded did not happen
  • ADR-0.0.31 and gz validate --distribution
  • GHI #830: backfilled releases
  • The distribution invariant is an ADR; a validator checks it before release. What ships is what the repository declares.
    For your system: the release event names version and hash; health reports the same version.
  • Issue #830: releases recorded after the fact. The work shipped before the record existed.
    A backfilled record proves what the tag holds now, not what users installed then.
    Your release event written late is a squawk, not a pass.
  • Two rules: a validator checks the release before it leaves, and the record is written when the release happens, not later.

Flight Card 12 brief — Sortie 12: a release that can be rolled back

  • Expansion · depends on Sortie 11 PASS · Go signed by your Chase in the repo by the date in the course calendar
  • ENVELOPE expansion
    DESIGN CLAIM A release can be rolled back in one governed command; the rollback is in the ledger and
    names the released hash; a planted canary secret appears in no image, log, or commit.
    SYSTEMS UNDER TEST serve entry (FastAPI or CLI) · build (uv build or image) · deploy env · release/rollback
    command · release ledger · runbook · secret injection · attestation
    SUBSTRATE repo + commit · Python 3.14 · uv · model/route · Docker/Podman or none (state which)
    DEPENDS ON Sortie 11 PASS (tracing, cost table, guardrails)

    TEST POINTS
    1 release N -> ledger {release, N, hash_N, ok}; health reports N
    2 release N+1 (planted defect) -> smoke fails; ledger {release, N+1, ok:false}
    3 rollback (one command, timed) -> ledger {rollback, N, hash == hash_N, ok}; health reports N
    4 rebuild N over its own path, then rollback -> refused, or hash mismatch recorded (not ok)
    5 canary search: image history, logs, traces, git log -> zero hits
    6 attest the release -> human attestation event in the ledger

    INSTRUMENTATION release ledger (>= 5 events) · hashes/IDs · health output x3 · rollback seconds · canary grep

    PRE-REGISTERED FALSIFIERS (any ONE => FAIL)
    - rollback needs a manual step, or restores a hash different from hash_N
    - canary found in any artifact
    - a release with no attestation event
    - passed only by editing the ledger, skipping the smoke check, or deleting the defect

    ABORT (halt-not-fail) container engine unavailable (fly the wheel path instead); model route down
    CHASE reads the ledger lines, the hashes, the canary output, and runs the runbook's rollback cold

    SPRINT (code freeze: see course calendar) Sortie 12 log · served + packaged/containerized + release
    + rollback · runbook · Design Analysis · AI_LOG · ceremony booked
