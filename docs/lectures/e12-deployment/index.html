slide 03

From working to operated

Framing. Working means it ran for you, on your machine, while you watched. Operated means a second person can release it, tell which version is live, and roll it back from a written page. Two rules. First, a release is a thing: an artifact with a version and a hash, and a rollback reinstalls that thing. If your rollback is check out the old tag and rebuild, you are releasing a new, untested artifact that happens to share a version number, and I will show you the two hashes later. Second, secrets are injected at run time and appear nowhere else, including the model's context. The claim comes from chapter twenty-one, with one addition: the rollback must name the same hash that was released. The last falsifier is the Heavy lane's: a release with no attestation event is not a release.

The slide's wording in full
  • The release is a thing, not a moment. A built artifact (a wheel or an image) with a version and a hash. Rollback reinstalls a thing that already exists. It never rebuilds from an old commit. / Secrets are injected at run time. The key reaches the process from the environment. It is never in the image, the log, the repository, or the model's context.
  • A release of your system can be rolled back in one governed command; the rollback is in the ledger and names the same artifact hash that was released; and a planted canary secret appears in no image layer, log, or commit. / Falsifiers: a rollback that needs a manual step; a rollback whose hash differs from the release it restores; the canary found in any artifact; a release with no attestation event.
slide 04

Serving an agent: a service or a job

Chapter twenty-one, section one. An agent is served either as a service or as a job, and you choose before you choose a framework. A service has a waiting caller, so it needs a time budget, idempotency, streaming for long answers, and a health route. A job has no waiting caller, so it needs a budget in turns and dollars, an artifact as its output, and an exit code the scheduler can read. Most of your systems are jobs that you will wrap as a service for the demo, and that is fine if the ADR says so. The failure I see every term is the service with job semantics: a long loop behind a POST, a client that times out and retries, and three copies of the agent spending your budget on the same task.

The slide's wording in full
  • A caller sends a request and waits. FastAPI or an equivalent in front of your loop. / Every request has a time budget; the loop halts inside it / A retried POST must not run the agent twice: idempotency key / Long answers stream; the client sees progress / /health reports status and version
  • A trigger starts a run; nobody waits on a socket. A CLI entry point, a cron line, a scheduled cloud agent. / The run has a turn and dollar budget, not a request timeout / Output is an artifact: a branch, a report, a ledger entry / Someone reads the result later; the result must say what it did / Exit code is the only status the scheduler sees
  • Most course systems are jobs that someone wraps as a service for the demo. Either is fine. Pick one in an ADR and state the lifecycle. / The mistake is a service with job semantics: a POST that starts a ten-minute loop, a client that times out at 60 seconds and retries, and three agents doing the same work with your key.
  • A request that outlives its caller becomes an orphan. Decide who owns the halt: the loop's budget or the server's timeout.
slide 05

A served agent in thirty lines (FastAPI)

Thirty lines, and every one of them is a decision from the last slide. The limit comes from the environment. The API key is read at startup inside the lifespan handler, so a missing key stops the process at boot instead of at the first request; that is Nygard's Fail Fast. Health returns the installed version, which is how you will see a rollback from outside. The run route takes an idempotency key as a header, so a client retry returns the first result instead of starting a second agent, and it wraps the loop in a timeout, so the halt happens inside the caller's budget and the caller gets a 504 that says so. The idempotency store is in memory; name that limit in your runbook.

slide 06

Containers, secrets, limits

Five concerns, each with a wrong place, a right place, and a check a peer can run without your help. The row to slow down on is secrets. An ENV line or a COPY of a dot-env file in a Dockerfile puts the key into a layer, and every pull of that image carries it; a later layer that deletes the file does not remove it from history. Inject at run time from an untracked file or a store, and check with a canary: a fake key with a unique string that you plant in your environment, then search the image history, the logs, and the git log for it. Rate limits: the provider's limit is not your limit. Your system needs its own budget per run and per key, and exceeding it on purpose is a test point.

The slide's wording in full
  • FastAPI's container guidance: one process per container; use the exec form of CMD so lifespan shutdown runs; add --proxy-headers behind a TLS proxy (fastapi.tiangolo.com/deployment/docker).
  • A secret in any layer of an image is in every copy of that image forever. Deleting it in a later layer does not remove it.
slide 07

Two ways to ship the same release

Two ways to ship the same thing, and the lab offers both because laptops differ. On the left, uv's own commands: bump the version, build a wheel into dist, install it into a separate environment that plays production. Rollback is reinstalling the prior wheel, and the wheel's hash is in the release record. On the right, an image. The one point to take away from the right panel: a tag is a pointer, and the next docker build with the same tag moves it. The image ID or the registry digest is the release. Both columns end with the same strip: a version is a name; record the hash when you release and check it when you roll back.

The slide's wording in full
  • uv version --bump patch → pyproject says 0.1.1 / uv build → dist/myagent-0.1.1-py3-none-any.whl (and an sdist) / Install into a deploy environment that stands in for production: uv venv deploy-env, then uv pip install the wheel into it. / Rollback: reinstall the prior wheel file from the release record. The release record holds the wheel's SHA-256; the rollback checks it before it installs. / Works on every laptop in the room. No daemon, no admin rights.
  • docker build -t myagent:0.1.1 . (or podman build) / The tag is a pointer. The image ID (or the registry digest) is the release. Record the ID in the release event, because a tag can be moved to a different image by the next build. / Rollback: stop the running container and start the prior image by ID or by a tag you have verified still points at that ID. / Needs Docker or Podman. Not every laptop can run it; that is why the lab does not require it.
  • A version number is a name. The hash is the release. Record the hash when you release and check it when you roll back.
slide 08

Unattended runs: who attests a job nobody watched?

Section three of the chapter asks who attests an unattended run. The vendors have converged on five controls, and you will see each of them in the teardowns. A stored trigger, which proves somebody wrote the prompt earlier and proves nothing about whether this run's actions were approved. An isolated environment with network limited by default. A narrow write path: one branch with a prefix, no merge. A human merge. And a record that someone reads, because a green status only says the process exited. Anthropic's routines documentation says that last point in so many words. For your system: if you schedule anything, the scheduled run writes to its own branch or its own file and a person accepts it, and the ledger shows both.

The slide's wording in full
  • The prompt and schedule are written ahead of time by an authorized person. The firing is evidence of storage, not of consent for this run's actions.
  • One branch with a known prefix (copilot/, claude/, codex/). No push to a protected branch; no merge by the agent.
  • A run log exists. A green status means the run exited; it does not mean the task succeeded. Somebody reads the transcript.
  • Fresh VM or runner per run; network limited by default; secrets held outside the sandbox where the vendor supports it.
  • Nobody watched the run, so the run's record must answer three questions: what did it change, under whose authority, and who accepted it.
slide 09

Nygard's stability patterns, applied to an agent

Nygard's second edition, 2018, which is on the reading list. Six cards from the stability chapters that map onto an agent loop. Timeouts on every call, and his advice not to retry at once, because a timeout usually means the fault is still there. Circuit Breaker on a flaky provider, with the state visible in health. Steady State, which is the one students forget: every store that grows needs a purge. Fail Fast, which you just saw in the lifespan handler. Then the two that speak most directly to automation. Force Multiplier is the antipattern: automation that spreads one bad decision everywhere, and a scheduled agent is exactly that. Governor is the answer: resistance in the unsafe direction, so that a person can step in. That is the confirmation gate you built in week three, applied to deployment.

The slide's wording in full
  • Every model call and tool call has one. Nygard: do not retry at once after a timeout; the fault is probably still there. Queue or halt.
  • After N failures from a provider or tool, stop calling it for a period and fail the run with a reason. Expose the breaker's state in /health.
  • Check the key, the model route, and the budget before the first turn. A run that cannot finish should not start.
  • Slow automation down in the unsafe direction so a human can intervene: deletes, deploys, mass writes need a pause and a person.
  • Automation that amplifies one wrong decision across the fleet. A background agent on a schedule is a force multiplier for whatever its prompt gets wrong.
  • The Governor is the pattern the course has been building since E3: a write needs a confirmation event, and an irreversible act needs a human.
slide 10

The Heavy lane and the release ceremony

All term you ran the Lite lane, gates one and two, ADR and tests. The Final System runs the Heavy lane, and the three gates a release adds are here. Docs: the docs describe the release that exists, and the test is to paste every command from the runbook. BDD: scenarios for the contract a caller relies on, and they run. Human: an attestation event in the ledger with one of three words, recorded by you. You have seen the reference design's incidents where an agent recorded an attestation that was never given; that is why the agent never records Gate 5. Last card: the changelog is for maintainers, the release notes are for the person who has to upgrade or roll back.

The slide's wording in full
  • The README, the runbook, and the release notes describe the release that exists. A command in the docs that fails when pasted is a gate failure.
  • Scenarios for the external contract: what a caller of /runs, or a user of the CLI, can rely on. Given, when, then; executed, not just written.
  • A person attests: Completed, Completed — Partial, or Dropped. The attestation is an event in the ledger. The agent never records it for you.
  • The changelog is every change, for maintainers. Release notes are what a user must know to upgrade and to roll back. Both name the version and the date.
  • Chapter 21.5: docs gate; BDD for external contracts; human attestation; release notes vs. changelog; the distribution invariant; MX mode. The reference design segment covers the last two.

slide 15

Teardown: Copilot cloud agent, read for mechanism

Copilot's agent, read for the four things we always read for. The mechanism: a task arrives, the agent runs in an Actions environment you can prepare with a setup-steps workflow, and it pushes to one branch and opens a draft. The design choice is to place the human gate in the pull request, where developers already work, and to deny the agent every action that would close that gate itself: no ready-for-review, no approve, no merge, and no CI run until a person approves it. The cost is minutes, credits, and review load. The failure modes are metagaming the gate, a PR that satisfies the checks but not the task, and safeguard circumvention if the agent can edit the workflow that checks it. The strip: the commits carry the assigner as co-author, which records who asked; nothing records who checked except the review.

The slide's wording in full
  • A task arrives from an issue, a panel, or a PR comment. The agent works in an ephemeral Actions environment prepared by .github/workflows/copilot-setup-steps.yml (job must be named copilot-setup-steps; on the default branch). It pushes to one copilot/ branch and opens a draft PR.
  • Put the human gate where developers already look: the pull request. Only users with write access can start it. It cannot mark its PR ready, approve, or merge. Actions workflows on its PR do not run until a person clicks Approve and run workflows.
  • Actions minutes plus AI credits per session. A 59-minute ceiling per session. Review load moves to the humans: every task ends in a PR someone must read.
  • #9 Metagaming the gate: a PR that passes the repo's checks without doing the task. #1 if a workflow can be edited to skip a check. The defense is a reviewer who reads the diff, not the PR summary.
  • Commits are authored by Copilot with the assigning developer as co-author, and signed. Attribution answers who asked; it does not answer who checked.

Teardown: scheduled agents and the stored prompt

Scheduled agents. The routines documentation is unusually direct, and I quote it on the left: the trigger attests only that the prompt was stored ahead of time, it is not consent for the actions of the run, text sent with a fire is wrapped as untrusted, and a green status does not mean the task succeeded. Read that against Appendix C. Hallucinated authorization is acting as if the schedule were the approval. Fabrication by status is reporting green as done. And a nightly schedule is Nygard's force multiplier. The Governor for your system is simple: a scheduled run writes only to its own branch or file, a person accepts it, and the ledger has two events, not one.

The slide's wording in full
  • Routines. The saved prompt runs as the assigned task, but the trigger 'attests only that the prompt was stored ahead of time' and 'can't act as approval or consent for actions during the run.' Text sent with an API fire arrives wrapped and labelled as untrusted data. A green run status 'does not mean the task in your prompt succeeded.' Runs have no permission-mode picker; included connectors can write without asking. / Actions cron. Scheduled workflows run from the default branch; in public repositories GitHub disables them after 60 days without activity. Secrets come from the Actions store. / Codex scheduled tasks. Run on a schedule or app event, locally, in a worktree, or in the cloud; results land in a Scheduled inbox.
  • #7 Hallucinated authorization: the run acts as if the schedule were consent. The routine docs deny it in writing; your system must deny it in code. / #3 Fabrication by status: 'green' reported as 'done.' / Force Multiplier: a nightly run repeats one wrong prompt every night. / Governor for your system: a scheduled run writes only to its own branch or file; a person accepts it; the ledger shows the run and the acceptance as two events.

slide 18

Live Design Analysis on the board: Copilot cloud agent (2025–26)

The live Design Analysis. On the board we do the two parts that are not on the slide: the why paragraph and the judgment loop. The strip gives you the skeleton. The decision is that the pull request is the gate. It privileges reviewability, because every change arrives in the place developers already review. It costs reviewer attention, and the more tasks you assign the more that cost grows. Its failure mode is metagaming the gate. The mechanism that preserves it is that the agent cannot merge, cannot approve, and cannot start CI on its own branch. Ask the room which component is the weakest line. My answer is memory: nothing persists but the branch, which is a design choice with a cost.

The slide's wording in full
  • Research, plan, then code; since 04/2026 no longer limited to PR workflows (can work on a branch before a PR)
  • The repository and its instruction files; the session ends with the branch and the PR as the only durable state
  • One agent, one repository, one branch per task; hands off to a human through the PR; third-party agents can be assigned too
  • Runs the repo's checks; reviewers comment with @copilot and it iterates; CI waits for a human's approval
  • Write-access users only; cannot approve or merge; commits co-authored by the assigner and signed; rulesets and admin disable
  • Ephemeral Actions runner; firewall on internet access; 59-minute session cap; billed in Actions minutes and AI credits
  • Judgment loop to finish aloud: Decision: the PR is the gate. Privileged: reviewability. Cost: review load. Failure mode: #9. Preservation: the agent cannot merge.

Reference design: MX mode

In June an audit found seventy validate scopes behind one function with a hundred and sixty-two parameters, and a hundred and sixteen handoffs; the response was MX mode and the rule that amendments append. Loose in the bay, hard at the door: be fast and untidy where the work is private, and hold every gate where the work leaves. The failure it answers is the opposite arrangement, which is common: strict rules everywhere inside and a release that opens for anything green. Your door is the deploy environment and the ceremony.

The slide's wording in full
  • What happened (Appendix G, 2026-06-20). An audit found 70 validate scopes behind one 162-parameter function and 116 handoffs. The response was MX mode and a rule that amendments append and are never edited inline. / What the phrase means for a release. Inside the hangar (a branch, a scratch environment, the bay) work can be untidy and fast. At the door (the push, the release, the ceremony) every gate holds and nothing is waived. The mistake it answers is the reverse: strict rules on every keystroke, and a door that opens for anything green. / For your Sortie. Your deploy environment is the door. The rollback command, the canary search, and the attestation run there, every time. /
slide 22

Evaluation lens: a strong Sortie 12

Weak: rollback by rebuild, a version with no hash, a tag as the only record, a key in the image, a runbook no one pasted, and green reported as done. Sound: one command each way with ledger events, matching hashes, version visible in health before and after, a canary search with zero hits, a timed rollback, and an attestation. Exceptional: the rollback refuses a mismatched hash, released artifacts are out of the build's reach, both paths flown, a Governor on anything unattended, a breaker visible in health, and the Chase runs your runbook cold.

The slide's wording in full
  • Rollback is 'git checkout v0.1.0 and rebuild' / Release event has a version but no hash or image ID / Image tagged latest; the tag is the only record / API key in a Dockerfile ENV line, a committed .env, or a trace / Runbook written from memory; a pasted command fails / Green status reported as a successful scheduled run
  • One command releases; one command rolls back; both append to the ledger / Rollback event names the same hash as the release it restores / Health reports the version; checked before and after rollback / Canary secret planted; image history, logs, and git log searched: zero hits / Rollback timed; the number is in the runbook / Human attestation event for the release
  • Rollback refuses an artifact whose hash differs from the release event / Released artifacts kept where a build cannot overwrite them / Both paths flown (wheel and image), same ledger format / A Governor: a scheduled or background run writes only to its branch and waits for a person / Circuit breaker on the model route, visible in /health / A stranger (the Chase) runs the runbook cold and succeeds

From working to operated

  • Working means it ran for you. Operated means someone else can release it, see it, and take it back.
  • A release you have never rolled back is a release you cannot vouch for.
  • Two rules the spine returns to
  • The release is a thing, not a moment: an artifact with a version and a hash. Rollback reinstalls it; no rebuild.
    Secrets are injected at run time. Never in the image, the log, the repository, or the model's context.
  • A release rolls back in one governed command; the ledger names the released hash; a planted canary secret appears in no image, log, or commit.
    Falsifiers: a manual step; a hash mismatch; the canary found; no attestation event.

Serving an agent: a service or a job

  • Decide which one you are shipping before you choose a framework
  • Service (request/response)
  • Job (run to completion)
  • Choose, and write it down
  • A caller sends a request and waits. FastAPI fronts your loop.
    Each request has a time budget; the loop halts inside it
    A retried POST must not run twice: idempotency key
    Long answers stream
    /health reports status and version
  • A trigger starts a run; nobody waits on a socket.
    Budget is turns and dollars, not a request timeout
    Output is an artifact: branch, report, or ledger entry
    The result must say what it did
    Exit code is the only status the scheduler sees
  • Most course systems are jobs wrapped as a service for the demo. Pick one in an ADR; state the lifecycle.
    The mistake: a service with job semantics. A ten-minute POST; a client that times out and retries.
  • A request that outlives its caller becomes an orphan. Decide who owns the halt: loop budget or server timeout.

Containers, secrets, limits

  • Image, config, secret, limit, log: each has a wrong place and a check the Chase can run
  • Concern · Wrong place · Right place · The Chase's check
  • Image / artifact · Built from a dirty tree; tagged latest; rebuilt for rollback · Built from a clean commit; version and hash recorded at release · Hash in the release event equals the hash of what is running
  • Config · Constants in code; a limit stated in a Markdown file · Environment or one config file, read at startup and logged (values, not secrets) · Change the limit without a rebuild; /health or the log shows it
  • Secrets · ENV or COPY in a Dockerfile; .env committed; key echoed in a trace · Injected at run: docker run --env-file (untracked), OS keychain, CI secret store · grep the image history, logs, and git log for the canary: zero hits
  • Rate limits and budgets · The provider's limit is the only limit · Per-run turn and dollar budget; per-key requests per minute; a 429 with Retry-After · Exceed the budget on purpose; the run halts and the ledger says why
  • Logs and traces · Full prompts with user data; tool arguments that carry the key · Structured events; redaction before write; the key never enters the model's context · Search the trace store for the canary and for a real user field
  • FastAPI's container guidance: one process per container; exec form of CMD; --proxy-headers behind a TLS proxy (fastapi.tiangolo.com/deployment/docker).
  • A secret in any image layer is in every copy forever. Deleting it in a later layer does not remove it.

Two ways to ship the same release

  • No container: a versioned wheel
  • Container: an image
  • uv version --bump patch → pyproject says 0.1.1
    uv build → dist/myagent-0.1.1-py3-none-any.whl

    Rollback: reinstall the prior wheel from the release record; check its SHA-256 first.
    Works on every laptop; no daemon.

Nygard's stability patterns, applied to an agent

  • Release It!, 2nd ed. (Pragmatic Bookshelf, 2018), 'Stability Antipatterns' and 'Stability Patterns': six that fit a loop with tools
  • Timeouts
  • Circuit Breaker
  • Steady State
  • Every model call and tool call has one. Do not retry at once after a timeout. Queue or halt.
  • After N failures, stop calling the provider or tool and fail the run with a reason. Breaker state in /health.
  • Everything that accumulates must be purged by something: traces, the idempotency store, memory rows, old wheels. No manual clean-up.
  • Fail Fast
  • Governor
  • Force Multiplier (antipattern)
  • Check key, model route, and budget before the first turn. A run that cannot finish should not start.
  • Slow automation down in the unsafe direction so a human can intervene: deletes, deploys, mass writes need a person.
  • Automation that amplifies one wrong decision across the fleet. A scheduled background agent multiplies whatever its prompt gets wrong.
  • The Governor is the course's pattern since E3: a write needs a confirmation event; an irreversible act needs a human.
