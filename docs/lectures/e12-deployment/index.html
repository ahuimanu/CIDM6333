From working to operatedWorking means it ran for you. Operated means someone else can release it, see it, and take it back.

Run the rollback before you vouch for the release, because until then the rollback is untested.

Two rules the spine returns to

The release is an artifact with a version and a hash. Rollback reinstalls that artifact and never rebuilds it.

Secrets are injected at run time. They appear in no image, log, repository, or model context.

The design claim Sortie 12 will try to disprove

A release rolls back in one governed command; the ledger records the released hash; a planted canary secret appears in no image, log, or commit.

Falsifiers: a manual step; a hash mismatch; the canary found; no attestation event.

Serving an agent: a service or a jobDecide which one you are shipping before you choose a framework

Service (request/response)

A caller sends a request and waits. FastAPI fronts your loop.

Each request has a time budget; the loop halts inside it

A retried POST must not run twice: idempotency key

Long answers stream

/health reports status and version

Job (run to completion)

A trigger starts a run; nobody waits on a socket.

Budget is turns and dollars, not a request timeout

Output is an artifact: branch, report, or ledger entry

The result must say what it did

Exit code is the only status the scheduler sees

Choose, and write it down

Your system may be a job that you wrap as a service for the demo. Pick one in an ADR and state the lifecycle.

The mistake is a service with job semantics: a ten-minute POST, and a client that times out and retries.

A request that outlives its caller becomes an orphan. Decide who owns the halt: loop budget or server timeout.

A served agent in thirty lines (FastAPI)Run with: fastapi run src/myagent/serve.py (fastapi[standard]; production server, 0.0.0.0:8000 by default)

import asyncio, os                        # src/myagent/serve.py; agent_loop() is your E1-E11 loop
from contextlib import asynccontextmanager
from importlib.metadata import version
from fastapi import FastAPI, Header, HTTPException

TURN_TIMEOUT_S = float(os.environ.get("TURN_TIMEOUT_S", "30"))   # limits from config
_seen: dict[str, dict] = {}              # idempotency store; in-process (restart forgets)

@asynccontextmanager
async def lifespan(app):
    app.state.api_key = os.environ["MODEL_API_KEY"]   # injected; missing = fail at boot
    yield                                             # shutdown: flush ledger, close clients

app = FastAPI(lifespan=lifespan)

@app.get("/health")
def health():
    return {"status": "ok", "version": version("myagent")}   # rollback visible here

@app.post("/runs")
async def run(task: dict, idempotency_key: str = Header(...)):   # Idempotency-Key
    if idempotency_key in _seen:                  # a retried POST gets the first result
        return _seen[idempotency_key]
    try:
        result = await asyncio.wait_for(agent_loop(task), TURN_TIMEOUT_S)
    except TimeoutError:                          # halt inside the caller's budget
        raise HTTPException(504, "agent exceeded its time budget; halted")
    _seen[idempotency_key] = result
    return result

Two ways to ship the same releaseThe lab offers both. The Sprint asks you to fly one of them end to end

No container: a versioned wheel

uv version --bump patch → pyproject says 0.1.1

uv build → dist/myagent-0.1.1-py3-none-any.whl

Install into a deploy environment: uv venv deploy-env, then uv pip install the wheel.

Rollback: reinstall the prior wheel from the release record; check its SHA-256 first.

Works on every laptop; no daemon.

Container: an image

docker build -t myagent:0.1.1 . (or podman build)

The tag is a pointer; the image ID or digest is the release. Record the ID in the release event.

Rollback: start the prior image by ID.

Needs Docker or Podman; the lab does not require it.

A version number is only a name, and the hash is the release. Record the hash at release and check it at rollback.

Nygard's stability patterns, applied to an agentRelease It!, 2nd ed. (Pragmatic Bookshelf, 2018), 'Stability Antipatterns' and 'Stability Patterns': six that fit a loop with tools

Timeouts

Every model call and tool call has one. Do not retry at once after a timeout. Queue or halt.

Circuit Breaker

After N failures, stop calling the provider or tool and fail the run with a reason. Breaker state in /health.

Steady State

Everything that accumulates must be purged by something: traces, the idempotency store, memory rows, old wheels. No manual clean-up.

Fail Fast

Check key, model route, and budget before the first turn. A run that cannot finish should not start.

Governor

Slow automation down in the unsafe direction so a human can intervene: deletes, deploys, mass writes need a person.

Force Multiplier (antipattern)

Automation that amplifies one wrong decision across the fleet. A scheduled background agent multiplies whatever its prompt gets wrong.

The Governor is the course's pattern since E3: a write needs a confirmation event; an irreversible act needs a human.

The common mistake: rollback by rebuild

21cb6c3d…

relcheck 0.1.0 wheel, first build: SHA-256 recorded in the release event

4aefd5f6…

relcheck 0.1.0 wheel, rebuilt after the version was set back: same file name, different bytes

0.1 s

time to roll back by reinstalling the recorded wheel into the deploy environment

What happened. I set the version back to 0.1.0 and ran uv build again. The new wheel overwrote the old, and the rollback installed it with a mismatched hash.

Why it passes a careless check. Version, file name, and health say 0.1.0. Only the hash differs.

Keep released artifacts where a build cannot overwrite them, and make rollback refuse a hash that differs from the release event.

Teardown: Copilot cloud agent, read for mechanismGitHub's PR-native background agent: the review is the gate

Mechanism

A task arrives from an issue, a panel, or a PR comment. The agent works in an ephemeral Actions environment prepared by .github/workflows/copilot-setup-steps.yml. It pushes to one copilot/ branch and opens a draft PR.

Design choice

Put the human gate where developers already look: the pull request. Only write-access users can start it. It cannot mark its PR ready, approve, or merge. Workflows on its PR wait for a person.

Cost

Actions minutes plus AI credits per session; a 59-minute ceiling. Review load moves to the humans: every task ends in a PR someone must read.

Failure mode

#9 Metagaming the gate: a PR that passes the repo's checks without doing the task. #1 if a workflow can skip a check. The defense is a reviewer who reads the diff.

Commits are authored by Copilot, co-authored by the assigning developer, and signed. Attribution answers who asked. Only the review records who checked.

Production Deployment

Evolution 12 is the last lecture. Through eleven Evolutions your system has worked on your laptop while you watched it. In this Evolution it becomes a system that runs when you are not watching, and one that you can take back when it goes wrong. As used in this lecture, a system is operated when someone other than its author can release it, see which version is live, and roll it back from a written page. The survey covers the background agents that the vendors now run for you in the cloud and on a schedule, and reads each one for who attests an unattended run. The build serves, packages, releases, and rolls back your system, with the rollback in the ledger.

From working to operated

Working means the system ran for you, on your machine, while you watched. Operated means a second person can release it, tell which version is live, and roll it back from a written page. The lecture adds two rules. First, a release is an artifact with a version and a hash, and a rollback reinstalls that artifact. If your rollback is to check out the old tag and rebuild, you are releasing a new, untested artifact that happens to share a version number, and I will show you the two hashes later in the lecture. Second, the process receives its secrets at run time, and they appear nowhere else, the model's context included. Sortie 12 tests the design claim from chapter twenty-one with one addition: the rollback must record the same hash that was released. The last falsifier belongs to the Heavy lane: a release with no attestation event does not count as a release.

Serving an agent: a service or a job

Chapter twenty-one, section one, distinguishes two ways to serve an agent: as a service or as a job. You choose between them before you choose a framework. A service has a waiting caller, so it needs a time budget, an idempotency key, streaming for long answers, and a health route. A job has no waiting caller, so it needs a budget in turns and dollars, an artifact as its output, and an exit code the scheduler can read. A job that you wrap as a service for the demo is an acceptable design if the ADR says so. The failure to avoid is the service with job semantics: a long loop behind a POST, a client that times out and retries, and three copies of the agent spending your budget on the same task.

A served agent in thirty lines (FastAPI)

The served agent is thirty lines, and each line carries a decision from the previous slide. The per-turn timeout (TURN_TIMEOUT_S) comes from the environment. The lifespan handler reads the API key at startup, so a missing key stops the process at boot instead of at the first request; that is Nygard's Fail Fast pattern. The health route returns the installed version, which is how you will see a rollback from outside the process. The run route takes an idempotency key as a header, so a client retry returns the first result instead of starting a second agent, and it wraps the loop in a timeout, so the halt happens inside the caller's budget and the caller gets a 504 that says so. I ran this file with the test client: a repeated key calls the loop once, a slow task returns 504, and a missing key header returns 422. The idempotency store is in memory, so state that limit in your runbook.

Containers, secrets, limits

Five concerns appear in the table, each with a wrong place, a right place, and a check a peer can run without your help. The row to slow down on is secrets. An ENV line or a COPY of a dot-env file in a Dockerfile puts the key into an image layer, and every pull of that image carries it; a later layer that deletes the file does not remove it from the history. Inject the key at run time from an untracked file or a secret store, and check with a canary, in other words a fake key with a unique string that you plant in your environment and then search for in the image history, the logs, and the git log. The provider's rate limit does not protect your budget. Your system needs its own budget per run and per key, and exceeding that budget on purpose is a test point. The note on the slide is FastAPI's own container guidance.

Two ways to ship the same release

There are two ways to ship the same release, and the lab offers both because laptops differ. The left panel uses uv's own commands: bump the version, build a wheel into dist, and install it into a separate environment that stands in for production. Rollback reinstalls the prior wheel, and the wheel's hash is in the release record. The right panel ships an image. The point to take from that panel is that a tag is a pointer, and the next docker build with the same tag moves it, so the image ID or the registry digest is the release. Both panels end on the same rule: a version number is only a name, so record the hash when you release and check it when you roll back.

Unattended runs: who attests a job nobody watched?

Section three of the chapter asks who attests an unattended run. The vendors in the teardown table ship the same five controls in some form, and you will see each control in the teardowns. The first is a stored trigger, which proves that somebody wrote the prompt earlier and proves nothing about whether this run's actions were approved. The second is an isolated environment with the network limited by default. The third is a narrow write path: one branch with a prefix, and no merge by the agent. The fourth is a human merge. The fifth is a record that someone reads, because a green status says only that the process exited; Anthropic's routines documentation states that last point in so many words. For your system the rule is this: if you schedule anything, the scheduled run writes to its own branch or its own file, a person accepts it, and the ledger shows both events.

Nygard's stability patterns, applied to an agent

Nygard's second edition of Release It!, 2018, is on the reading list, and the slide takes six cards from its stability chapters that map onto an agent loop. Timeouts go on every call, and Nygard advises against an immediate retry, because the fault is probably still there when the timeout fires. A Circuit Breaker guards a flaky provider, with the breaker's state visible in health. Steady State requires that every store that grows has a purge, and the idempotency store in the served agent is the example to check. Fail Fast is what you saw in the lifespan handler. The last two speak directly to automation. Force Multiplier is the antipattern: automation that spreads one bad decision everywhere, and a scheduled agent is that automation. Governor is the answer: resistance in the unsafe direction, so that a person can step in. The Governor is the confirmation gate you built in Evolution 3, applied to deployment.

The Heavy lane and the release ceremony

Through the term you ran the Lite lane, gates one and two, the ADR and the tests. The Final System runs the Heavy lane, and the slide lists the three gates a release adds. Gate 3 is docs: the docs describe the release that exists, and the test is to paste every command from the runbook. Gate 4 is BDD: scenarios for the contract a caller relies on, and the scenarios run. Gate 5 is human: an attestation event in the ledger with one of three words, recorded by you. You have seen the reference design's incidents in which an agent recorded an attestation that nobody gave; for this reason the agent never records Gate 5. The last card separates two documents: the changelog is for maintainers, and the release notes are for the person who has to upgrade or roll back.

The common mistake: rollback by rebuild

The common mistake is rollback by rebuild, and I made it on purpose while I wrote the lab. I built version 0.1.0, released it, and recorded its hash. Then I set the version back and built again, which is what a rollback by rebuild does. The result was the same file name, the same version string, and different bytes; the first eight characters of the two hashes are on the slide. The rollback installed the new file, health reported 0.1.0, and only the hash showed that the running artifact differed from the released one. In my run the smoke test caught the difference because the code had changed; a subtle change would have passed the smoke test and left the hash as the only evidence. The fix is in the strip, and it is step four of the lab: keep released artifacts out of the build's reach, and make the rollback compare hashes.

Teardown: Copilot cloud agent, read for mechanism

The Copilot cloud agent teardown reads for the four headings every teardown uses: mechanism, design choice, cost, and failure mode. The mechanism is that a task arrives, the agent runs in an Actions environment you can prepare with a setup-steps workflow, and it pushes to one branch and opens a draft pull request. The design choice places the human gate in the pull request, where developers already work, and denies the agent every action that would close that gate itself: no ready-for-review, no approve, no merge, and no CI run until a person approves it. The cost is Actions minutes, AI credits, and review load. The failure modes are metagaming the gate, in other words a PR that satisfies the checks but not the task, and safeguard circumvention if the agent can edit the workflow that checks it. The strip states the attribution rule: the commits carry the assigner as co-author, which records who asked, and only the review records who checked.

Teardown: scheduled agents and the stored prompt

The scheduled-agent teardown starts from the routines documentation, which I quote on the left panel because it states the rule in plain words: the trigger attests only that the prompt was stored ahead of time, it is not consent for the actions of the run, text sent with a fire arrives wrapped as untrusted data, and a green status does not mean the task succeeded. Read those four lines against Appendix C. Hallucinated authorization (failure mode 7) occurs when the run acts as if the schedule were the approval. Fabrication by status (failure mode 3) occurs when the run reports green as done. A nightly schedule is Nygard's Force Multiplier, because it repeats one wrong prompt every night. The Governor for your system follows: a scheduled run writes only to its own branch or file, a person accepts it, and the ledger records the run and the acceptance as two separate events.

Reference design: MX mode

The reference design's phrase for this Evolution is loose in the bay, hard at the door. In June an audit found seventy validate scopes behind one function with a hundred and sixty-two parameters, and a hundred and sixteen handoffs; the response was MX mode and the rule that amendments append. The phrase means that work can be fast and untidy where it is private, and that every gate holds where the work leaves. The arrangement it answers is the reverse one: strict rules on every keystroke inside, and a release door that opens for anything green. Evaluation lens: a strong Sortie 12

A weak Sortie 12 rolls back by rebuild, records a version with no hash, keeps a tag as the only record, leaves a key in the image, submits a runbook no one pasted, and reports green as done. A sound Sortie 12 has one command each way with ledger events, matching hashes, the version visible in health before and after, a canary search with zero hits, a timed rollback, and an attestation. An exceptional Sortie 12 adds a rollback that refuses a mismatched hash, released artifacts kept out of the build's reach, both paths flown, a Governor on anything unattended, a breaker visible in health, and a runbook the Chase runs cold.

Flight Card 12 brief: Sortie 12, a release that can be rolled back

Flight Card 12 expands the envelope. It has six test points: a good release, a bad release that the smoke check catches, a timed one-command rollback whose hash matches the first release, the rebuild trap from the common-mistake slide, the canary search, and the attestation.
