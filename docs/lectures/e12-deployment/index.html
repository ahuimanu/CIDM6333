slide 03

From working to operated

As used in this course, working means the system ran for you, on your machine, while you watched. Operated means a second person can release it, tell which version is live, and roll it back from a written page. Two rules follow from that definition. First, a release is an artifact with a version and a hash, and a rollback reinstalls that artifact. If your rollback is to check out the old tag and rebuild, you are releasing a new, untested artifact that happens to share a version number, and I will show you the two hashes later in the lecture. Second, the process receives its secrets at run time, and they appear nowhere else, the model's context included. Sortie 12 tests the design claim from chapter twenty-one with one addition: the rollback must record the same hash that was released. The last falsifier belongs to the Heavy lane: a release with no attestation event fails the card, because nobody has attested that the release exists.

The slide's wording in full
  • The release is a built artifact (a wheel or an image) that carries a version and a hash. Rollback reinstalls an artifact that already exists and never rebuilds from an old commit. / The deploy environment injects secrets at run time: the key reaches the process from the environment. The key never appears in the image, the log, the repository, or the model's context.
  • A release of your system can be rolled back in one governed command; the rollback is in the ledger and records the same artifact hash that was released; and a planted canary secret appears in no image layer, log, or commit. / Falsifiers: a rollback that needs a manual step; a rollback whose hash differs from the release it restores; the canary found in any artifact; a release with no attestation event.
slide 04

Serving an agent: a service or a job

Chapter twenty-one, section one, serves an agent either as a service or as a job, and you choose between them before you choose a framework. A service has a waiting caller, so it needs a time budget, an idempotency key, streaming for long answers, and a health route. A job has no waiting caller, so it needs a budget in turns and dollars, an artifact as its output, and an exit code the scheduler can read. A job that you wrap as a service for the demo is an acceptable design if the ADR says so. The failure to avoid is the service with job semantics: a long loop behind a POST, a client that times out and retries, and three copies of the agent spending your budget on the same task.

The slide's wording in full
  • A caller sends a request and waits. FastAPI or an equivalent in front of your loop. / Every request has a time budget; the loop halts inside it / An idempotency key keeps a retried POST from running the agent twice / Long answers stream; the client sees progress / /health reports status and version
  • A trigger starts a run; nobody waits on a socket. A CLI entry point, a cron line, a scheduled cloud agent. / The run has a turn budget and a dollar budget in place of a request timeout / Output is an artifact: a branch, a report, a ledger entry / A person reads the result later, so the result must state what the run did / Exit code is the only status the scheduler sees
  • A course system can be a job that a student wraps as a service for the demo. Either lifecycle is acceptable. Pick one in an ADR and state the lifecycle. / The failure case is a service with job semantics: a POST that starts a ten-minute loop, a client that times out at 60 seconds and retries, and three agents doing the same work with your key.
  • A request that outlives its caller becomes an orphan. Decide which mechanism halts the run: the loop's budget or the server's timeout.
slide 05

A served agent in thirty lines (FastAPI)

The served agent is thirty lines, and each line carries a decision from the previous slide. The turn limit comes from the environment. The lifespan handler reads the API key at startup, so a missing key stops the process at boot instead of at the first request; that is Nygard's Fail Fast pattern. The health route returns the installed version, which is how you will see a rollback from outside the process. The run route takes an idempotency key as a header, so a client retry returns the first result instead of starting a second agent, and it wraps the loop in a timeout, so the halt happens inside the caller's budget and the caller gets a 504 that says so. I ran this file with the test client: a repeated key calls the loop once, a slow task returns 504, and a missing key header returns 422. The idempotency store is in memory, so state that limit in your runbook.

slide 06

Containers, secrets, limits

The table lists five concerns, each with a wrong place, a right place, and a check a peer can run without your help. The row to slow down on is secrets. An ENV line or a COPY of a dot-env file in a Dockerfile puts the key into an image layer, and every pull of that image carries it; a later layer that deletes the file does not remove it from the history. Inject the key at run time from an untracked file or a secret store, and check with a canary, in other words a fake key with a unique string that you plant in your environment and then search for in the image history, the logs, and the git log. The provider's rate limit does not protect your budget. Your system needs its own budget per run and per key, and exceeding that budget on purpose is a test point. The note on the slide is FastAPI's own container guidance.

The slide's wording in full
  • FastAPI's container guidance: one process per container; use the exec form of CMD so lifespan shutdown runs; add --proxy-headers behind a TLS proxy (fastapi.tiangolo.com/deployment/docker).
  • A secret in any layer of an image is in every copy of that image forever. Deleting it in a later layer does not remove it.
slide 07

Two ways to ship the same release

The slide shows two ways to ship the same release, and the lab offers both because laptops differ. The left panel uses uv's own commands: bump the version, build a wheel into dist, and install it into a separate environment that stands in for production. Rollback reinstalls the prior wheel, and the wheel's hash is in the release record. The right panel ships an image. The point to take from that panel is that a tag is a pointer, and the next docker build with the same tag moves it, so the image ID or the registry digest is the release. Both panels end on the same rule: a version number is only a name, so record the hash when you release and check it when you roll back.

The slide's wording in full
  • uv version --bump patch → pyproject says 0.1.1 / uv build → dist/myagent-0.1.1-py3-none-any.whl (and an sdist) / Install into a deploy environment that stands in for production: uv venv deploy-env, then uv pip install the wheel into it. / Rollback: reinstall the prior wheel file from the release record. The release record holds the wheel's SHA-256; the rollback checks it before it installs. / This path needs no daemon and no admin rights, so a standard student laptop can run it.
  • docker build -t myagent:0.1.1 . (or podman build) / The tag is a pointer. The image ID (or the registry digest) is the release. Record the ID in the release event, because a tag can be moved to a different image by the next build. / Rollback: stop the running container and start the prior image by ID or by a tag you have verified still points at that ID. / This path needs Docker or Podman. Some laptops cannot run either, so the lab does not require this path.
  • A version number is a label that a later build can reuse; the hash identifies the release. Record the hash when you release and check it when you roll back.
slide 08

Unattended runs: who attests a job nobody watched?

Section three of the chapter asks who attests an unattended run. The vendors in the teardown table ship the same five controls in some form, and you will see each control in the teardowns. The first is a stored trigger, which proves that somebody wrote the prompt earlier and proves nothing about whether this run's actions were approved. The second is an isolated environment with the network limited by default. The third is a narrow write path: one branch with a prefix, and no merge by the agent. The fourth is a human merge. The fifth is a record that someone reads, because a green status says only that the process exited; Anthropic's routines documentation states that last point in so many words. For your system the rule is this: if you schedule anything, the scheduled run writes to its own branch or its own file, a person accepts it, and the ledger shows both events.

The slide's wording in full
  • The prompt and schedule are written ahead of time by an authorized person. The firing shows only that the prompt was stored, and it gives no consent for this run's actions.
  • One branch with a known prefix (copilot/, claude/, codex/). No push to a protected branch; no merge by the agent.
  • A run log exists. A green status means only that the run exited. A person reads the transcript to decide whether the task succeeded.
  • Fresh VM or runner per run; network limited by default; secrets held outside the sandbox where the vendor supports it.
  • Nobody watched the run, so the run's record must answer three questions: what did it change, under whose authority, and who accepted it.
slide 09

Nygard's stability patterns, applied to an agent

Nygard's second edition of Release It!, 2018, is on the reading list, and the slide takes six cards from its stability chapters that map onto an agent loop. Timeouts go on every call, and Nygard advises against an immediate retry, because the fault is probably still there when the timeout fires. A Circuit Breaker guards a flaky provider, with the breaker's state visible in health. Steady State requires that every store that grows has a purge, and the idempotency store in the served agent is the example to check. Fail Fast is what you saw in the lifespan handler. The last two speak directly to automation. Force Multiplier is the antipattern: automation that spreads one bad decision everywhere, and a scheduled agent is that automation. Governor is the answer: resistance in the unsafe direction, so that a person can step in. The Governor is the confirmation gate you built in Evolution 3, applied to deployment.

The slide's wording in full
  • Every model call and tool call has one. Nygard: do not retry at once after a timeout; the fault is probably still there. Queue or halt.
  • After N failures from a provider or tool, stop calling it for a period and fail the run with a reason. Expose the breaker's state in /health.
  • Check the key, the model route, and the budget before the first turn, so that a run that cannot finish never starts.
  • Slow automation down in the unsafe direction so a human can intervene: deletes, deploys, mass writes need a pause and a person.
  • Automation that amplifies one wrong decision across the fleet. A background agent on a schedule is a force multiplier for whatever its prompt gets wrong.
  • The Governor is the pattern the course has been building since E3: a write needs a confirmation event, and an irreversible act needs a human.
slide 10

The Heavy lane and the release ceremony

Through the term you ran the Lite lane, gates one and two, the ADR and the tests. The Final System runs the Heavy lane, and the slide lists the three gates a release adds. Gate 3 is docs: the docs describe the release that exists, and the test is to paste every command from the runbook. Gate 4 is BDD: scenarios for the contract a caller relies on, and the scenarios run. Gate 5 is human: an attestation event in the ledger with one of three words, recorded by you. You have seen the reference design's incidents in which an agent recorded an attestation that nobody gave; for this reason the agent never records Gate 5. The last card separates two documents: the changelog is for maintainers, and the release notes are for the person who has to upgrade or roll back.

The slide's wording in full
  • The README, the runbook, and the release notes describe the release that exists. A command in the docs that fails when pasted is a gate failure.
  • Scenarios for the external contract: what a caller of /runs, or a user of the CLI, can rely on. Given, when, then, and each scenario runs as a test.
  • A person attests: Completed, Completed — Partial, or Dropped. The attestation is an event in the ledger. The agent never records it for you.
  • The changelog is every change, for maintainers. Release notes are what a user must know to upgrade and to roll back. Both state the version and the date.
  • Chapter 21.5: docs gate; BDD for external contracts; human attestation; release notes vs. changelog; the distribution invariant; MX mode. The reference design segment covers the last two.
slide 11

21cb6c3d…

The common mistake is rollback by rebuild, and I made it on purpose while I wrote the lab. I built version 0.1.0, released it, and recorded its hash. Then I set the version back and built again, which is what a rollback by rebuild does. The result was the same file name, the same version string, and different bytes; the first eight characters of the two hashes are on the slide. The rollback installed the new file, health reported 0.1.0, and only the hash showed that the running artifact differed from the released one. In my run the smoke test caught the difference because the code had changed; a subtle change would have passed the smoke test and left the hash as the only evidence. The fix is in the strip, and it is step four of the lab: keep released artifacts out of the build's reach, and make the rollback compare hashes.

The slide's wording in full
  • What happened. The version was set back to 0.1.0 and uv build ran again. The new wheel overwrote the old one at the same path. The rollback installed it, and the ledger recorded a rollback to 0.1.0 with a hash that did not match the release it claimed to restore. / Why it passes a careless check. The version string is right, the file name is right, and health reports 0.1.0. Only the hash shows that the running wheel differs from the released wheel.
  • Keep every released artifact where a build cannot overwrite it, and make the rollback refuse a hash that differs from the release event.

Teardown: background and cloud agents, September 2026

The table lists five systems, read for runtime and governance. Codex cloud runs a container per task, runs your setup script with network access, and then blocks the network in the agent phase by default. GitHub renamed Copilot's agent from coding agent to cloud agent on April first; it runs in an ephemeral Actions environment with a 59-minute cap, behind a firewall, and it can push only to its own branch. slide 15

Teardown: Copilot cloud agent, read for mechanism

The Copilot cloud agent teardown reads for the four headings every teardown uses: mechanism, design choice, cost, and failure mode. The mechanism is that a task arrives, the agent runs in an Actions environment you can prepare with a setup-steps workflow, and it pushes to one branch and opens a draft pull request. The design choice places the human gate in the pull request, where developers already work, and denies the agent every action that would close that gate itself: no ready-for-review, no approve, no merge, and no CI run until a person approves it. The cost is Actions minutes, AI credits, and review load. The failure modes are metagaming the gate, in other words a PR that satisfies the checks but not the task, and safeguard circumvention if the agent can edit the workflow that checks it. The strip states the attribution rule: the commits carry the assigner as co-author, which records who asked, and only the review records who checked.

The slide's wording in full
  • A task arrives from an issue, a panel, or a PR comment. The agent works in an ephemeral Actions environment prepared by .github/workflows/copilot-setup-steps.yml (the job must be called copilot-setup-steps, and the file must sit on the default branch). It pushes to one copilot/ branch and opens a draft PR.
  • Put the human gate where developers already look: the pull request. Only users with write access can start it. The agent cannot mark its PR ready, approve, or merge. Actions workflows on its PR do not run until a person clicks Approve and run workflows.
  • Actions minutes plus AI credits per session. A 59-minute ceiling per session. Review load moves to the humans: every task ends in a PR someone must read.
  • #9 Metagaming the gate: a PR that passes the repo's checks without doing the task. #1 if a workflow can be edited to skip a check. A reviewer who reads the diff, instead of the PR summary, defends against both.
  • Commits are authored by Copilot with the assigning developer as co-author, and signed. The attribution records who asked for the work. Only the PR review records who checked it.

Teardown: scheduled agents and the stored prompt

The scheduled-agent teardown starts from the routines documentation, which I quote on the left panel because it states the rule in plain words: the trigger attests only that the prompt was stored ahead of time, it is not consent for the actions of the run, text sent with a fire arrives wrapped as untrusted data, and a green status does not mean the task succeeded. Read those four lines against Appendix C. Hallucinated authorization (failure mode 7) occurs when the run acts as if the schedule were the approval. Fabrication by status (failure mode 3) occurs when the run reports green as done. A nightly schedule is Nygard's Force Multiplier, because it repeats one wrong prompt every night. The Governor for your system follows: a scheduled run writes only to its own branch or file, a person accepts it, and the ledger records the run and the acceptance as two separate events.

slide 21

Reference design: MX mode

The reference design's phrase for this Evolution is loose in the bay, hard at the door. In June an audit found seventy validate scopes behind one function with a hundred and sixty-two parameters, and a hundred and sixteen handoffs; the response was MX mode and the rule that amendments append. The phrase means that work can be fast and untidy where it is private, and that every gate holds where the work leaves. The arrangement it answers is the reverse one: strict rules on every keystroke inside, and a release door that opens for anything green. For your system the door is the deploy environment and the ceremony, so the rollback, the canary search, and the attestation run there every time.

From working to operated

  • Run the rollback before you vouch for the release, because until then the rollback is untested.

Serving an agent: a service or a job

  • Decide which one you are shipping before you choose a framework
  • Service (request/response)
  • Job (run to completion)
  • Choose, and write it down
  • A caller sends a request and waits. FastAPI fronts your loop.
    Each request has a time budget; the loop halts inside it
    A retried POST must not run twice: idempotency key
    Long answers stream
    /health reports status and version
  • A trigger starts a run; nobody waits on a socket.
    Budget is turns and dollars, not a request timeout
    Output is an artifact: branch, report, or ledger entry
    The result must say what it did

Containers, secrets, limits

  • Image, config, secret, limit, log: each has a wrong place and a check the Chase can run
  • Concern · Wrong place · Right place · The Chase's check
  • Image / artifact · Built from a dirty tree; tagged latest; rebuilt for rollback · Built from a clean commit; version and hash recorded at release · Hash in the release event equals the hash of what is running
  • Config · Constants in code; a limit stated in a Markdown file · Environment or one config file, read at startup and logged (values, not secrets) · Change the limit without a rebuild; /health or the log shows it
  • Secrets · ENV or COPY in a Dockerfile; .env committed; key echoed in a trace · Injected at run: docker run --env-file (untracked), OS keychain, CI secret store · grep the image history, logs, and git log for the canary: zero hits
  • Rate limits and budgets · The provider's limit is the only limit · Per-run turn and dollar budget; per-key requests per minute; a 429 with Retry-After · Exceed the budget on purpose; the run halts and the ledger says why
  • Logs and traces · Full prompts with user data; tool arguments that carry the key · Structured events; redaction before write; the key never enters the model's context · Search the trace store for the canary and for a real user field
  • FastAPI's container guidance: one process per container; exec form of CMD; --proxy-headers behind a TLS proxy (fastapi.tiangolo.com/deployment/docker).
  • A secret in any image layer is in every copy forever. Deleting it in a later layer does not remove it.

  • Circuit Breaker

    You have proven a release when you have rolled it back once.

    • Record the hash when you release, check it when you roll back, and keep secrets out of everything you ship. Sign the card, freeze the code, and book the ceremony.
