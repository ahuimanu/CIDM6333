Every framework is a theory of who owns the loopWhere control lives, framework by framework

A new framework has arrived every year since 2022. Each encodes a theory of where control lives: your code, the model, the vendor's harness, or a graph you draw. You choose that theory and defend it.

Workflows versus agents (Anthropic, Dec 2024)

A workflow runs the model along code paths you wrote. An agent lets the model direct its own control flow. Anthropic's advice: use a workflow wherever the path is known in advance, and the open loop only where it is not.

The statement Sortie 2 will try to disprove

The same task runs under two patterns with identical tool traces and the cost or quality delta ADR-1 predicted. If the predicted delta is absent from the evidence, the ADR recorded a rationalization.

The five workflow patterns and the agentAnthropic, 'Building Effective Agents': the catalog you refactor into

Prompt chaining

A fixed sequence. Each step's output is the next step's input, with an optional gate between steps.

When: Decomposable task; accuracy over latency

Routing

A classifier sorts each input and dispatches it to a specialized path.

When: Distinct input classes that deserve distinct prompts or models

Parallelization

Sectioning splits the task, runs the parts, and merges the results. Voting runs the same task N times and aggregates the answers.

When: Independent subtasks; confidence from multiple samples

Orchestrator–workers

A central model decomposes the task, delegates, and synthesizes.

When: Subtasks unknown in advance; large edits across files

Evaluator–optimizer

One model produces, another critiques, and the pair loops until the criteria are met.

When: Clear evaluation criteria; iteration measurably helps

The agent

The open loop: the model plans, acts on tools, observes, and continues until it is done or halted.

When: Open-ended problems; the path cannot be scripted; trust and budget in place

E1's loop refactored without touching the toolsThe trace must stay identical; only control moves

E1: the open loop

model(messages) → Step

answer? halt

tool? call → observe

repeat under BUDGET

Control: the model, bounded by code.

Trace: T1 tool A, T2 tool B, T3 answer.

As orchestrator–workers

orchestrator(messages) → [subtask₁, subtask₂]

worker(subtask₁) → calls tool A

worker(subtask₂) → calls tool B

synthesize → answer

Control: a planner plus bounded workers, each with its own budget.

Trace: same tools, same order, or the refactor changed behavior.

As evaluator–optimizer

producer(messages) → draft (tools A, B)

evaluator(draft, criteria) → PASS | revise

loop ≤ K rounds → answer

Control: a critic gates the halt; the halt condition is a criterion.

Trace: same tools, plus evaluator turns you can count.

Teardown: LangChain to LangGraph (2022 to 2024)Why chains became graphs with state

LangChain (late 2022)

LangChain wrapped the ReAct prompt in objects (chains, agents, tools, memory). The wrapper made the loop importable and also hid it, so practitioners paid the abstraction tax in opaque prompts and release-to-release drift.

LangGraph (2024)

LangGraph models the agent as a state graph. Nodes are steps, edges are control flow you draw, state is typed, checkpoints persist it, and a human interrupt is an edge. You own every edge.

Pydantic AI (2024–25): why typed outputs

Pydantic AI validates every model output against a Pydantic model before the output acts, and retries or rejects a malformed one.

Theory of control: the type system owns the model–code boundary. E1's Step schema in miniature.

Cost: what the schema cannot express, the model cannot do (E3).

CAMEL: two role-playing agents. MetaGPT: a software company as prompts, SOPs as coordination. AutoGen: conversation as coordination. CrewAI: roles, goals, backstories, a process.

Theory of control: conversation among personas; FIPA and BDI rediscovered (E8).

Cost: no evaluator; one role's summary becomes the next role's fact.

Patterns and Orchestration Frameworks

Evolution 2 gives the halting loop from Evolution 1 a name and a home. Every framework is a theory of who owns the loop, and the choice of a framework is the first decision you will defend with alternatives on the table. Four teardowns trace LangChain to LangGraph, Pydantic AI, the role-based frameworks of 2023, and the vendor SDKs of 2025. In the lab you refactor the loop into a pattern from the catalog and record the choice in ADR-1.

Every framework is a theory of who owns the loop

Framing. Learn what a framework assumes about control rather than its API. LangGraph assumes that you own every edge. The Claude Agent SDK assumes that the vendor owns the loop and that you supply tools and instructions. CrewAI assumes that control is a conversation among roles. Each assumption is a theory, and the framework churn of 2022 to 2025 is the field arguing about those theories. The distinction from Evolution 1 now sharpens. A workflow calls the model along code paths you wrote. An agent lets the model direct its own control flow. A workflow is predictable, cheap, and testable, so build one wherever the path is known. Sortie 2 tests one statement: the same task runs under two patterns with identical tool traces, and the cost or quality difference that ADR-1 predicted appears in the evidence. If the predicted difference does not appear, the ADR recorded a rationalization. [~8 min]

The five workflow patterns and the agent

The catalog lists five workflows and the agent. Prompt chaining runs a fixed sequence with optional gates between steps and trades latency for accuracy. Routing classifies the input and dispatches it to a specialized path. Parallelization takes two forms, sectioning and voting. In orchestrator-workers a central model decomposes the task and delegates the parts, and the tools of Evolution 3 and the subagents of Evolution 8 plug in here. In evaluator-optimizer a producer and a critic run in a loop, which is the evaluation gate of Evolution 10 in miniature. The agent is the open loop you built in Evolution 1. The catalog puts it last and recommends it least. The source advises you to start with the simplest pattern that works and to add complexity only when it measurably helps. That advice is the null hypothesis of your ADR. [~8 min]

E1's loop refactored without touching the tools

The worked example, in prose. Your E1 loop calls the model, reads a Step, either answers or calls a tool, and repeats under a budget. Control sits with the model, and code bounds it. The first refactor is orchestrator-workers. A planner splits the task, each bounded worker calls one tool, and a synthesis step produces the answer. Control is now split between the planner and the workers, and each worker has its own budget. The second refactor is evaluator-optimizer. A producer drafts, a critic checks the draft against criteria, and the loop runs at most K rounds. The halt is now a criterion rather than the model's say-so. The sortie requires one discipline: hold the tool layer constant. If the two runs do not call the same tools in the same order, the refactor changed behavior and the comparison measures nothing. With the tools held constant, the measured delta is attributable to the decision in your ADR and to nothing else. [~7 min]

When to keep it simple

The source's advice forms a ladder, and each rung becomes a row in your ADR. Start with one model call and measure it. That measurement is the baseline row. Add a workflow only when the task decomposes and the gain is measurable, and write the predicted delta before the run. Add an agent only when the path cannot be scripted and trust, budget, and evaluation exist, which is what E1 gave you. Add a framework only when it buys something a stdlib loop cannot, such as checkpoints, tracing, or typed handoffs. 'None' is a legitimate alternative, and it must appear in ADR-1. Every layer a framework adds between you and the model call is a layer you cannot see into during Drift (the abstraction tax). If you cannot explain what the framework did on turn three, you do not own the loop. [~5 min]

Teardown: LangChain to LangGraph (2022 to 2024)

The first teardown covers one company and two theories of control. LangChain, in late 2022, wrapped the ReAct prompt in objects (chains, agents, tools, memory). The wrapper made the loop importable and also hid it, so practitioners paid the abstraction tax in opaque prompts and release-to-release drift. LangGraph, in 2024, corrected this by modeling the agent as a state graph you draw, with typed state, checkpoints, and a human interrupt as an edge. You own every edge. The four rows of the table are where the two differ most.Planning went from hidden to explicit, memory from opaque objects to typed state, governance from none to an interrupt, and runtime from a script to persisted runs with tracing. In judgment-loop terms, the decision was to move control from the library into a graph that the user draws, and the cost is that you now have to draw it. [~5 min]

Teardowns: Pydantic AI and the role-based frameworks

Two more theories. Pydantic AI holds that the type system owns the boundary between model and code. The library validates every output before the output can act, tools are typed functions, and a malformed call never executes. Your E1 Step schema was this idea in miniature. The cost is that what the schema cannot express the model cannot do, and small local models fail the schema more often, which Evolution 3 shows. The role-based frameworks hold that control is a conversation. CAMEL runs two role players, MetaGPT runs a software company as prompts, AutoGen treats chat as coordination, and CrewAI runs crews with roles and a process. This is FIPA and BDI rediscovered with a language model in the reasoner slot, and Evolution 8 takes it up in full. The cost is AutoGPT's cost multiplied. No one in the conversation is an evaluator, so one role's polished summary becomes the next role's fact. [~5 min]

Teardown: vendor SDKs (2025), who owns the loop?

The vendor SDKs, read by their theory of control. OpenAI's Agents SDK composes agents with handoffs and guardrails, a runner loops, and tracing ships with the runner. The Claude Agent SDK ships the harness as a library: the vendor owns the loop, and you supply tools, instructions, and hooks. Google's ADK builds a hierarchy, with workflow agents for sequential, parallel, and loop control and A2A for peers. Each vendor has a governance story (guardrail tripwires, permission prompts and hooks, callbacks), and none of the three records what was attested. The feature rows are as of early 2026, and the rate at which they go stale is part of the teardown. [~5 min]

Reference design: ADR-0.0.2, 'popularity is not rationale'

The reference design's model ADR decides a command-line parser. The stakes are low, so the reasoning is easy to read, and for this reason it is a good model. The decision was argparse over click. Click was the more popular library, and the ADR rejected popularity as a reason. The reasons that counted were zero external dependencies for a kit whose job is governance, a smaller upgrade surface, and the stdlib-first posture that later became doctrine. Your ADR-1 takes the same shape: intent from the PRD, the decision in one sentence, at least three alternatives including none, consequences in both directions with the one you will measure, a scorecard, and a checklist of what the choice must support by Evolution 12. Write the ADR before the code. An ADR written after the code records a rationalization. [~5 min]

Three forcing functions and ten peer challenges

Stress a decision before you record it. The reference design's planning step supplies three forcing functions. In the pre-mortem, assume it is Evolution 12 and the choice has failed, then write the story. Whatever you wrote is a consequence. The second forcing function is 'what would have to be true': ask what would have to be true for the rejected alternative to have been right. If that is plausible, your decision needs a measurable consequence. Habit is not a constraint. The ten challenges, which you will put to a peer's ADR at the Chase station, are so what, scope, alternative, dependency, gold standard, timeline, evidence, consumer, regression, and parity (the list is chapter 11's). [~2 min]

Evaluation lens: strong Sortie 2, strong ADR-1

A weak submission chose its framework because a tutorial used it, lists alternatives as names, refactored the tools along with the pattern so that nothing is attributable, asserts 'better' without a measurement, and wrote the ADR afterward. A sound submission runs two patterns with identical traces in the ledger, predicts one consequence and measures it, lists three real alternatives including none, fills a scorecard whose winner is not the feature count, and commits the ADR before the refactor. An exceptional submission, and the one I want to see, records a prediction that did not appear and amends the ADR with the evidence. [~4 min]

Flight Card 2: two patterns, one trace

Flight Card 2 stays at the center of the envelope and is the first sortie with a dependency: Sortie 1 must have passed. The design claim is the same statement: the same task runs under two patterns with identical tool traces and the cost or quality delta that ADR-1 predicted. There are three test points: the task under pattern A with a measurement, the same task under pattern B with the tool sequence identical, and the comparison against the prediction in the ADR. The last falsifier on the card makes an ADR dated after the refactor commit a FAIL, because a prediction written after the refactor is not a prediction. [~3 min]
