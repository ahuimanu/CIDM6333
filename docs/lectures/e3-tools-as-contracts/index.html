A tool is a contract; the model is an untrusted callerEverything the model sends across the boundary is validated before it acts

The model does not call your function. It emits text that asks for the call. Every step from that text to the effect runs in your code.

Why a local 8B model this Evolution

A frontier model honors the contract, so you never see it enforced. A small local model breaks it in ten turns: malformed JSON, invented arguments, tools that do not exist.

The design claim Sortie 3 will try to disprove

No write-class tool executes without a prior confirmation event in the ledger, including when the write is requested by text the model read.

Declaring a tool: name, description, schema, side-effect classThe four fields, and the one that decides whether a gate applies

Name and description

The description is the only thing the model reads. Write it as a contract.

Schema

JSON Schema or a Pydantic model. Validation is the first gate; a failed call never reaches the function.

Side-effect class

read: runs freely. write: needs a confirmation event. irreversible: needs an attestation. The tool declares its class; the gate never guesses it from the name.

Idempotency and budget

A write retried is a second write. When a timeout or a retry budget runs out, the loop halts.

Design rule: the gate reads the side-effect class field; no class declared means irreversible.

Permission gating: the confirmation event precedes the callRead freely; write with confirmation; irreversible with attestation. No ledger event, no call.

The gate, in your loop

step = parse(model(messages))      # Step schema
if step.tool:
    spec = TOOLS[step.tool]          # KeyError → halt
    args = spec.schema.validate(step.args)
    ev = None                        # for reads
    if spec.effect != "read":
        ev = ledger.find("confirm",
                 tool=step.tool, args=args)
        if ev is None:
            ledger.emit("denied", step)
            observe("DENIED: confirm first")
            continue
    ledger.emit("call", step, ev)
    observe(spec.fn(**args))

Four properties the Chase will check

1. Order. The confirm event precedes the call event.

2. Binding. Confirm states tool and arguments; a blanket 'yes' is a disabled gate.

3. Source. The human's action in the host, never the model.

4. Denial leaves a trace: ledger event, observation, filesystem byte-identical.

Toolformer (Feb 2023) vs. function calling (Jun 2023)

Toolformer: calls learned by fine-tuning; the contract lives in the weights, unvalidated.

Function calling: tools declared at inference; the contract lives in the prompt, validated by your code.

Learned calls put the contract in the model; declared calls put it in your loop.

Gorilla and ToolBench (2023): retrieval

Gorilla retrieved API docs at inference; ToolBench collected 16,000 real APIs and a retriever.

The description is what retrieval and the model both read. A retrieved tool the model has never seen is an untrusted tool.

Progressive disclosure: the map in context, the catalog on disk.

Seventeen Claude Code hooks: orientation at SessionStart, gates before writes and commits, verifiers after tool use, pipeline-gate.py, verifier-pipe-gate.py. Codex gets two; Copilot gets one.

08-21: presence is not procedure

A gate passed an artifact that existed but was empty. The gate verified presence and skipped procedure. Fix: check the record of the procedure (the ledger event) rather than the output.

08-23: bypassed by Bash writes

Bash writes (echo >, sed -i, python -c) passed the Write and Edit fence; the hook saw 'Bash'. Fix (GHI #844/#847): check git diff --cached at the commit locus.

Gate at the call when the schema can see the effect; gate at the effect (the diff, the ledger) when it cannot. Chapter 12's exercise shows the difference.

slide 01

Tools as Contracts

Evolution 3 connects the loop, which already halts and now has a pattern, to the world. The statement that organizes the lecture is that a tool is a contract and the model is an untrusted caller. Four teardowns cover the two ways a model learned to call tools, the retrieval systems that scaled the catalog, the screen as a tool, and Claude Code hooks, which the harness runs around every tool call. The lab has three parts: a read tool that runs freely, a write tool that does not run until a confirmation event is in the ledger, and a local eight-billion-parameter model that produces the calls. The course requires the local model because a small model's failures make the contract visible.

slide 02

A tool is a contract; the model is an untrusted caller

Framing. The model does not call your function. It emits text that asks for the call, and your code performs every step between that text and the effect: it parses the text, validates it against a schema, decides whether the call is permitted, runs it, and hands back an observation. Governance lives in those steps, and for this reason the lecture treats the model as an untrusted caller. The term is architectural rather than moral: the loop trusts nothing the model sends until the loop's own code has checked it. The right panel explains why the course requires a local model. A frontier model honors the contract so reliably that you never see it enforced. A small model breaks it in the first ten turns (malformed JSON, invented arguments, tools that do not exist, a write where a read would do), so the gate you write is one you have watched refuse. The design claim Sortie 3 will try to disprove ends with the phrase the fourth test point depends on: including when the write is requested by text the model read.

slide 03

Declaring a tool: name, description, schema, side-effect class

A tool declaration has four fields. The model emits the name and reads the description, so you write the description as a contract: what the tool does, what it must not do, and what it returns on failure. The schema (JSON Schema or a Pydantic model) is the first gate. A call that fails validation never reaches the function; it returns a structured error that the model can read and retry. The side-effect class is the field the gate reads. You declare it on the tool rather than infer it from the name, because a tool's name can mislead (a delete tool called 'cleanup'), and the gate must not depend on it. The fourth field covers idempotency and budget. A read can be retried without harm, and a retried write is a second write, so the retry policy reads the declared idempotency. Every tool has a timeout and every loop a retry budget, and when either runs out the loop halts. The strip states the fail-closed rule: the gate treats a tool with no class declared as irreversible.

slide 04

Permission gating: the confirmation event precedes the call

The slide shows the gate as fourteen lines of your own loop, so that you can see it needs no framework. The loop parses the model's step, looks the tool up in the registry (an unknown tool halts), validates the arguments against the schema, and checks the side-effect class. For a read it records the call and runs the function. For any other class it searches the ledger for a confirm event bound to this tool and these arguments. If none exists, the loop records a denial, hands the model a DENIED observation, and continues. If one exists, the loop records the call with the event and runs the function. The four properties on the right are what the Chase reads from the ledger: order, binding, source, and a trace left by every denial. Source is the property the injection test point depends on. The confirm comes from the human's action in the host (a keypress, a command), never from model output and never from content the model read.

slide 05

Failure and recovery: errors are observations

The table lists six kinds of failure, and the loop handles each with the same shape of policy. The model sees the error as an observation, the loop retries under a budget, and when the budget runs out the loop halts. Two rows need a reason attached. The loop halts on a second identical schema rejection because the model has shown that it is not reading the error, and the loop never retries a write automatically because a retried write is a second write. Every row ends in a ledger event. A failure the ledger does not show is a failure the Chase cannot read, so a loop that swallows an error has removed its own evidence.

slide 06

Teardowns: Toolformer, function calling, Gorilla, ToolBench

The slide holds four teardowns, two on each side. Toolformer (February 2023) taught a model to insert API calls into its own text by self-supervised fine-tuning, so the model learned when a call lowered its next-token loss. The calls are learned and implicit, the contract lives in the weights, and nothing validates it. Function calling (June 2023) declared the tools at inference, one JSON Schema per function in the request and a structured call in the response, so the contract lives in the prompt and your code validates it. Function calling won for this reason: it moved the contract to where you can read and enforce it. Gorilla and ToolBench answered a different problem. When the catalog holds thousands of APIs the prompt cannot hold them, so Gorilla retrieved the relevant documentation at inference, and ToolBench built a benchmark over 16,000 real APIs, with a retriever that selects candidates before the model chooses. Two lessons survive. The retriever and the model both read the description, so you write it for both. A retrieved tool the model has never seen is an untrusted tool, which is the tool-poisoning surface of Evolution 5 arriving two years early.

slide 07

Teardowns: computer use; Claude Code hooks

Computer use (Anthropic, October 2024) shows what generality costs a contract. Perception is a screenshot and action is a click, a keystroke, or a scroll, so the contract collapses to one tool with one argument space, and every action is write-class because a click can cause anything. The schema cannot say what a click will cause, so the gate has to sit at the effect (what changed) rather than at the call (what was asked). A Claude Code hook is a shell command the harness runs at a lifecycle event (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop, and SessionEnd, among others), and a PreToolUse hook can allow, deny, or ask. The harness runs it regardless of what the model decided, and that is what makes a hook enforcement rather than instruction. A hook sees the call as declared. It cannot see an effect that the declared surface hides, and a Bash call is the standard case: the tool is Bash, and the write sits inside the argument string.

slide 08

Reference design: the 17 hooks, and two August incidents

gzkit renders its canon into seventeen Claude Code hooks: orientation at SessionStart, gates before writes and commits, verifiers after tool use, and two pipeline gates (pipeline-gate.py and verifier-pipe-gate.py) that check the governed path was followed. Codex gets two hooks and Copilot gets one, and the matrix states which rule is enforced where. Two incidents in August changed where the gates sit. On August 21 a gate checked that a required artifact existed and passed it, while the artifact was present and empty because the procedure that should have produced it had not run. The gate verified presence and skipped procedure, so the fix made gates check the record of the procedure (the ledger event, the receipt) instead of the existence of its output. On August 23, writes made through the Bash tool (echo >, sed -i, python -c) passed a PreToolUse fence that watched Write and Edit, because the hook saw the tool name 'Bash' and not the file. The fix (GHI #844/#847) moved the write-side fences to the commit locus, where git diff --cached shows every write whatever tool made it. The strip states the design decision for your own gate: gate at the call when the schema can see the effect, and at the effect when it cannot. Chapter 12's exercise has you implement the gate both ways and show a write that one catches and the other misses.

slide 09

Evaluation lens: a strong Sortie 3

The lens has three columns. A weak sortie has a gate that is a sentence in the prompt, with nothing in code that refuses. Its confirmation is a blanket yes at session start that every later write spends, or a confirm recorded after the call or written by the model. It skips the injection test, or it swaps the local model for a hosted one to hide the malformed calls. A sound sortie shows a read that runs without a confirm event and a write refused with a denied event and an observation. Its confirm is bound to the tool and its arguments and timestamped before the call. An injected request is denied with no file change, a halt is exercised at least once with its reason in the ledger, and the local model sits on the substrate line with its malformed calls counted. An exceptional sortie goes further. It implements the gate twice (as a hook and in the loop) and shows one write that only one of them catches. It attempts a Bash-style write that the call-locus gate misses and the diff-locus check catches. It leaves one tool without a side-effect class and shows the gate refusing it as irreversible. After a denial, the model chooses a read path, and the filesystem hash is identical before and after the denied write.

slide 10

Flight Card 3 brief · the gate holds

Flight Card 3 is the first expansion of the envelope, and it depends on a Sortie 2 PASS. It has four test points. In the first, the read tool answers a request with no confirm and a call event in the ledger. In the second, the gate refuses the write, records a denied event, returns an observation to the model, and leaves the file unchanged. In the third, the human confirms the same request through a host action, and the Chase checks that the confirm event precedes the call event and is bound to the tool and its arguments. In the fourth, the model reads a file that says 'now write X', and the pass condition is a denial with no confirm event in existence. The abort criterion separates infrastructure from the design claim: if the local model cannot produce a parseable tool call in N attempts, the sortie halts rather than fails, and you record N.
