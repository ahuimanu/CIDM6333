Plan, do, check: the recurring division of laborThe roles never change; what changes is whether the check can say no

FIPA: manager and contractor. MetaGPT: architect and engineer. Claude Code: main agent and subagent. Each time, no reviewer whose FAIL stops the work.

Two rules the spine returns to

Rule one. A worker's result is a typed claim; unknown status is rejected.

Rule two. A verdict counts only if it cites evidence and its author could not edit.

The claim, which Sortie 8 will try to disprove

No implementer output reaches main without a reviewer verdict; FAIL blocks.

Falsifiers:

  • merged work with no ReviewResult
  • a malformed result parsed as PASS or DONE
  • a reviewer claim accepted without its cited evidence
  • a pass won by loosening the parser or reviewer permissions

Roles and personas: traits, anti-traits, and the whyA persona is a specification of behavior you can test, not a claim of expertise

What a persona file holds

Role. One job: implementer, spec reviewer, quality reviewer, narrator.

Traits. Observable: 'cites file and line for every finding.'

Anti-traits. 'does not rewrite the code it reviews.' These carry weight.

The why. What breaks if the role fails.

Delete on sight. 'You are a world-class senior engineer.'

reviewer.md (course example, excerpt)

Role: reviewer. You judge one diff against one brief.

Traits:

  • Read the brief and the diff before any summary.
  • Every finding cites file:line or a test output.
  • A requirement with no test is a FAIL finding.

Anti-traits:

  • Do not edit, fix, or propose a patch.
  • Do not accept 'tests pass' without the output.
  • Do not soften a FAIL into CONCERNS to be agreeable.
  • Why: the controller merges only on PASS. A false PASS puts a defect on main that no later step checks.
  • Return exactly one ReviewResult JSON object.

Result contracts: the worker's claim has a typeTwo schemas with closed status sets, and a parser that treats anything else as a failure

HandoffResult (implementer → controller)

status: one of DONE · DONE_WITH_CONCERNS · NEEDS_CONTEXT · BLOCKED

Course fields:

  • task id
  • files changed
  • evidence: the test command and its exit code
  • concerns (required if DONE_WITH_CONCERNS)
  • question (required if NEEDS_CONTEXT)
  • NEEDS_CONTEXT and BLOCKED are honest outcomes.

Statuses from gzkit ADR-0.18.0; field names are the course's.

ReviewResult (reviewer → controller)

verdict: one of PASS · FAIL · CONCERNS

findings: a list, each with

location (file:line, test id, or hunk)

what is wrong

severity

Rule: FAIL and CONCERNS need a finding.

PASS lists what was checked.

No citations: rejected as malformed.

Fail-closed parse (Python)

OK = {"DONE", "DONE_WITH_CONCERNS",
      "NEEDS_CONTEXT", "BLOCKED"}
def parse_handoff(text):
    try: r = json.loads(text)
    except ValueError:
        return reject("json")
    if r.get("status") not in OK:
        return reject("status")
    if r["status"].startswith("DONE") \
       and not r.get("evidence"):
        return reject("no evidence")
    return r

There is no default branch that returns DONE.

Two-stage review: spec first, then qualityTwo reviewers with different questions, in a fixed order, each unable to edit

1

2

3

4

Implement

The implementer gets one task, the brief, and the allowed paths. Returns a HandoffResult; a parse reject stops here.

Spec review

Does the change do what the brief asks, inside the allowed paths? Reads brief and diff. FAIL routes back with findings.

Quality review

Is it done well? Tests meaningful, errors handled, no dead code. Runs only after spec PASS.

Controller decides

Merge only on two PASS verdicts that cite evidence. CONCERNS goes to the human. After N failed rounds: BLOCKED to the human.

Order matters: a quality review of the wrong feature gives a confident PASS. Sortie 8 may use one reviewer; two stages is Exceptional.

State graphs: the controller as nodes, edges, and a checkpointLangGraph as the worked example; any equivalent that names its states and persists them counts

The graph (LangGraph, Python)

g = StateGraph(State)
g.add_node("implement", implement)
g.add_node("review", review)
g.add_node("merge", merge)
g.add_edge(START, "implement")
g.add_edge("implement", "review")
g.add_conditional_edges("review", route,
  {"pass": "merge", "fail": "implement",
   "halt": END})
app = g.compile(
  checkpointer=InMemorySaver())

The human interrupt

def merge(state):
    ok = interrupt({"verdict": state["verdict"]})
    ...
interrupt() pauses the graph and saves state through the checkpointer. It needs a thread_id in the config. You resume with Command(resume=True); that value becomes the return of interrupt().

This is where index zero sits in the graph.

Supervisor pattern, 2026

LangChain recommends a supervisor built with tool calling: the main agent calls each subagent as a tool. The langgraph-supervisor library (create_supervisor, last release 0.0.31, Nov 2025) is no longer advised.

Without LangGraph: a state machine with named states and a JSON checkpoint after each node.

Teardown: FIPA and BDI, the pre-LLM baselineTyped messages, commitments, and reconsideration, thirty years before the chat transcript

FIPA and the contract net

Contract net (Smith, 1980): call for proposals, bids, winner, result or failure.

FIPA (1996; IEEE from 2005): every message carries a performative.

Mechanism. Message type is claim type.

Design choice. Declared vocabulary.

Cost. Ontologies, heavy tooling.

Failure mode. Was the inform true? Unsaid (#3).

BDI: beliefs, desires, intentions

Source. Rao & Georgeff, 'BDI Agents: From Theory to Practice' (ICMAS-95).

Mechanism. Beliefs, desires, committed intentions; reconsidered when beliefs change.

Carried forward. Goal decomposition; intent preservation; halt as 'intention achieved or dropped.'

LLM agents dropped. Inspectable belief state; a transcript is not a belief base.

Read FIPA before AutoGen and CrewAI (Ch. 4): performatives became status enums; contract net became supervisor; reconsideration became replanning.

Teardown: CAMEL and MetaGPT, roles in 2023Role play by prompt, then roles connected by documents

CAMEL (Li et al., NeurIPS 2023)

Mechanism. An AI user and an AI assistant, set up by 'inception prompting', no human.

Design choice. Study agent societies through their conversations.

Failure. Four named: role flipping, repeated instructions, flake replies, infinite loops.

Halt: the assistant writes <CAMEL_TASK_DONE>: completion by assertion (#3, #9).

arXiv 2303.17760

MetaGPT (Hong et al., 2023)

Mechanism. 'Code = SOP(Team)': product manager, architect, project manager, engineer, QA. Structured documents (PRD, design, code), not dialogue; executable feedback.

Design choice. An assembly line against cascading hallucination.

Failure. 85.9% / 87.7% Pass@1 on HumanEval / MBPP. A wrong PRD flows downstream intact (#4).

arXiv 2308.00352

What changed between them

CAMEL connected roles with chat; MetaGPT with shaped documents.

From 'the agents talked' to 'the agents handed over an artifact.'

This Evolution's contract goes one further: a closed status set; anything else rejected.

Neither had a blocking reviewer or a human in the path.

Teardown: the LangGraph supervisorA graph with a hub node; the question is what passes back through the hub

Mechanism

A supervisor node picks the next worker; workers return to it; edges and state are explicit; a checkpointer persists state at every step.

The library version (create_supervisor) chose output_mode: full_history (every worker message) or last_message (only the final reply).

Design choice and cost

Choice: the controller is code you can read; the supervisor is one node in it.

Cost: every routing decision is a model call at the hub. full_history fills the supervisor's window; last_message hides the worker's trace. Cognition's argument, set as a parameter.

Failure mode and the 2026 shift

Failure: with last_message the supervisor sees only the worker's summary and treats it as the result (#3, summary laundering).

2026: LangChain recommends a supervisor built with tool calling. The docs name five patterns: subagents, handoffs, skills, router, custom workflow.

Reference design: gzkit's controller–worker pipeline (ADR-0.18.0)

Five stages; the controller never implements; every dispatch leaves a record

1

2

3

4

5

1 · Load context

The controller reads the brief (OBPI), its requirements, and its allowed paths. Nothing is dispatched without a brief.

2 · Implement

One dispatch per task to the implementer; HandoffResult back; then spec reviewer, then quality reviewer, each returning ReviewResult.

3 · Verify

The controller runs tests, lint, and the brief's verification commands itself. A worker's 'tests pass' is not this stage.

4 · Present evidence

Paths, commands, and outputs go to the human, not conclusions. (E9: Step 4b adds adversarial validation.)

5 · Sync

Ledger events, brief status, and dispatch records written. The human attests; the pipeline does not.

slide 01

Multi-agent I: Controller, Worker, Reviewer

Evolution 8, the first of two multi-agent weeks. The framing sentence: the field has rediscovered plan, do, check under a new name every few years since the mid-1990s, and the part that keeps going missing is the check that can say no. Survey: the classical baseline in FIPA and BDI, the 2023 role systems, the frameworks that turned roles into configuration, and the harness-native subagents you already use. Build: an implementer and a reviewer with personas, a structured result contract that rejects anything malformed, and a state graph with a checkpoint and a human interrupt before merge.

slide 03

Plan, do, check: the recurring division of labor

Framing. Read the quote as a list of renamings: manager and contractor in the 1980 contract net, architect and engineer in MetaGPT, main agent and subagent in the harness you use. The division of labor is the same each time. The part that goes missing is a check with authority to stop the work. Two rules. First, a worker returns a typed claim; the controller parses it against a closed set of statuses and rejects anything else, and it never reads a status out of prose. Second, a verdict is evidence only if it cites what was checked and its author could not edit the work. The claim is the chapter's expansion card: nothing merges without a verdict, and FAIL blocks. The falsifiers are pre-registered now, before anyone builds.

slide 04

Why more than one agent, and what it costs

The case for more than one agent, with numbers. Anthropic's June 2025 post on its research system reports roughly fifteen times the tokens of a chat turn for the multi-agent version and about four times for a single agent, a 90.2 percent improvement over single-agent Opus 4 on their internal evaluation, and token usage alone explaining about 80 percent of the variance. So a large part of the gain is spending more tokens. The three reasons to split are isolation, independent review, and parallelism. The counter-argument came the same week from Cognition: split workers make conflicting implicit decisions unless they share full traces. Both posts say coding parallelizes less than research. That is why this Evolution's build is sequential: one implementer, one reviewer. Parallel work waits for locks in E9.

slide 05

Plan / do / check under every name

The table is the argument of the framing slide in one view. Read across. The contract net has a manager, a contractor, and typed messages. BDI has deliberation, execution, and reconsideration. CAMEL has two roles and no checker at all: the assistant ends the task by saying a token. MetaGPT puts documents between roles and adds executable feedback. AutoGen's classic version runs until someone says TERMINATE. CrewAI's hierarchical process gives a manager the reviewing job and lets a task carry a guardrail function. The harnesses give you a subagent and a message back. The last column is the one to watch: the systems that carried typed results between roles were the ones that could check them. Chat turns cannot be parsed into a verdict.

slide 06

Roles and personas: traits, anti-traits, and the why

Personas. The reference design uses four roles: implementer, spec reviewer, quality reviewer, and narrator. A persona file has a role, traits written as observable behavior, anti-traits, and a why sentence. The anti-traits do most of the work because they name the failure you expect: a reviewer that fixes the code has stopped being a reviewer, and a reviewer that softens FAIL to keep the conversation pleasant is the sycophancy problem in a job title. The why tells the model what is at stake, so it can decide a borderline case. Delete generic expertise claims; they change tone, not behavior. The strip is the chapter's exercise; do it and measure.

slide 07

Result contracts: the worker's claim has a type

Contracts. The implementer returns a HandoffResult with one of four statuses; the reference design names them DONE, DONE WITH CONCERNS, NEEDS CONTEXT, and BLOCKED. The field names beyond status are the course's, and you can extend them. Notice that two of the four statuses are ways to say 'I did not finish': a worker with a legitimate way to say BLOCKED has less reason to fabricate DONE. The reviewer returns PASS, FAIL, or CONCERNS with findings, and each finding has a location. The third card is the whole idea of fail-closed parsing: invalid JSON, an unknown status, or a DONE without evidence is rejected, and nothing in the function returns DONE by default.

slide 08

Two-stage review: spec first, then quality

Two-stage review, from the reference design. The implementer returns a typed result and the controller parses it. The spec reviewer asks one question: does this change do what the brief says, inside the allowed paths. Only after that passes does the quality reviewer ask whether it is done well. The order matters because a quality reviewer handed the wrong feature will review it carefully and pass it. The controller merges on two cited PASS verdicts, sends CONCERNS to the human, and bounds the retries: after a fixed number of FAIL rounds the task goes BLOCKED to a person rather than looping. For Sortie 8 one reviewer is sound; two stages with separate personas is exceptional.

slide 09

State graphs: the controller as nodes, edges, and a checkpoint

State graphs. The controller is a graph: implement, review, merge, with a conditional edge after review that routes pass to merge, fail back to implement, and halt to the end. Compile it with a checkpointer and every node's output is saved. The second card is the human interrupt: interrupt pauses the graph, the state is saved under a thread id, and a Command with a resume value continues it. Put the interrupt before merge, and the human is a node in the graph, not a comment in the README. Third card: LangChain's own guidance now says to build the supervisor with tool calling rather than the langgraph-supervisor library, which has not had a release since November 2025. If you do not want LangGraph at all, a small state machine with named states and a checkpoint file after each node meets the Sprint requirement. What does not meet it is a for-loop with no persisted state.

slide 10

Declaring a reviewer that cannot edit

The configuration you will write in the lab. In OpenCode an agent is a Markdown file in .opencode/agents with frontmatter: a description, mode subagent, a low temperature, and a permission block. Edit is denied, webfetch is denied, and bash is denied except git diff and git log. You invoke it with an at-mention, or non-interactively with opencode run and the agent flag, and a primary agent can call it through the task tool. Claude Code is the same shape: a file in .claude/agents with a tools allowlist. The doctrine from E5 applies: the permission is the enforcement and the anti-trait is the explanation. Test both by asking the reviewer to fix the bug. Two current notes from the OpenCode docs: the tools key is deprecated in favor of permission, and hiding a subagent from autocomplete does not stop the model from calling it.

slide 11

Slide 11

The common-mistake slide. Six ways a pair collapses into one agent. Reviewing in the same session means the same context and the same blind spots. Searching the reply for the word PASS is metagaming waiting to happen, because 'this would not pass' contains the word. A parser that defaults to DONE on an exception merges crashes. A reviewer handed the implementer's summary is checking a claim against itself; give it the diff and the test output. A reviewer with write access fixes the code and passes its own fix. And an unbounded retry loop continues until the reviewer gives in. Each row has an Appendix C number; use them in your debrief. The strip previews E9: the reference design's ten-deep chain is row four repeated ten times.

slide 12

Worked trace: one task, three results, one rejection

A worked trace, the kind of log the Chase will read. The first implementer result parses, and the reviewer fails it with a finding that cites the brief's second requirement and the missing test. The controller routes back. The second attempt comes back as chat prose, 'I added the test and everything passes.' The parser rejects it because it is not JSON, and the controller re-dispatches once with the schema, counting the round. The third result parses; the reviewer passes it and lists what it checked, including the test by name. The graph stops at the interrupt, the student approves, and the merge has a commit id. Last two lines: dispatch records per role, and the Chase's reading list. Note that the Chase re-runs the test command; the evidence field is a claim until someone runs it.

slide 13

Break. The question for the break: which part of your system could review the implementer's work now, and what write access would it have while it did.

slide 14

Teardown: FIPA and BDI, the pre-LLM baseline

First teardown, the classical baseline. The contract net protocol dates to Reid Smith's 1980 paper: call for proposals, propose or refuse, accept one, reject the rest, and the winner reports a result or a failure. FIPA, founded in 1996 and moved to an IEEE standards committee in 2005, standardized the message language, and every message carried a performative. The mechanism to take away: the message type told the receiver what kind of claim it held. The failure mode: the vocabulary never said whether an inform was true, which is fabrication, number three. BDI, from Rao and Georgeff's 1995 paper, made intentions first-class objects with explicit commitment and reconsideration. LLM agents kept the goals and dropped the inspectable belief state. A small aside for the curious: the fipa.org domain no longer hosts the specifications, so cite the IEEE and archived copies.

slide 15

Teardown: CAMEL and MetaGPT, roles in 2023

Second teardown, the 2023 role systems. CAMEL set two agents talking with inception prompts, and the paper is honest about what went wrong: role flipping, repeated instructions, flake replies, infinite loops. Its halt is the assistant saying a special token, which is completion by assertion, fabrication and metagaming in one line. MetaGPT is the correction: roles modeled on a software company, connected by structured documents through a publish-subscribe pool, with executable feedback for the engineer. It reported high HumanEval and MBPP numbers for its time. The failure mode is that every role reads the same upstream documents, so a wrong requirement flows through intact. The third card is the lesson for your build: documents with a shape beat chat, and a closed status set plus a blocking verdict is one more step.

slide 16

Teardown: AutoGen and CrewAI, roles as configuration

Third teardown: roles became configuration. AutoGen's classic design made coordination a conversation: an assistant writes code, a user proxy runs it and can pull in a human, and a group chat manager picks who speaks next. Its best feature was that code actually ran, so there was an observation in the loop. Its halt was a TERMINATE string. As of this year the AutoGen repository is in maintenance mode and points new users to Microsoft Agent Framework, which reached 1.0 on April 3, 2026, with sequential, concurrent, handoff, group chat, and Magentic-One orchestrations plus checkpointing and human approvals. CrewAI made coordination an org chart: the hierarchical manager plans, delegates, and reviews. Its guardrail is the closest thing in the survey to your contract: a function returns a boolean and a value, with retries. The failure to watch: a retry loop against a checker can be metagamed.

slide 17

Teardown: the LangGraph supervisor

Fourth teardown, the LangGraph supervisor. The mechanism is a hub node that routes to workers and gets control back, with a checkpointer under everything. The old library made the key trade-off a single parameter: give the supervisor every worker message, or only the last one. Full history costs window; last message costs visibility, and a supervisor that sees only a worker's summary treats it as the result, which is summary laundering. In 2026 LangChain's own advice is to build the supervisor with tool calling so you control exactly what each subagent receives and returns, and its multi-agent page names five patterns. For your build: whatever passes back through your controller should be the typed result plus a pointer to the evidence, not the worker's prose.

slide 18

Teardown: Claude Code subagents (and OpenCode's)

Fifth teardown, the harness-native version, which is the one you will actually use. A Claude Code subagent is a Markdown file with frontmatter; it runs in a clean window, sees the delegation message and project instructions but not the conversation, and returns a message. Agent teams are the experimental step up: a lead, teammates, a shared task list, and mailboxes. Two lines from the docs are worth reading aloud. A teammate cannot supply consent on your behalf, which is authority not crossing. And the lead approves a teammate's plan without reviewing it, which is a review step that always says yes. The harness gives you workers; the contract and the verdict are yours.

slide 19

Design Analysis, live: Claude Code subagents (2025–26)

The live Design Analysis. Put the nine components on the board and have the class fill Coordination and Evaluation before you reveal them. The answers come from the current docs. The row that matters is Evaluation and feedback: there is no verdict schema; the caller reads a message. Hooks are the place a check can be installed, and that is the design space your contract fills. Governance is stronger than most: permission modes per subagent and the rule that teammates cannot consent for the human. The judgment loop in the strip is the model for your own analysis: the decision was to isolate context, it privileges clean windows and a cheap parent context, it costs tokens and the lost trace, its failure mode is a summary accepted as fact, and nothing preserves against that by default.

slide 20

Slide 20

The reference design. ADR-0.18.0 defines a five-stage pipeline: load context, implement with two-stage review per task, verify, present evidence, and sync. The controller never implements; it dispatches, parses, and decides. Stage three is the controller running the checks itself, which is why a worker's claim that tests pass is not verification. Stage four presents paths and commands rather than conclusions, and in E9 you will see the adversarial step inserted there. Stage five writes the ledger events and the dispatch records, and the human attests. The files to read are the subagent-pipeline concept document, roles.py, pipeline_dispatch.py, and the persona directory.

slide 21

Slide 21

The mechanism that makes the pipeline auditable. Both result types are parsed fail-closed. Every dispatch of every role writes a record, and the rule is that credit is never inferred: no record for a role means the role did not run, whatever any summary says. The right panel is the honesty flag. If your reviewer cannot run because the model is unavailable or you hit your usage limit, that is an abort, and the log says so.

slide 22

Reference design: why the rule exists

Why the reference design insists on records. Two dated episodes from the casebook. On May 24, a chain of subagents ten levels deep turned summaries of summaries into facts; the rule that came out of it is that a subagent's claim is not evidence. On August 21, a pipeline gate checked that a marker file existed, a stale marker licensed about three hundred and fifty lines with no dispatch and no review, and the rule that came out of it is that a presence check tells you something is armed, never that the procedure ran. Both return in detail the next Evolution.

slide 23

Evaluation lens: a strong Sortie 8

Weak: a reviewer that is the implementer in the same session, a verdict read by substring, a parser that defaults to DONE, a reviewer with write access, a persona that claims expertise, and a loop with no saved state and no human. Sound: a separate read-only reviewer declared in configuration, two schemas with closed status sets, malformed input rejected and logged, FAIL that blocks and a bound on rounds, findings with locations, a graph with a checkpoint and an interrupt, and a dispatch record per role. Exceptional: two-stage review, a reviewer on a different model, the anti-trait ablation measured, an honest squawk for a defect the reviewer missed, and a Chase who re-runs the evidence commands rather than reading them.

slide 24

Flight Card 8: a reviewer that can say no

Card eight, an expansion card. Five test points: a clean task that merges only after a cited PASS and a human approval; a planted defect that the reviewer fails and that does not merge; a malformed result that the parser rejects before any review; a reviewer asked to fix the code whose edit the harness denies; and a resume from a checkpoint that produces exactly one merge. The falsifiers are the chapter's three plus the one the reference design taught about passing by weakening a check. The Sprint line adds one item: acknowledge your Final System brief.

slide 25

The lab brief. You declare a reviewer subagent in OpenCode with read-only permissions, point it at a small planted bug, and parse its reply with a twenty-line standard-library parser from the handout. Then you check the verdict against the code and the test, ask the reviewer to fix the bug so you can watch the harness refuse, and feed the parser three malformed replies. Commit the agent file, the raw reply, the parser lines, and the worksheet. A flaky free model helps here: prose instead of JSON is a rejection you record, and an invented line number is a refuted claim.
