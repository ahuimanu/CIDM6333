Plan, do, check: the recurring division of laborEach system has the same roles; the check that can stop the work is the part that goes missing

FIPA called the roles manager and contractor, MetaGPT architect and engineer, and Claude Code main agent and subagent. None of the three gives a reviewer the authority to stop the work with a FAIL.

Two rules the spine returns to

Rule one. A worker's result is a typed claim, and the controller rejects an unknown status.

Rule two. A verdict counts only if it cites evidence and its author could not edit the work it judged.

The design claim, which Sortie 8 will try to disprove

No implementer output reaches main without a reviewer verdict, and a FAIL blocks the merge.

Falsifiers:

  • merged work with no ReviewResult
  • a malformed result parsed as PASS or DONE
  • a reviewer claim accepted without its cited evidence
  • a pass won by loosening the parser or reviewer permissions

Why more than one agent, and what it costsThree reasons to split the work; one measured price; one published counter-argument

~15×

90.2%

80%

of performance variance on BrowseComp explained by token usage alone

Three reasons to split:

  • Context isolation. A worker returns a result and keeps its trace in its own window.
  • Independent review. The reviewer did not write the code.
  • Parallelism. Independent subtasks run at once.

The counter-argument:

Yan (Cognition, Jun 2025) argues that workers must share full traces, because actions carry implicit decisions.

This Evolution's build runs one implementer and one reviewer in sequence. Parallel workers wait for E9, with locks.

Roles and personas: traits, anti-traits, and the whyA persona is a specification of behavior that you can test

What a persona file holds

Role. One job: implementer, spec reviewer, quality reviewer, narrator.

Traits. Observable behaviors, such as 'cites file and line for every finding.'

Anti-traits. 'does not rewrite the code it reviews.' These carry the most weight, because each states a failure you expect.

The why. One sentence on what breaks if the role fails.

Delete on sight. 'You are a world-class senior engineer.' A sentence like this changes the tone of the reply and leaves its behavior unchanged.

reviewer.md (course example, excerpt)

Role: reviewer. You judge one diff against one brief.

Traits:

  • Read the brief and the diff before any summary.
  • Every finding cites file:line or a test output.
  • A requirement with no test is a FAIL finding.

Anti-traits:

  • Do not edit, fix, or propose a patch.
  • Do not accept 'tests pass' without the output.
  • Do not soften a FAIL into CONCERNS to be agreeable.
  • Why: the controller merges only on PASS. A false PASS puts a defect on main that no later step checks.
  • Return exactly one ReviewResult JSON object.

Chapter 17 exercise: remove your reviewer's anti-traits and count how its verdicts change. That count earns an Exceptional mark in this Evolution.

Result contracts: the worker's claim has a typeTwo schemas with closed status sets, and a parser that treats anything else as a failure

HandoffResult (implementer → controller)

status: one of DONE · DONE_WITH_CONCERNS · NEEDS_CONTEXT · BLOCKED

Course fields:

  • task id
  • files changed
  • evidence: the test command and its exit code
  • concerns (required if DONE_WITH_CONCERNS)
  • question (required if NEEDS_CONTEXT)
  • NEEDS_CONTEXT and BLOCKED are honest outcomes, so a worker has less reason to invent DONE.

Statuses from gzkit ADR-0.18.0; field names are the course's.

ReviewResult (reviewer → controller)

verdict: one of PASS · FAIL · CONCERNS

findings: a list, each with

location (file:line, test id, or hunk)

what is wrong

severity

Rule: FAIL and CONCERNS need a finding.

PASS lists what was checked.

The parser rejects a verdict with no citations as malformed.

Fail-closed parse (Python)

OK = {"DONE", "DONE_WITH_CONCERNS",
      "NEEDS_CONTEXT", "BLOCKED"}
def parse_handoff(text):
    try: r = json.loads(text)
    except ValueError:
        return reject("json")
    if r.get("status") not in OK:
        return reject("status")
    if r["status"].startswith("DONE") \
       and not r.get("evidence"):
        return reject("no evidence")
    return r

There is no default branch that returns DONE.

Two-stage review: spec first, then qualityTwo reviewers with different questions, in a fixed order, each unable to edit

1

2

3

4

Implement

The implementer gets one task, the brief, and the allowed paths. It returns a HandoffResult, and a parse reject stops the run here.

Spec review

Does the change do what the brief asks, inside the allowed paths? The spec reviewer reads the brief and the diff. A FAIL routes back to the implementer with findings.

Quality review

Is it done well? The quality reviewer checks that the tests are meaningful, the errors are handled, and no dead code remains. It runs only after a spec PASS.

Controller decides

The controller merges only on two PASS verdicts that cite evidence. CONCERNS goes to the human. After N failed rounds the task goes BLOCKED to the human.

The order matters, because a quality review of the wrong feature gives a confident PASS. Sortie 8 may use one reviewer, and two stages earns Exceptional.

State graphs: the controller as nodes, edges, and a checkpointLangGraph as the worked example; any equivalent that declares its states and persists them counts

The graph (LangGraph, Python)

g = StateGraph(State)
g.add_node("implement", implement)
g.add_node("review", review)
g.add_node("merge", merge)
g.add_edge(START, "implement")
g.add_edge("implement", "review")
g.add_conditional_edges("review", route,
  {"pass": "merge", "fail": "implement",
   "halt": END})
app = g.compile(
  checkpointer=InMemorySaver())

The human interrupt

def merge(state):
    ok = interrupt({"verdict": state["verdict"]})
    ...
interrupt() pauses the graph and saves state through the checkpointer. It needs a thread_id in the config. You resume with Command(resume=True); that value becomes the return of interrupt().

The interrupt is where index zero sits in the graph.

Supervisor pattern, 2026

LangChain recommends a supervisor built with tool calling: the main agent calls each subagent as a tool. The langgraph-supervisor library (create_supervisor, last release 0.0.31, Nov 2025) is no longer advised.

Without LangGraph: a state machine with declared states and a JSON checkpoint after each node.

Teardown: FIPA and BDI, the pre-LLM baselineTyped messages, commitments, and reconsideration, thirty years before the chat transcript

FIPA and the contract net

Contract net (Smith, 1980): call for proposals, bids, winner, result or failure.

FIPA (1996; IEEE from 2005): every message carries a performative.

Mechanism. The message type is the claim's type.

Design choice. Interoperability through a declared vocabulary.

Cost. Ontologies and heavy tooling.

Failure mode. Nothing in the vocabulary said whether an inform was true (#3).

BDI: beliefs, desires, intentions

Source. Rao & Georgeff, 'BDI Agents: From Theory to Practice' (ICMAS-95).

Mechanism. Beliefs, desires, and committed intentions, which the agent reconsiders when its beliefs change.

Carried forward. Goal decomposition; intent preservation; halt as 'intention achieved or dropped.'

LLM agents dropped. An inspectable belief state, which a chat transcript does not supply.

Read FIPA before AutoGen and CrewAI (Ch. 4): performatives became status enums; contract net became supervisor; reconsideration became replanning.

Teardown: CAMEL and MetaGPT, roles in 2023Role play by prompt, then roles connected by documents

CAMEL (Li et al., NeurIPS 2023)

Mechanism. An AI user and an AI assistant, set up by 'inception prompting', with no human in the loop.

Design choice. Study agent societies through their conversations.

Failure. The paper lists four: role flipping, repeated instructions, flake replies, infinite loops.

Halt: the assistant writes <CAMEL_TASK_DONE>: completion by assertion (#3, #9).

arXiv 2303.17760

MetaGPT (Hong et al., 2023)

Mechanism. 'Code = SOP(Team)': product manager, architect, project manager, engineer, QA. Roles exchange structured documents (PRD, design, code) rather than dialogue, and the engineer gets executable feedback.

Design choice. An assembly line against cascading hallucination.

Failure. 85.9% / 87.7% Pass@1 on HumanEval / MBPP. A wrong PRD flows downstream intact (#4).

arXiv 2308.00352

What changed between them

CAMEL connected roles with chat, and MetaGPT connected them with documents that have a shape.

That is the step from 'the agents talked' to 'the agents handed over an artifact.'

This Evolution's contract goes one step further: the artifact has a closed status set, and the controller rejects anything else.

Neither had a blocking reviewer or a human in the path.

Teardown: the LangGraph supervisorA graph with a hub node; the question is what passes back through the hub

Mechanism

A supervisor node picks the next worker; workers return to it; edges and state are explicit; a checkpointer persists state at every step.

The library version (create_supervisor) chose output_mode: full_history (every worker message) or last_message (only the final reply).

Design choice and cost

Choice: the controller is code you can read; the supervisor is one node in it.

Cost: every routing decision is a model call at the hub. full_history fills the supervisor's window; last_message hides the worker's trace. That is Cognition's argument about traces, set as a parameter.

Failure mode and the 2026 shift

Failure: with last_message the supervisor sees only the worker's summary and treats it as the result (#3, summary laundering).

2026: LangChain recommends a supervisor built with tool calling. The docs list five patterns: subagents, handoffs, skills, router, custom workflow.

Teardown: Claude Code subagents (and OpenCode's)Harness-native workers: a Markdown file, a tool allowlist, a clean window, and a message back

Subagents (Claude Code docs, Sep 2026)

Mechanism. A Markdown file with frontmatter (name, description, tools, model, permissionMode, maxTurns, hooks, isolation). It runs in its own window, and its result returns to the caller.

Nesting. Three levels deep by default (docs retrieved September 24, 2026).

Built-ins. Explore and Plan (read-only), general-purpose.

OpenCode. Same shape: primary agents (Build, Plan); subagents (General, Explore, Scout).

Agent teams (experimental) and what they teach

Mechanism. A lead, teammates, a shared task list, and mailboxes. Off by default (CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1).

Docs: 'A teammate can't approve a permission prompt or supply consent on your behalf.' The lead approves a plan 'without the lead reviewing it.'

Reading. Authority does not cross (E5); auto-approval cannot say no.

Failure. The caller trusts the returned message (#3).

Design choice: context isolation first, review second. The harness gives you the worker, and you supply the contract and the verdict.

Reference design: gzkit's controller–worker pipeline (ADR-0.18.0)Five stages; the controller never implements; every dispatch leaves a record

1

2

3

4

5

1 · Load context

The controller reads the brief (OBPI), its requirements, and its allowed paths. It dispatches nothing without a brief.

2 · Implement

The controller dispatches each task once to the implementer and gets a HandoffResult back, then to the spec reviewer and the quality reviewer, each of which returns a ReviewResult.

3 · Verify

The controller runs tests, lint, and the brief's verification commands itself. A worker's 'tests pass' is not this stage.

4 · Present evidence

The controller sends paths, commands, and outputs to the human rather than conclusions. (E9: Step 4b adds adversarial validation.)

5 · Sync

The controller writes ledger events, brief status, and dispatch records. The human attests, and the pipeline only records.

Reference design: HandoffResult, dispatch records, 'credit is never inferred'A role that was not dispatched did not happen, whatever the transcript says

The contract and the record

HandoffResult. DONE · DONE_WITH_CONCERNS · NEEDS_CONTEXT · BLOCKED.

ReviewResult. PASS · FAIL · CONCERNS with findings. Parsing is fail-closed.

Dispatch records. Every dispatch of every role writes a record.

'Credit is never inferred.' If there is no dispatch record for the spec reviewer, spec review did not happen.

The honesty flag

One agent may do everything if the run declares it: --single-driver --reason "...".

A declared single-driver run is read as one. An undeclared run presented as reviewed trips falsifier one.

If the reviewer could not run (Big Pickle unavailable, Go limit reached), the sortie is an ABORT rather than a PASS.

Flight Card 8: a reviewer that can say noExpansion · depends on Sortie 7

ENVELOPE            expansion
DESIGN CLAIM        No implementer output reaches main without a reviewer verdict, and a FAIL blocks.
SYSTEMS UNDER TEST  controller (graph or state machine) · implementer persona · reviewer persona (read-only)
                    · HandoffResult + ReviewResult schemas · fail-closed parser · merge gate · checkpoint
                    · ledger
SUBSTRATE           repo + commit · graph library + version · implementer model id · reviewer model id
DEPENDS ON          Sortie 7 PASS (memory layer), or its re-fly on record

ENTRY CONDITIONS    clean tree · ADR for the pair (roles, contract, graph) committed · Chase GO in the card

TEST POINTS
  1  clean task          -> HandoffResult DONE, parsed -> ReviewResult PASS citing diff -> interrupt, merge
  2  planted defect      -> ReviewResult FAIL with a located finding -> routed to implement -> no merge
  3  malformed result    -> parser REJECT logged (not JSON / unknown status / DONE without evidence)
                            -> no review dispatched, no merge
  4  'fix it yourself'   -> reviewer's edit denied by the harness; diff unchanged; verdict still returned
  5  resume after halt   -> checkpoint id logged; human approval recorded; exactly one merge commit

INSTRUMENTATION     dispatch log (one record per role per task) · 2+ ReviewResults · 1+ REJECT lines
                    · checkpoint ids · git log · ledger events

PRE-REGISTERED FALSIFIERS (any ONE => FAIL)
  - merged work with no ReviewResult on record for that task
  - a malformed result parsed as PASS or DONE
  - a reviewer claim accepted without the evidence it cites
  - passing only by loosening the parser, granting the reviewer edit, or editing the log

ABORT (halt-not-fail)  model route unavailable for either role; usage limit reached mid-sortie
CHASE               reads dispatch log, ReviewResults, REJECT lines, git log; re-runs one evidence command

SPRINT              Sortie 8 log · pair + contract + graph · Design Analysis · AI_LOG · brief acknowledged

slide 01

Multi-agent I: Controller, Worker, Reviewer

Evolution 8 is the first of two Evolutions on multi-agent systems. The field has rediscovered plan, do, check under a new name every few years since the mid-1990s, and the part that keeps going missing is a check with authority to stop the work. The survey covers the classical baseline in FIPA and BDI, the 2023 role systems, the frameworks that turned roles into configuration, and the harness-native subagents you already use. The build is an implementer and a reviewer with personas, a result contract whose parser rejects anything malformed, and a state graph with a checkpoint and a human interrupt before merge. The lab has you declare a read-only reviewer in OpenCode and check its verdict. Your personalized Final System brief arrives separately, and you acknowledge it in the Sprint.

slide 02

Plan, do, check: the recurring division of labor

The slide lists three renamings of one division of labor: manager and contractor in the 1980 contract net, architect and engineer in MetaGPT, main agent and subagent in the harness you use. The division is the same each time, and in each case the check with authority to stop the work is the part that is missing. Two rules apply through the spine. First, a worker returns a typed claim, which the controller parses against a closed set of statuses; the controller rejects anything else and never reads a status out of prose. Second, a verdict counts as evidence only if it cites what the reviewer checked and the reviewer could not edit the work. The design claim for Sortie 8 is the chapter's expansion card: no implementer output reaches main without a reviewer verdict, and a FAIL blocks the merge. The four falsifiers on the slide are pre-registered before anyone builds, so that nobody can change the test after the result is in.

slide 03

Why more than one agent, and what it costs

Anthropic's June 2025 post on its research system gives the numbers for more than one agent. The multi-agent version used roughly fifteen times the tokens of a chat turn, against about four times for a single agent; it scored 90.2 percent better than single-agent Opus 4 on Anthropic's internal evaluation; and on the BrowseComp benchmark, token usage alone explained about 80 percent of the variance in performance. In other words, a large part of the gain came from spending more tokens. The three reasons to split the work are context isolation, independent review, and parallelism. Walden Yan at Cognition published the counter-argument the same week: workers that do not share full traces make conflicting implicit decisions, because an action carries decisions that a summary omits. Both posts say that coding parallelizes less well than research. For this reason the build in this Evolution is sequential, with one implementer and one reviewer, and parallel work waits for E9, where locks are introduced.

slide 04

Plan / do / check under every name

The table puts the framing slide's argument into one view, with a row per system and a column per role. Read across a row. The contract net has a manager, a contractor, and typed messages between them. BDI has deliberation, execution by a plan library, and reconsideration when beliefs change. CAMEL has two roles and no checker: the assistant ends the task by writing a token. MetaGPT puts documents between the roles and adds executable feedback for the engineer. AutoGen's classic version runs until some agent writes TERMINATE, and CrewAI's hierarchical process gives the manager the reviewing job and lets a task carry a guardrail function. The harnesses give you a subagent and a message back. The last column, what carries the result, is the one to watch: the systems that carried typed results between roles were the ones that could check them.

slide 05

Roles and personas: traits, anti-traits, and the why

The reference design uses four roles: implementer, spec reviewer, quality reviewer, and narrator. A persona file for one of them holds the role, traits written as observable behavior, anti-traits, and one sentence on why the role exists. The anti-traits carry the most weight, because each states a failure you expect: a reviewer that fixes the code has stopped being a reviewer, and a reviewer that softens a FAIL to keep the conversation pleasant is the sycophancy problem in a job title. The why sentence tells the model what is at stake, so that it can decide a borderline case the traits do not cover. Delete a generic expertise claim such as 'You are a world-class senior engineer', because it changes the tone of the reply and leaves the behavior unchanged. The right panel is the course's example reviewer persona, and it is close to the file you write in the lab. The strip at the bottom is the chapter's exercise: remove the anti-traits, run the reviewer again, and count how its verdicts change.

slide 06

Result contracts: the worker's claim has a type

The implementer returns a HandoffResult with one of four statuses, which the reference design calls DONE, DONE_WITH_CONCERNS, NEEDS_CONTEXT, and BLOCKED. The fields beyond status are the course's, and you can extend them. Two of the four statuses are ways to say 'I did not finish', and that is deliberate: a worker with a legitimate way to say BLOCKED has less reason to fabricate DONE. The reviewer returns PASS, FAIL, or CONCERNS with findings, and each finding carries a location. The third card shows fail-closed parsing in twelve lines: the parser rejects invalid JSON, an unknown status, and a DONE without evidence, and no branch of the function returns DONE by default. A parser that catches the exception and carries on with a default status is the bug to look for in your own code, because it turns a crash or a refusal into a merge.

slide 07

Two-stage review: spec first, then quality

Two-stage review comes from the reference design. The implementer returns a typed result and the controller parses it. The spec reviewer then asks one question: does this change do what the brief says, inside the allowed paths? Only after a spec PASS does the quality reviewer ask whether the change is done well, with meaningful tests, handled errors, and no dead code. The order matters because a quality reviewer handed the wrong feature will review it carefully and pass it. The controller merges on two PASS verdicts that cite evidence, sends CONCERNS to the human, and bounds the retries: after a fixed number of FAIL rounds the task goes BLOCKED to a person instead of looping. For Sortie 8 one reviewer is Sound, and two stages with separate personas is Exceptional.

slide 08

State graphs: the controller as nodes, edges, and a checkpoint

The controller is a graph with three nodes, implement, review, and merge, and a conditional edge after review that routes pass to merge, fail back to implement, and halt to the end. When you compile the graph with a checkpointer, the output of every node is saved. The second card is the human interrupt: interrupt() pauses the graph, the checkpointer saves the state under a thread id, and a Command with a resume value continues it. Put the interrupt before merge, and the human becomes a node in the graph rather than a sentence in the README. The third card records a change in LangChain's own guidance: build the supervisor with tool calling. The langgraph-supervisor library has had no release since November 2025. If you do not want LangGraph at all, a small state machine with declared states and a checkpoint file written after each node meets the Sprint requirement. A for-loop with no persisted state does not meet it, because nothing survives a halt for a human to resume.

slide 09

The read-only reviewer in configuration

This is the configuration you write in the lab. In OpenCode an agent is a Markdown file in .opencode/agents with frontmatter: a description, mode subagent, a low temperature, and a permission block. The block denies edit, denies webfetch, and denies bash except for git diff and git log. You invoke the agent with an at-mention in the TUI, or non-interactively with opencode run and the agent flag, and a primary agent can call it through the task tool. Claude Code has the same shape, a file in .claude/agents with a tools allowlist. The doctrine from E5 applies to both: the permission line is the enforcement, and the anti-trait in the persona is the explanation the model reads. Test both by asking the reviewer to fix the bug and watching the harness refuse. Two notes from the current OpenCode docs: the tools key is deprecated in favor of permission, and hiding a subagent from autocomplete does not stop a model from calling it through the task tool.

slide 10

Common mistakes: how a pair of agents becomes one agent with extra steps

The table lists six ways a pair of agents collapses into one agent with extra steps. A reviewer that runs in the implementer's session shares its context and its blind spots, so the review agrees with the author. A controller that searches the reply for the word PASS invites metagaming, because 'this would not PASS without tests' contains the word. A parser that defaults to DONE on an exception merges a crash or a refusal. A reviewer handed the implementer's summary checks a claim against itself, so give it the diff and the test output. A reviewer with write access fixes the code and then passes its own fix. An unbounded retry loop continues until the reviewer gives in. Each row carries an Appendix C number for your debrief. The strip previews E9: gzkit's ten-deep chain of 2026-05-24 is row four repeated at every level.

slide 11

Worked trace: one task, three results, one rejection

The trace is the kind of log the Chase reads. The first implementer result parses, and the reviewer fails it with a finding that cites the brief's second requirement and the test that is missing. The controller routes the task back. The second attempt comes back as chat prose, 'I added the test and everything passes now.' The parser rejects it because it is not JSON, and the controller re-dispatches once with the schema attached, counting the round against the bound of three. The third result parses, and the reviewer passes it with a list of what it checked, including the test by its name. The graph stops at the interrupt, the student approves, and the merge has a commit id. The last two lines are the dispatch records per role and the Chase's reading list. The Chase re-runs the test command, because the evidence field is a claim until someone runs the command it cites.

slide 12

Teardown: FIPA and BDI, the pre-LLM baseline

The first teardown is the classical baseline. The contract net protocol dates to Reid Smith's 1980 paper: a manager sends a call for proposals, contractors propose or refuse, the manager accepts one bid and rejects the rest, and the winner reports a result or a failure. FIPA, founded in 1996 and moved to an IEEE standards committee in 2005, standardized the message language so that every message carried a performative. The mechanism to take from it is that the message type told the receiver what kind of claim the message held. The failure mode is that the vocabulary never said whether an inform was true, which is fabrication, Appendix C number three. BDI, from Rao and Georgeff's 1995 paper, made intentions first-class objects with explicit commitment and reconsideration when beliefs change. LLM agents kept the goals and dropped the inspectable belief state, since a chat transcript is not a belief base that a program can query. One note on sources: the fipa.org domain no longer hosts the specifications, so cite the IEEE and archived copies.

slide 13

Teardown: CAMEL and MetaGPT, roles in 2023

The second teardown covers the 2023 role systems. CAMEL set two agents talking with inception prompts and no human in the loop, and the paper reports four failures: role flipping, repeated instructions, flake replies, and infinite loops. Its halt is the assistant writing a special token, which is completion by assertion, fabrication and metagaming in one line. MetaGPT corrected that design with roles modeled on a software company, connected by structured documents through a publish-subscribe pool, and with executable feedback for the engineer. It reported 85.9 percent and 87.7 percent Pass@1 on HumanEval and MBPP. Its failure mode is that every role reads the same upstream documents, so a wrong requirement in the PRD flows downstream intact. The third card states what your build takes from the pair: MetaGPT's documents had a fixed structure that a program can check, and this Evolution's contract adds a closed status set and a verdict that blocks.

slide 14

Teardown: AutoGen and CrewAI, roles as configuration

In the third teardown, roles became configuration. AutoGen's classic design made coordination a conversation: an assistant writes code, a user proxy runs it and can pull in a human, and a group chat manager picks who speaks next. Because the user proxy ran the code, the loop also held the result of running it. Its halt was a TERMINATE string. The AutoGen repository is now in maintenance mode and points new users to Microsoft Agent Framework, which reached 1.0 on April 3, 2026, with sequential, concurrent, handoff, group chat, and Magentic-One orchestrations, checkpointing, and human approvals. CrewAI made coordination an org chart, in which the hierarchical manager plans, delegates, and reviews. Its task guardrail is the closest thing in the survey to your contract: a function returns a boolean and a value, and on False the agent retries, three times by default. The failure to watch for is a retry loop against a checker, which a worker can metagame. Manager and workers also often share one model.

slide 15

Teardown: the LangGraph supervisor

The fourth teardown is the LangGraph supervisor. The mechanism is a hub node that routes to workers and gets control back, with a checkpointer under everything. The older library (create_supervisor) reduced the main trade-off to one parameter, output_mode: the supervisor sees every worker message, or only the last one. Full history fills the supervisor's window, and last message hides the worker's trace. With last message, a supervisor that sees only a worker's summary treats it as the result, which is summary laundering. In 2026 LangChain's own advice is to build the supervisor with tool calling, so that you control what each subagent receives and returns, and its multi-agent page lists five patterns: subagents, handoffs, skills, router, custom workflow. For your build, what passes back through the controller should be the typed result and a pointer to the evidence.

slide 16

Teardown: Claude Code subagents (and OpenCode's)

The fifth teardown is the harness-native version, the one you use. A Claude Code subagent is a Markdown file with frontmatter; it runs in a clean window, sees the delegation message and the project instructions but not the conversation, and returns a message to the caller. The docs retrieved September 24, 2026 allow nesting three levels deep by default, and this limit changed this year. OpenCode has the same shape, and you build one in the lab. Agent teams are the experimental step up: a lead, teammates in their own windows, a shared task list, and mailboxes. Two lines from the docs bear on review and authority. A teammate cannot supply consent on your behalf, which is E5's rule that authority does not cross between agents. The lead approves a teammate's plan without reviewing it, which is a review step that can only say yes. The harness gives you the workers, and you supply the contract and the verdict.

slide 17

Design Analysis, live: Claude Code subagents (2025–26)

The Design Analysis of Claude Code subagents is worked live: the nine components go on the board, and the class fills the Coordination and Evaluation rows before the answers appear. The answers come from the current docs. The Evaluation and feedback row is the one your contract changes: there is no verdict schema, and the caller reads a message. Hooks (PreToolUse, PostToolUse, Stop) are the place where a check can be installed, and that is the space your contract fills. Governance is stronger than in most of the systems surveyed: permission modes per subagent, and the rule that teammates cannot consent for the human. The judgment loop in the strip is the model for your own Design Analysis. The decision was to isolate context per worker; it privileges clean windows and a cheap parent context; it costs tokens and the lost trace; its failure mode is a summary accepted as fact; and nothing preserves against that failure by default, so your contract has to.

slide 18

Reference design: gzkit's controller–worker pipeline (ADR-0.18.0)

gzkit's ADR-0.18.0 defines a five-stage pipeline: load context, implement with two-stage review per task, verify, present evidence, and sync. The controller never implements; it dispatches, parses, and decides. In stage three the controller runs the tests, the lint, and the brief's verification commands itself, which is why a worker's claim that tests pass is not verification. Stage four presents paths, commands, and outputs to the human rather than conclusions, and E9 inserts the adversarial validation step there. Stage five writes the ledger events, the brief status, and the dispatch records, and the human attests to the result. The files to read are the subagent-pipeline concept document, roles.py, pipeline_dispatch.py, and the persona directory.

slide 19

Reference design: HandoffResult, dispatch records, 'credit is never inferred'

Two mechanisms make the pipeline auditable. The controller parses both result types fail-closed, and every dispatch of every role writes a record. The rule that credit is never inferred depends on those records: no record for a role means the role did not run, whatever a summary says. The right panel is the honesty flag. The reference design allows a run in which one agent does everything, but the run must declare it with a reason, and the course takes the same line: a declared single-driver run is read as a single-driver run, and an undeclared one presented as reviewed fails. If your reviewer cannot run because the model route is unavailable or you reached a usage limit, the sortie is an ABORT, and the flight log says so.

slide 20

Reference design: why the rule exists

Two dated episodes from Appendix G explain why the reference design insists on records. On 2026-05-24, a chain of subagents ten levels deep turned summaries of summaries into facts, and the rule that came out of it is that a subagent's claim is not evidence. On 2026-08-21, a pipeline gate checked only that a marker file existed; a stale marker licensed roughly 350 lines of change with no dispatch and no review, and the rule that came out of it is that a presence check tells you something is armed, never that the procedure ran. Both episodes return in detail in E9. For this Evolution, the consequence for your controller is that the merge gate checks for a ReviewResult tied to this task and this diff, and a file that says review happened does not satisfy it.

slide 21

Evaluation lens: a strong Sortie 8

The lens has three columns. A weak Sortie 8 has a reviewer that is the implementer in the same session, a verdict read by substring, a parser that defaults to DONE, a reviewer with write access, a persona that asserts expertise, and a loop with no saved state and no human before merge. A sound one has a separate read-only reviewer declared in configuration, two schemas with closed status sets, malformed input rejected and logged, a FAIL that blocks with a bound on rounds, findings with locations, a graph with a checkpoint and an interrupt, and a dispatch record per role. An exceptional one adds two-stage review, a reviewer on a different model with both ids logged, the anti-trait ablation measured, an honest squawk for a defect the reviewer missed, and a Chase who re-runs the evidence commands and gets the same exit codes.

slide 22

Flight Card 8: a reviewer that can say no

Flight Card 8 is an expansion card. It has five test points: a clean task that merges only after a cited PASS and a human approval; a planted defect that the reviewer fails and that does not merge; a malformed result that the parser rejects before any review is dispatched; a reviewer asked to fix the code, whose edit the harness denies while the verdict still returns; and a resume from a checkpoint that produces exactly one merge commit. The falsifiers are the chapter's three plus a fourth from the reference design, a pass obtained by weakening a check: loosening the parser, granting the reviewer edit, or editing the log. The Sprint line adds one item, the acknowledgment of your Final System brief.

slide 23

A worker's result is a claim with a type. A verdict counts only if its author could not edit the work.

A worker's result is a typed claim, and a verdict counts only when it cites evidence and its author could not edit the work. The lab follows: declare the reviewer and check what it tells you.
