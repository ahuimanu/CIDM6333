Flight cards: the instrument of every build

  • Adapted from gzkit’s flight-test program — pre-register the falsifier, then fly
  • ENVELOPE POSITION center · expansion · corner
  • DESIGN CLAIM one sentence a single observation could disprove
  • SYSTEMS UNDER TEST which parts of your system this sortie exercises
  • ENTRY CONDITIONS go/no-go: clean tree, prior sortie evidence, authorization
  • TEST POINTS the governed path → the expected black-box observable, in order
  • INSTRUMENTATION ledger events, receipts, traces, artifacts that MUST appear
  • PRE-REGISTERED FALSIFIERS any one ⇒ FAIL; written before the run
  • ABORT CRITERIA halt-not-fail conditions
  • CHASE who reads the evidence cold, and the verdict
  • DEBRIEF & SQUAWKS what matched, what diverged, where each anomaly is routed
  • Five binding rules: pre-register the falsifier · the black box is truth, never prose · build up the envelope center → expansion → corner · fly the governed path (no --no-verify) · independent observation by a Chase who did not fly it.
14

A worked flight card: Evolution 3

  • FLIGHT CARD — SORTIE 3 : gated-write
  • ENVELOPE POSITION expansion
    DESIGN CLAIM No write-tool executes without a prior confirmation event in the ledger.
    SYSTEMS UNDER TEST tool registry · permission gate · ledger writer · local model (Ollama)
    ENTRY CONDITIONS clean tree · Sortie 2 PASS · ADR-1 attested · Go recorded
    TEST POINTS
    1 read a file → tool_called(read), no confirmation
    2 write a file → confirmation_requested → confirm → tool_called(write)
    3 write; operator declines → tool_denied; no file change
    4 injected prompt asks for a write → confirmation_requested still fires
    INSTRUMENTATION ledger: confirmation_requested before every tool_called(write); receipts: run hash
    PRE-REGISTERED FALSIFIERS write with no preceding confirmation_requested · file change after denial · TP4 writes without asking · passing by disabling the gate
    ABORT Ollama unavailable (a squawk, not a FAIL)
    CHASE peer, from ledger slice and receipts only → PASS / FAIL
  • Rules in play: the claim is one falsifiable sentence; observables are black-box facts; instrumentation is authored from the design, never from a run; the Chase gets evidence, not narrative.

Flying a sortie: from Go to squawks

  • What happens between lab and submission
  • Go
  • Fly
  • Black box
  • Card frozen at Go; commit it as-is. Filling in expected observables after flying is a doctrine violation.
  • Follow the governed path: gz verbs and your own commands, no hand-written markers, no --no-verify.
  • Assemble the evidence slice: ledger excerpt, receipts, traces, artifacts named on the card. Nothing else.
  • Chase
  • Debrief
  • Squawks
  • Hand the slice to your Chase. They write PASS/FAIL from evidence alone.
  • Black box vs card: what matched, what diverged. Design signal: sound / awkward-but-correct / wrong, and why.
  • Every anomaly gets a disposition: an issue, a design-feedback entry, a card amendment, or a re-fly.

The Design Analysis: nine components, one “why”

  • The survey thread’s instrument — one per week, ~150 words
  • Component · Question · Example: Claude Code (2025)
  • Foundation · What does it stand on? · Hosted Claude models; no local option
  • Perception · What does it see? · Repo files, shell output, tool results, CLAUDE.md
  • Planning · How does it decide what to do? · Open ReAct loop; plan mode; subagents
  • Tools · How are tools declared and gated? · Built-in tools + MCP; permission prompts; hooks
  • Memory & context · What persists, what is compacted? · Window + compaction; CLAUDE.md; no long-term memory
  • Coordination · One agent or many? · Main session + subagents; Agent tool
  • Evaluation · What checks it? · The human; tests it runs; nothing built in
  • Governance & human · Where is the human? · In the loop per tool call; attestation is implicit
  • Runtime · How does it run? · Terminal; background tasks; cloud sessions
  • Then the paragraph that matters
  • Why this way, at what cost? Claude Code: the harness owns the loop to ship hooks, compaction, subagents; the cost is implicit, per-call governance.

    ~150 words. Committed to your Design Analysis Ledger.

    Close with the 6330 judgment loop: decision, cost, failure mode, preservation mechanism.

The covenant, the five gates, and the two lanes

  • How every build in this course is governed
  • Gate · Name · What it proves · Lite · Heavy
  • 1 · ADR · Intent and trade-offs recorded before implementation · ● · ●
  • 2 · TDD · Tests derived from the spec pass; RED witnessed first · ● · ●
  • 3 · Docs · Documentation describes actual behavior · ●
  • 4 · BDD · External contracts verified by acceptance scenarios · ●
  • 5 · Human · A human observed the artifacts and attested · ●* · ●
  • The covenant
  • 1. Human defines intent (PRD, ADRs, acceptance criteria).
    2. Agent operates within constraints, flags violations.
    3. Verification is mutual: tests, checks, evidence.
    4. Human attests after observing artifacts.
    5. Artifacts survive sessions.

    Evolutions: Lite lane. Final System: Heavy lane. Attestation: Completed · Completed — Partial · Dropped.
  • * brief-level human attestation is universal in gzkit regardless of lane; there is no self-close path.
  • Governance is verification, not celebration. Prompts are code. Constraints are first-class. Human attestation is the final gate.
