The question behind the course

Why are agentic systems built this way, and can you answer for yours?

Survey

In each Evolution we take two or three real systems apart against one component model. You write one Design Analysis per Evolution.

Build

You choose one system on day one and add a layer in every Evolution. Each layer flies against a flight card and is defended face to face.

“A system can produce an answer without being able to answer for it.” · Tree Hollow. In this course, you are the one who answers.

What makes a system an agent?From PEAS to the LLM agent loop to the nine components you will analyze

Russell & Norvig

An agent perceives through sensors and acts through actuators. Specify it by PEAS: Performance measure, Environment, Actuators, Sensors.

The nine components of a Design Analysis

Foundation

model, weights, data; local or hosted

Perception

what it sees: text, tool results, screens, events

Planning

ReAct, CoT/ToT, decomposition, fixed workflow or open loop

Tools

declaration, calling, permissioning, recovery

Memory & context

window, compaction, persistence, retention

Coordination

single, controller–worker, crew, graph, protocol

The LLM agent loop

Perceive → Reason → Act → repeat until a halt condition. ReAct (2022) is the canonical form. The 2023 autonomous agents failed most often at the halt condition.

Evaluation

what checks it; how failure is detected and replanned

Governance & human

index zero, in the loop, on the loop, absent; what is attested

Runtime

scheduling, observability, rollback, cost

Why governance: the Degradation PatternHow you lose control one “looks good” at a time

Week 1

You prompt carefully, review every line, understand what is built.

Week 2

You skim diffs and trust the green checkmarks.

Week 3

You batch approvals; “looks good” becomes reflexive.

Week 4

You approve PRs you did not read, for code you do not understand.

The Zero Doctrine: the human is index zero

First in priority: your intent drives every decision.

Final in authority: you sign off, not the model.

Cannot be automated away.

Gates constrain agents; humans must engage. Gates without human engagement produce passing checks that no person verified.

What this course does about it

Every build is governed (PRD → ADR → brief → tests → attestation).

Every week you defend the work face to face, no AI.

Every claim is flown against a pre-registered falsifier.

Every AI interaction is logged; the log is discussed, not filed.

Flight cards: the instrument of every buildAdapted from gzkit’s flight-test program: pre-register the falsifier, then fly

ENVELOPE POSITION center · expansion · corner

DESIGN CLAIM one sentence a single observation could disprove

SYSTEMS UNDER TEST which parts of your system this sortie exercises

TEST POINTS the governed path → the expected black-box observable, in order

INSTRUMENTATION ledger events, receipts, traces, artifacts that MUST appear

PRE-REGISTERED FALSIFIERS any one ⇒ FAIL; written before the run

ABORT CRITERIA halt-not-fail conditions

CHASE who reads the evidence cold, and the verdict

DEBRIEF & SQUAWKS what matched, what diverged, where each anomaly is routed

Five binding rules: pre-register the falsifier · the black box is truth, never prose · build up the envelope center → expansion → corner · fly the governed path (no --no-verify) · independent observation by a Chase who did not fly it.

A worked flight card: Evolution 3FLIGHT CARD · SORTIE 3 : gated-write

ENVELOPE POSITION  expansion
DESIGN CLAIM  No write-tool executes without a prior confirmation event in the ledger.
SYSTEMS UNDER TEST  tool registry · permission gate · ledger writer · local model (Ollama)
ENTRY CONDITIONS  clean tree · Sortie 2 PASS · ADR-1 attested · Go recorded
TEST POINTS
  1  read a file → tool_called(read), no confirmation
  2  write a file → confirmation_requested → confirm → tool_called(write)
  3  write; operator declines → tool_denied; no file change
  4  injected prompt asks for a write → confirmation_requested still fires
INSTRUMENTATION  ledger: confirmation_requested before every tool_called(write); receipts: run hash
PRE-REGISTERED FALSIFIERS  write with no preceding confirmation_requested · file change after denial · TP4 writes without asking · passing by disabling the gate
ABORT  Ollama unavailable (a squawk, not a FAIL)
CHASE  peer, from ledger slice and receipts only → PASS / FAIL

Rules in play: the design claim is one falsifiable sentence; observables are black-box facts; instrumentation is authored from the design, never from a run; the Chase gets evidence, not narrative.

The reference design: gzkitGovZero Kit: a development covenant for human–AI collaboration

What it is

A governance meta-harness one tier above Claude Code, Codex, and Copilot. It wraps agents with gates, evidence, and attestation. PRD → ADR → brief (OBPI) → REQ → TASK → evidence. Five gates: ADR, TDD, Docs, BDD, Human. The append-only ledger is the truth.

The arc, January to August 2026

Jan

Genesis; enforced governance via hooks

Feb–Mar

stdlib-first; OBPI pipeline; personas; subagent dispatch; three layers of truth

Apr

Receipts (ARB); first outside adopter; universal attestation

Why it is the reference design

The one system where we have the whole record: 87 ADR packages, 542 briefs, 15,380 ledger events, 558 course-corrections, 76 releases, and dated incidents from January to August 2026. We read this one from the inside, including what went wrong.

May

AGENTS.md as derived view; V.I.B.E.S. defined; eight rule sharpenings

Jun–Jul

Repudiations; MX hangar; airlock; foundation sunset

Aug

Measurement era; commit-locus enforcement; “presence is not procedure”

The covenant, the five gates, and the two lanesHow every build in this course is governed

GateNameWhat it provesLiteHeavy
1ADRIntent and trade-offs recorded before implementation●●
2TDDTests derived from the spec pass; RED witnessed first●●
3DocsDocumentation describes actual behavior●
4BDDExternal contracts verified by acceptance scenarios●
5HumanA human observed the artifacts and attested●*●

The covenant

1. Human defines intent (PRD, ADRs, acceptance criteria).

2. Agent operates within constraints, flags violations.

3. Verification is mutual: tests, checks, evidence.

4. Human attests after observing artifacts.

5. Artifacts survive sessions.

Evolutions: Lite lane. Final System: Heavy lane. Attestation: Completed · Completed — Partial · Dropped.

* brief-level human attestation is universal in gzkit regardless of lane; there is no self-close path.

Governance is verification, not celebration. Prompts are code. Constraints are first-class. Human attestation is the final gate.

Choosing your system (E0)One system that can take all twelve layers · pitch it in one page

Governance MCP server over gzkit

Expose gz verbs and the ledger as MCP tools/resources; an agent that answers “what is attested?”

Research and evidence assistant

Retrieves, summarizes, and cites with receipts; memory of what was read; a reviewer agent that checks citations.

Support or triage agent

Classifies incoming requests, gathers context through tools, drafts responses, escalates to a human under rules.

Data-pipeline operator

Plans and runs ETL steps as tools, validates outputs, replans on failure, keeps a run ledger.

Code-review or test-writing agent

Reads a repo, proposes tests or reviews under a spec-reviewer/quality-reviewer split, never merges.

Personal operations agent

Calendar, files, and messages through MCP servers with strict write gating and an audit trail.

Constraints: an identifiable user and problem; work you may show; every layer addable; no credentials or private data in the repo; local-model weeks feasible on your hardware. Your own idea is welcome if it passes these.

slide 01

CIDM 6333

Welcome to CIDM 6333, Agentic Systems Design and Development. I am Dr. Jeffry Babb. This deck is the orientation. It covers what the course is, how each class session runs, what you will build, what you will analyze, how the work is scored, and the four choices you make in Evolution 0 (model, harness, framework, and kit). The slide lists the four parts of the semester: survey the systems, build your own, govern the build, and defend it in person.

slide 02

The question behind the course

The course asks two questions. The first is a survey question: why are these systems designed the way they are? For each design you will ask what problem it answered and what it cost, rather than whether it is popular. The second is a build question: can you make one, and can you answer for it? The Tree Hollow essay is the first reading because it states the stake. A model can produce an answer that it cannot answer for. In this course you are the person who answers, and the flight cards, the consultations, and the attestations each put that obligation on you at a specific point in the week.

slide 03

Layers of AI: the one everybody forgets

This is the first of two maps you will use all semester. It has seven layers. Agentic AI sits on top (memory, planning, tool use, autonomous execution). Under it are generative AI, deep learning, neural networks, machine learning, and classical AI. At the bottom is the data foundation: ownership, definitions, data quality, and lineage. Every agentic system you analyze stands on all seven. When you write a Design Analysis, start at the bottom: which model, which weights, and which data the system stands on, and whether they are local or hosted. The foundation returns in E7, when you build memory on embeddings, and in E11, when you ask what your evaluation data actually is.

slide 04

From AI & ML to Agentic AI

The second map has five stages, left to right. AI and ML turn data into decisions. Deep learning stacks networks for complex tasks. Generative AI creates content. AI agents take on autonomous tasks: tool use, planning, memory, context management, and a human in the loop. Agentic AI automates whole processes with multiple agents, protocols, delegation, intent preservation, rollback, evaluators, cost management, observability, and governance. This course covers the two right-hand columns. Evolutions 1 through 7 build the AI Agents column on your system, and Evolutions 8 through 12 build the Agentic AI column. I have assigned every box on this board to an Evolution, and the Course Topic Guide shows the mapping.

slide 05

What makes a system an agent?

Before the LLM there was a workable definition of an agent: something that perceives its environment and acts on it, specified by PEAS (performance measure, environment, actuators, sensors). The LLM agent loop is that definition with a model as the reasoner: perceive, reason, act, and repeat until a halt condition holds. Most of what went wrong in 2023 was the halt condition. The nine components on the right are the questions you will ask of every system this semester: what it stands on, what it sees, how it plans, how it uses tools, what it remembers, how it coordinates, what evaluates it, where the human is, and how it runs. A Design Analysis is nine short answers and one paragraph on why.

slide 06

Why governance: the Degradation Pattern

The course structure follows from one pattern, the Degradation Pattern. In week one a developer reads every line the agent writes; by week four the same developer approves pull requests without reading them. No one decides to lose control. Control erodes one approval at a time. The Zero Doctrine, from gzkit, is the response: the human is index zero, first in priority and final in authority, and that role cannot be automated away. The covenant binds both sides. Gates constrain the agents, and humans must engage. Gates without engagement produce theater, in which every check passes and no person has verified anything.

slide 07

Two threads, every week

Thread A is the survey. In lecture I take two or three systems apart; you pick one and write a Design Analysis of about a hundred and fifty words (nine components and one paragraph on why it was built that way). The analyses accumulate in a ledger in your repository, and because the class has fewer than ten students, the class together covers the whole corpus. gzkit is the reference design because it is the one system whose full record is available. Thread B is the build: one system, one layer per Evolution, each layer flown against a flight card and governed with the kit.

slide 08

How the semester runs

The semester has an orientation, twelve Evolutions, and a closeout. Each Evolution adds one layer: the agent loop, patterns and frameworks, tools, two Evolutions of MCP, context, memory, two of multi-agent coordination, two of evaluation, and deployment. Two Evolutions are starred: E3 and E7 must run on a local open-weight model whichever route you chose.

slide 09

The arc: twelve layers on one system

Read this slide from the bottom up. After E1 you have a loop that halts and a PRD. By E3 the loop has gated tools. By E5 it speaks MCP and is hardened. By E7 it has context discipline and memory. By E9 it is a small crew with an adversary. By E11 it can be evaluated and traced. By E12 it is served and released with a rollback path. The final system is this stack, closed out under the Heavy lane. For this reason the system you choose in E0 has to be one that can take every one of these layers.

slide 10

How a class session runs

Every class session has the same shape. The first hour is lecture: the Evolution's design claim, two or three systems taken apart, what the reference design did, where the naive version breaks, what a strong sortie looks like, and the brief for the Evolution's flight card. Laptops close and no AI is used. Drift opens with a stand-up of one minute each, in which you give the previous Evolution's verdict and the new card's design claim. Every card leaves the hour with a Go or a No-Go. The last half hour is lab, where you fly the first test points with me in the room. You fly the rest of the sortie on your own; it is due the evening before the next session.

slide 11

This schedule works because the class has fewer than ten students. The stand-up takes ten minutes.

slide 12

Flight cards: the instrument of every build

A flight card is a one-page form you fill in before you touch the terminal. It comes from gzkit's flight-test program, which borrowed it from aircraft flight test, where a pilot does not fly an untested aircraft to see what happens. The envelope position states how far from the known-good center the sortie goes. The design claim is one sentence that a single observation could disprove. The test points are the path you will fly and the observable you expect at each step. The instrumentation lists what must appear in the black box. You write the falsifiers before the run, and if any one appears, the sortie has failed. A Chase reads the evidence cold and writes the verdict. You then debrief and route every squawk. Five rules bind the card, and the fifth matters most: the Chase never sees your narrative, only your evidence.

slide 13

A worked flight card: Evolution 3

This is the card for E3, written the way I want yours written. The design claim is one falsifiable sentence: no write-tool executes without a prior confirmation event. Four test points follow in order, each with the observable that must appear in the black box. In test point 4, the file the agent reads contains a prompt injection that asks for a write, and the gate must still fire. You write the falsifiers before you run anything. The last falsifier is the anti-vibing tripwire: a pass obtained by disabling the gate is a fail. The abort criterion keeps a broken Ollama install from being scored as a design failure. The Chase gets the ledger slice and the receipts, and never your account of the run.

slide 14

Flying a sortie: from Go to squawks

The sortie has six steps. Step 1: freeze the card at Go and commit it as it stands. Step 2: fly the governed path and capture evidence during the run, not afterward. Step 3: assemble the black box from only the evidence the card lists. Step 4: your Chase reads it cold and writes the verdict; if the Chase cannot reach PASS from the evidence alone, you have not passed, however well the run went. Step 5: debrief by comparing the black box against the card. Step 6: route every squawk (an anomaly) to an issue in your repository, a design-feedback entry, an amendment to the card, or a re-fly.

slide 15

The Design Analysis: nine components, one “why”

The Design Analysis is the survey thread's instrument, and it is about a hundred and fifty words on purpose. It has nine components, one line each, and then a paragraph on why the system was built this way and what that cost. The example on the slide is Claude Code. Anthropic's harness owns the loop so that hooks, compaction, and subagents can ship as product features; the cost is that governance is per call and implicit, and the reference design fills that gap one tier up. End it with the judgment loop from CIDM 6330: the decision, what it privileged, what it cost, what breaks first, and what preserves the intent.

slide 16

The survey: what we take apart, in order

This is the corpus, in order. Before LLMs came symbolic agents, expert systems, BDI, multi-agent platforms, and reinforcement learning. Later designs reuse these ideas with a language model in the reasoner slot, and part of the survey is to trace which ideas each one reuses. In 2022 the loop arrived: chain-of-thought, then ReAct. In 2023 came tools, function calling, AutoGPT and its spirals, memory, and roles. In 2024 agents were put to work on coding benchmarks, Devin, and computer use, and Anthropic released MCP in November. 2025 brought the harnesses (Claude Code, Codex, the SDKs), A2A, AGENTS.md, skills, the spec kits, and context engineering as a discipline. 2026 brings harness engineering, background agents, and the reference design's own history, which the course reads as case studies because its full record is available.

slide 17

The reference design: gzkit

gzkit is the reference design. It is a governance meta-harness: it sits one tier above the vendor harnesses and wraps them with evidence capture, gates, and human attestation. It does not run agents. Its spine is PRD, ADR, brief, requirement, task, and evidence, with five gates and two lanes. gzkit is the reference because its whole record is available, including the failures, and not because it is right: the ADR whose attested implementation did not exist, the hooks that never saw a Bash write, and the pipeline gate that checked only that a marker file existed.

slide 18

The covenant, the five gates, and the two lanes

gzkit has five gates: ADR (intent before implementation), TDD (tests from the spec, with the red witnessed before the green), Docs (what is written matches what runs), BDD (acceptance scenarios for anything with an external contract), and Human (a person looked and signed). The Lite lane is gates 1 and 2, and your weekly Evolutions run in it. The Heavy lane is all five, and the Final System closes out under it. The covenant is five sentences, and it binds both parties. The attestation vocabulary is closed: Completed, Completed — Partial with a reason, or Dropped with a reason. No other status counts.

slide 19

What an Evolution submission contains

Each Evolution's folder receives the same eight items: the card as frozen at Go; the code and tests for the layer; the evidence slice, limited to what the card lists; your Chase's verdict; your debrief with squawks; your Design Analysis; the governance artifacts the kit touched during the Evolution; and the Evolution's entry in your AI log.

slide 20

How an Evolution is scored

The rubric will be posted before the first Evolution is due. This slide shows its intended shape, so that you know from the first day what I am looking for. The rubric has five dimensions, each scored from zero to four. The first is the card: whether its design claim was falsifiable, and whether you wrote the instrumentation from the design rather than from a run. The second is evidence and verdict: whether the black box supports the design claim, and whether the Chase could reach the verdict from evidence alone. The third is the Design Analysis: specific answers and a stated reason for the design. The fourth is the defense: mechanism rather than outcome, trade-offs that hold under counterfactuals, and the AI log discussed. The fifth is professional practice, which includes Chase duty for a peer. Two caps apply. A card you cannot defend caps at developing, and work that is not in the repository at the deadline cannot be evaluated.

slide 21

The Final System: the same system, closed out and released

The final system is your system, closed out under the Heavy lane and released. You do not start a new project for it. I set the scope from your demonstrated work. The deliverables are the governance chain end to end, the evaluation suite with a red-team card, a served or containerized system with a rollback path, a release, your Design Analysis Ledger, your AI log with a final reflection, and a closeout ceremony in which you execute and I observe. Scoring follows the CIDM 6330 governed-revision split: thirty, twenty-five, twenty-five, ten, and ten.

slide 22

Choosing your system (E0)

The slide offers six starting points, and your own idea is welcome if it meets the constraints. The first fills a gap in the reference design: gzkit deliberately does not speak MCP, so an MCP server over the gz verbs and the ledger is useful and also raises a good teardown question. The other five are ordinary shapes that take every layer: a research assistant with receipts, a triage agent with escalation rules, a pipeline operator that replans, a review agent that never merges, and a personal operations agent with hard write gating. Whatever you choose, ask whether you can add all twelve layers to it. If memory, a second agent, or serving would be artificial in your system, choose a different one.

slide 23

Model access: choose your route

You choose one of two routes and state it in your E0 pitch. Route A is a subscription, about twenty dollars a month, plus a small API budget for the SDK and MCP work, because agents are built in a harness and an API, not in a chat window. Route B is fully local: Ollama, open-weight models sized to your machine, and a local harness. Route A is faster and more capable. Route B is private and free, and it exposes the trade-offs that the hosted route hides. On either route, everyone runs E3 and E7 on a local model. For sizing, a thirty-billion-parameter coder model needs twenty-four to thirty-two gigabytes of memory, and a twenty-billion or eight-billion model runs in eight to sixteen.

slide 24

Harness choices

Your harness is where the model works inside your repository. Each harness is also one of the systems the course takes apart, because each encodes a theory of control. Claude Code has the most extensive hook system, and for that reason gzkit renders seventeen hooks into it. Codex is AGENTS.md-native and sandboxed, and gzkit uses it as the cross-vendor adversary. Gemini CLI, Copilot, and OpenCode are the other options. On Route A, pick one primary harness; on Route B, use OpenCode or a similar harness with Ollama. Learn the others as well, because their control surfaces are the lecture material for E5 and E6.

slide 25

Orchestration framework choices: ADR-1 by Evolution 2

In E2 you commit to an orchestration layer in ADR-1, with alternatives and consequences, and you defend the choice in Drift. The table sets out the options. The Claude Agent SDK gives you the Claude Code harness as a library, with hooks and MCP built in, at the price of dependence on one vendor. The OpenAI Agents SDK makes handoffs, guardrails, and tracing first-class. Google's ADK is A2A-native. Pydantic AI treats validation as governance and runs on any provider, including a local Ollama endpoint. LangGraph makes the agent a state graph that you own edge by edge. "None" is also a legitimate choice: the reference design uses the standard library first on purpose, because every framework lets its authors' theory of control into your system. Popularity does not count as a rationale in ADR-1.

slide 26

Kit choices: governing the build

The kit governs the build. gzkit is the default: it is the reference design, I demonstrate it in every Evolution, and its CLI gives you the whole chain. The alternatives (spec-kit, OpenSpec, BMAD, GSD) are allowed. If you choose one, record the choice in your ADR, defend it, and supply whatever the covenant requires that the kit does not provide: gates, an evidence record, and attestation. The comparison document in the gzkit repository is the reading for this choice.

slide 27

The toolkit: install in E0

Install the toolkit in E0, before you pitch. Install Python 3.14 or newer through uv. Install gzkit as a uv tool. Initialize a fresh project in the Lite lane, so that you see what it scaffolds. Install Ollama with at least one model sized to your machine, on either route. Install your harness. The right-hand panel lists the rest, plus four problems I met when I onboarded a fresh project against the current release. First, gz init writes about five hundred files; commit them once. Second, the generated project needs a README before the gates pass. Third, exclude the generated directories from ruff and ty. Fourth, in Claude Code the pipeline hook refuses source edits until a pipeline is active, and that refusal is intended.

slide 28

Readings: no textbook, three streams

The course has no textbook. The reading comes from three streams. The first is primary sources: the vendor guides that defined the patterns, the papers that defined each generation, the MCP specification, and current system cards. The second is the reference design's own documents, one or two per Evolution, which give the inside view. The books at the bottom of the slide are optional, and none is required for purchase.

slide 29

The course repository

You keep one repository in the course organization. It contains a root README that tells a reader where everything is and which route and framework you chose; the AI log; a design-analyses folder with the running ledger; one folder per Evolution; the system itself in src and tests, one codebase that grows in every Evolution; the design folder the kit manages; the gzkit folder that gz init generates, committed once; a final folder for the brief, the runbook, the release notes, and the ceremony record; and a feedback folder that only I write into. Two rules apply. The work lives in the repository, not in links, and nothing sensitive is ever committed.

slide 30

AI: permitted with attribution, absent from Drift

The university gives faculty three postures on generative AI. This course takes "permitted with attribution," and you attribute through your AI log and through the governance artifacts that show you directed the work. Write one entry per Evolution: what you asked, what you got, what you kept, what you rejected, why, and how you verified it. The log is material for discussion in Drift, and I do not use it for surveillance. Three rules are fixed. Unattributed use is an integrity violation. "The model did that" is acceptable only if you can say why you accepted it. The failure modes you red-team your system against in E11 (fabrication, skipped verification, gaming the gate) are the same ones I watch for in your own work.

slide 31

Policies at a glance

The choice between Route A and Route B is yours. The AI log starts in E0, and no AI is used in Drift.

slide 32

Evolution 0
