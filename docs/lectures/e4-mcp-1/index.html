N×M becomes N+MThe combinatorial cost before the protocol

N hosts and M tools meant N×M adapters. A protocol makes each side implement one thing: N clients, M servers, N+M pieces of code.

Three promises a signature cannot make

Discovery: a client asks what a server offers before calling. Negotiation: client and server state versions and capabilities; a mismatch is an error. Transport independence: a pipe on your laptop, HTTP on a host you do not control. Your E3 tool had none of these.

The statement Sortie 4 will try to disprove

Every declared tool is discoverable, callable, and schema-validated from two independent clients; every call is logged server-side. If a tool works from the harness but not from the script, the harness did the protocol's work, and you have measured that work.

Hosts, clients, servers, and the three primitivesThe architecture, and the question of who controls each primitive

Host · Client · Server

Host: the application the human is in. Client: one connector per server, inside the host. Server: declares capabilities and answers requests over JSON-RPC 2.0.

The human sits in the host. The server never sees the human.

Tools

Functions the model may call: a name, a description, a JSON Schema for input. The model chooses; the host may gate the call.

Model-controlled. E3's contract, on the wire.

Resources

Data the server exposes by URI: files, records, a ledger. The application decides what enters context, and when.

Application-controlled. Content, not instructions (E5).

Prompts

Templates the server offers the user: a workflow with a name and arguments, surfaced as a slash command.

User-controlled. The human picks; the server proposes.

Extensions and tasks

An `extensions` field in both capability sets; long-running work moved to the tasks extension (`tasks/get`, `tasks/update`). Adopt an extension only when the core cannot express the need.

Negotiated on every request.

Deprecated in 2026-07-28

Roots, sampling, and logging: deprecated, twelve-month window. HTTP+SSE transport: deprecated; use Streamable HTTP.

Do not build a new server on a deprecated feature.

Building the server: declare, run, inspect, connect twiceFastMCP-style: the schema comes from the type hints; the transport is a flag

Declaration (Python SDK, FastMCP style)

from mcp.server.fastmcp import FastMCP
srv = FastMCP("e3-tools")

@srv.tool()
def read_note(path: str) -> str:
    """Read a note. Side effects: none."""
    log("call", "read_note", path)
    return NOTES.read(path)

@srv.resource("ledger://events")
def ledger() -> str:
    return LEDGER.tail(50)

srv.run(transport="stdio")  # HTTP later

The four steps of the lab, in order

1. Declare one E3 read tool: docstring as description, type hints as schema.

2. Run over stdio; the inspector confirms server/discover and tools/list.

3. Connect two clients: your harness and a twenty-line script.

4. Read the server log: two calls, two matching entries.

The description is the model's only view of the tool. Write it as a contract: what it does, what it must not do, side-effect class.

Teardown: ChatGPT plugins and OpenAPI-style tool specsDescription without negotiation: why the pre-protocol attempts stalled

ChatGPT plugins (March 2023)

A manifest, an OpenAPI document, a paragraph the model read. Vendor-hosted, one product, one store.

Right: a model could read a spec and call an endpoint. Lacked: other hosts, negotiation, local transport, content or prompts.

Control: the vendor owns discovery, hosting, and the loop.

OpenAPI-style tool specs (2023– )

Function calling, mid-2023: a JSON Schema per function, a structured call back; schemas generated from OpenAPI.

Right: schemas as contracts, in-process, any model. Lacked: discovery, negotiation, a second primitive. Each host wrote its own loader.

Control: you own loop and schema; nobody owns the boundary.

Where is the human?

In the host, and only in the host. The client must get the human's approval before a tool runs; the server never assumes it. The wire carries requests only; no message on it grants permission.

The protocol delegates governance to the host by design; E5 shows what happens when the host's trust is misplaced.

What a healthy protocol needs around it

A versioning and deprecation policy (twelve-month window). Independent SDKs (TypeScript, Python, Go, C#; Rust in beta). A server registry with provenance, or it is a supply chain (E5: SmartLoader). Governance that is not one vendor.

Read it as a Design Analysis

Problem: N×M. Decision: a client–server protocol over JSON-RPC, three server primitives, negotiated capabilities. Alternatives: a plugin store; per-vendor function calling; a library. Consequences: adoption across hosts; a new security surface. The human: outside the wire.

The doctrine and its reasoning

The verbs (gz status, gz validate, ledger, receipts) run on the standard library over files.

Why: attestation must not depend on availability. The ledger must be readable with cat. Same posture as ADR-0.0.2.

Campaign review: MCP 'absent and un-designed', but the refusal was written down.

What changes one tier up

The doctrine forbids prerequisites and allows presence. A server above the core adds a way in without adding a dependency.

The pool ADR sketches this tier. Falsifier: kill the server, run gz validate.

Reference design: the governance server as a student projectgz verbs as tools, the ledger as a resource, 'what is attested?' answered from the record

Tools (model-controlled)

gz_status(): the repo's governance state. gz_validate(scope): run the validators, return the report. Read-class only. Write verbs (gz attest, gz release) stay behind a host gate, as in E3.

Resources (application-controlled)

ledger://events?tail=N: the last N events. attest://<artifact>: what is attested for one artifact. receipts://<id>. The host decides when these enter context.

Prompts (user-controlled)

/what-is-attested: a template that reads the attestation resource and answers only from it. The answer is checkable against the resource it was given.

Chapter 13 exercise: ask your harness 'what is attested in this repo?' and check the answer against the ledger. An added attestation is summary laundering, and the server is the instrument to catch it.

MCP I: Building a Server

Evolution 4 takes the tool contract of Evolution 3, where the model was an untrusted caller, out of your process and puts it on a wire, so that any host can discover it. The question becomes what a protocol has to promise that a function signature does not. Three teardowns cover the plugin era that failed, the OpenAPI specs that described a tool without negotiating anything, and the protocol that won and then moved to a foundation. In the lab you serve your E3 tools over MCP, list them in the inspector, call them from your harness and from a script, and log each call at the server. The revision of the specification that went to general availability on July 28 changed the wire in ways your SDK may or may not already reflect, so the lecture teaches the current revision and states what changed.

N×M becomes N+M

Framing. The problem MCP answered was combinatorial. Before November 2024 each host and each tool wrote adapters for each other, and the field paid N times M. A protocol lets each side write one adapter and pay N plus M. A protocol then makes three promises that a function signature cannot: discovery, negotiation, and transport independence. Your E3 tool had a schema and a gate and none of these three, because nothing outside your process could ask it anything. The design claim for the sortie is that two independent clients and one server show identical behavior, with every call logged. One of the falsifiers is asymmetric: a tool that works from the harness and fails from the script means the harness was compensating for the protocol, and the sortie has measured the compensation.

Hosts, clients, servers, and the three primitives

The slide puts the architecture in one column and the primitives in the rest. The host is the application the human is in, each server gets one client inside the host, and client and server exchange JSON-RPC requests in both directions. The specification distinguishes the three primitives by who controls each one, and that distinction is the design analysis of the protocol. Tools are model-controlled; a tool is the E3 contract put on the wire. Resources are application-controlled: the host decides what enters context, and for this reason E5 treats a resource that carries an instruction as an attack. Prompts are user-controlled. Two more cards follow: extensions, with the tasks extension for long-running work, and the deprecation list from the July 28 revision. The deprecation list matters because tutorials written before that revision still teach roots and sampling. A new server should not adopt a feature the specification has scheduled for removal.

The wire after 2026-07-28: a stateless core

The revision that went to general availability on July 28 rewrote the wire, and the headline change is statelessness: there is no handshake and no session header, and every request carries its version and capabilities in its metadata. The changelog gives an infrastructure rationale: any request can land on any instance behind a round-robin balancer, because no instance has to remember anything between calls. The change that bites a server author is the third row. Roots, sampling, and elicitation were calls the server made back into the client; under the new revision a server that needs more input returns a result typed input_required, and the client retries the request with the answers attached. The fourth row is your first test point: server/discover is mandatory, and it is the inspector's first call. The last two rows cover subscriptions, which are now one stream, and list results, which must carry a TTL and a cache scope; put your tools in deterministic order and give an honest TTL. Check which revision your pinned Python SDK speaks before you build, because the SDKs shipped on the day of the revision and a version pinned earlier may not have it.

Building the server: declare, run, inspect, connect twice

This slide shows the server itself, in the shape the Python SDK gives you. FastMCP derives the input schema from the type hints and the description from the docstring, so the function you wrote in E3 becomes a server with one decorator. A resource is addressed by URI; here the URI returns the last fifty ledger events. The transport is a flag: stdio for this Evolution, Streamable HTTP when the host is not on your laptop. The four steps on the right are the lab in order. The third step carries the design claim, because two clients, one of them a script, leave the harness no way to hide protocol work from you. The strip at the bottom is the bridge to E5. The description is all the model sees, so write it as a contract; in E5 you will read tool descriptions that an adversary wrote.

Teardown: ChatGPT plugins and OpenAPI-style tool specs

Two teardowns follow, both from before the protocol. The plugin store of March 2023 offered description without negotiation, ran inside one product, and its vendor deprecated it within a year. Function calling and the OpenAPI-derived schemas were the correct idea in-process, and they are what your E3 tool is, but every host still wrote its own loader, so the combinatorial cost did not change. Read both by their theory of control, as E2 read the frameworks: in the plugin model the vendor owns discovery and the loop, and in the OpenAPI model you own the loop and nobody owns the boundary. MCP specified the boundary between host and server, which neither predecessor had specified.

MCP as a system: where is the human?

The third teardown reads MCP itself as a system, on the board as a Design Analysis. The timeline runs down the left and ends at the foundation and the GA revision, so that the protocol's own governance apparatus is visible: a deprecation policy with a twelve-month window and an enhancement-proposal process. The question the course asks of every system is where the human is, and here the answer is precise: in the host, and only in the host. The wire carries requests only, and no message on it grants permission. That design choice has a consequence, and E5 covers the consequence. Two more cards follow: what a protocol needs around it, where a registry without provenance counts as a supply chain, and the analysis in the template's five fields.

Reference design: why gzkit refused MCP

The reference design refused the protocol this Evolution teaches. Its storage-tiers doctrine states that no external protocol may be a prerequisite for a core governance operation. A kit whose job is to be trusted keeps the smallest dependency surface, which is the same posture gzkit took in ADR-0.0.2 when it chose argparse over click. The campaign review nevertheless scored MCP as absent and un-designed, and the review held the refusal the honest way: written down, with its alternatives, and open to reversal. The reversal is on the right. A server one tier up exposes the verbs and the ledger without becoming a prerequisite, and the falsifier for the tier boundary is a two-step test: kill the server, then run gz validate. If gz validate fails, the server became a prerequisite and the doctrine no longer holds.

Reference design: the governance server as a student project

This slide lays out the project that reverses the refusal one tier up, by primitive, so that the three kinds of control are visible. The tools are the read-class verbs; the write verbs stay behind a host gate, as in E3. The resources are the ledger and the attestation record, addressed by URI, and they enter context only when the host decides. The one prompt asks the question the ledger can answer. The strip holds the exercise from chapter 13, and the exercise is also the first instrument this course has given you against summary laundering: you can now diff the model's answer to 'what is attested?' against the resource the model was handed.

Evaluation lens: a strong Sortie 4

A weak Sortie 4 shows one harness pretending to be two clients, a client silently repairing arguments, a log that is a narrative, a write tool on the wire with no gate, and a server built on a deprecated feature because the tutorial was from 2025. A sound Sortie 4 shows discovery and listing captured from the inspector, two independent clients with identical logged calls, a server-side log with the four fields, the write tool held back with the reason written down, and the SDK and protocol revision on the SUBSTRATE line. An exceptional Sortie 4 adds a third client with a divergence explained, a deliberately wrong schema that the server rejects, cache fields honored, the governance server with the attestation diff, and a debrief that states what the protocol forced you to write.

Flight Card 4 brief: one server, two clients

Flight Card 4 sits at the center of the envelope and depends on Sortie 3, because the write gate must already hold before anything goes on the wire. The card has four test points: discovery, a call from the harness, the same call from a script, and a bad call the server must reject. The abort criterion is the one that is new this term: an SDK and protocol revision mismatch that prevents discovery is an infrastructure failure rather than a refuted design claim, so it halts the sortie instead of failing it. Record the revision on the SUBSTRATE line so that the Chase can tell the two apart.

A protocol is a contract that strangers can discover, negotiate, and reach over any transport.

Close. A protocol adds three things to the E3 tool: a stranger can discover what it offers, negotiate a version and capabilities with it, and reach it over a pipe or over HTTP. Sortie 4 requires that every call from both clients appear in the log the server keeps.
