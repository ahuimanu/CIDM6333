slide 03

Memory is the part of context that survives

Framing. The window you budgeted in Evolution 6 is gone when the session ends; memory is the part of it you chose to keep. Two rules govern the whole lecture. First, a memory is a claim with a source. The record says where the item came from, when it was written, and who wrote it; a record without those fields is a rumor, and the agent repeats a rumor with the same confidence it gives a fact. Second, retrieved text is data, never instruction. This is the E5 rule applied to your own store, since a memory is content that some earlier session, or some attacker, wrote. The design claim for Sortie 7 comes from chapter 16. It has two halves, recall and forgetting, and three falsifiers: a fact that was never stored, an item kept past its rule, and retrieval that changes an answer it had no business changing.

The slide's wording in full
  • A memory that survives the session can be wrong in a later session, and no reader can detect the error unless the record states where it came from
  • Memory is the part of context that survives the session. Anything that survives can be stale, planted, or never true, and the model reads it as fact on every later turn.
  • A memory is a claim with a source. Every stored item carries where it came from, when, and who wrote it. No reader can check a record without provenance, and the agent still repeats it as fact. / Retrieved text is data, never instruction. E5's rule applies to your own store. Some earlier session, or some attacker, wrote any memory that says 'always do X', so the agent reads it as content and does not obey it.
  • With memory on, the system answers a question about a prior session correctly that it cannot answer with memory off, and eviction removes exactly what the retention rule says it removes. A recalled fact that was never stored, an item retained past its rule, or retrieval that changes an answer that should not change falsifies this statement.
slide 04

Five kinds of memory, and where each lives

Chapter 16 distinguishes five kinds of memory, and the sixth card on the slide is the question ADR-2 answers. The window is short-term memory, and the harness owns it. Working state is typed. If your loop keeps its current goal in a paragraph of prose, the loop cannot validate the goal, compare it with the last one, or test it, so the paragraph does not count as state. Episodic memory is what happened, append-only and dated. Semantic memory is what is known; because facts change, every update must record what it replaces. Procedural memory is skills and recipes, and it changes by review rather than by the agent alone. A course system produces sortie outcomes, which are episodic, and a few user and project facts, which are semantic, so episodic plus a small semantic store is the shape to justify first in ADR-2. Write the kinds down before you build; the choice of store follows from them.

The slide's wording in full
  • Identify the kind before you pick the store; each kind has a different writer and a different clock
  • What the model sees this turn: instructions, history, tool results, retrieved text. Writer: the harness. Clock: the session. E6 budgeted it.
  • Typed fields the loop reads and writes: goal, current step, open approvals, budget left. A Pydantic object or a row, not prose. Clock: the task.
  • What happened: turns, tool calls, sortie outcomes, corrections. Append-only and dated. Reflexion's buffer and Generative Agents' stream are episodic.
  • What is known: facts about the user, the project, the domain. Mutable, so each change must identify the record it supersedes. RAG's Wikipedia index is semantic.
  • How to do things: skills, prompts, tool recipes. Voyager's skill library, Claude Code skills, your AGENTS.md. A reviewer approves each change; the agent does not change it alone.
  • Plan for episodic memory (sortie outcomes, decisions) and a small semantic store (user and project facts) unless your system needs another kind. Record the choice in ADR-2 before you build a store.
slide 05

A memory is a claim with a source

The record is where the first rule becomes code. The left panel lists four operations, and each one leaves a ledger event: write, store, read, and evict or forget. The right panel shows the record the lab uses. It carries an id that is never reused, the kind, the source file, the date, the writer, a retain-until date, a supersedes field, and the text. The store and the ledger answer different questions. The store says what is remembered now; the ledger says what was remembered on any given date, and that second question is the one an auditor asks. The strip at the bottom states the Chase's test. A recalled sentence that traces to no record and no source file is a fabrication (App. C #3) even when it happens to be true, because nothing in the system can show how it got there.

The slide's wording in full
  • A memory record is a claim with a source
  • Write. Who decides to store: the user ('remember this'), the agent (auto memory), or a rule (every sortie verdict). Every write is a ledger event. / Store. One record per chunk, with provenance. Append-only where you can; ids never reused. / Read. Retrieval returns ids and scores; the block injected into the prompt cites the ids. / Evict and forget. Eviction follows a rule; forgetting follows a request. Each leaves a ledger event, so the store has no unexplained gap.
  • If the Chase cannot trace a recalled sentence to a record, and the record to a source file, the recall is a fabrication (App. C #3), whether or not it happens to be true.
slide 06

Retrieval: chunk, represent, store, score, inject

Retrieval has five steps, and each is an ADR-2 decision. Chunking comes first, with a finding from the build of the lab tool. When the chunks lost their headings, the question about the Sortie 5 verdict returned the Sortie 3 verdict, because both chunks said 'Chase verdict' and neither said which sortie. The fix was to keep the heading with each chunk. Represent: term counts or embedding vectors, with the same model used to index and to query. Store: a JSONL file holds hundreds of records, which is enough at course scale. Score: cosine similarity, a small k, and a threshold, so that 'nothing found' is a possible answer. Inject: a marked block that the model is told to cite. The strip covers the case where retrieval makes answers worse (an irrelevant hit crowds the window, a stale hit outranks the fresh one, or a planted record reads as instruction). A run with memory off is the control that shows which of these happened.

The slide's wording in full
  • Split by paragraph or section. Keep the heading with each chunk. Without it, 'Chase verdict: FAIL' does not say which sortie, and the lab's first test returned the wrong one.
  • Bag-of-words (term counts weighted by rarity) or an embedding vector from a local model. Index and query with the same model.
  • memory.jsonl, with vectors cached beside the text in the sortie. A JSONL file holds hundreds of records; the need for a vector database depends on scale, and the memory design does not require one.
  • A marked block: id, source, date, text. The model is told to cite the id it used. The block is data.
  • Retrieval hurts when an irrelevant hit crowds the window, a stale hit outranks the fresh one, or a planted record reads as instruction. A memory-off run on the same question shows which of these failures occurred.

Two retrievers for the lab

Two retrievers, both in the lab's single file. Path B is bag-of-words: the script tokenizes the text, drops stopwords, weights rare terms up, and compares question and chunk by cosine. It needs nothing but the standard library. It is strong on exact identifiers, which is what a flight log is built from (model tags, record ids, file paths, commands), and it fails on synonyms. Path A calls Ollama's embed endpoint with embeddinggemma. The vectors come back at unit length, so the dot product is the cosine. Path A handles paraphrase, costs a model download, and produces numbers that no reader can audit, so the Chase audits the text and the id in every case. I checked the OpenCode Go and Zen documentation on September 24: neither offers an embeddings endpoint, so the course harness provides no hosted route, and no one needs another API key for this Evolution.

The slide's wording in full
  • OpenCode Go and OpenCode Zen publish no embeddings endpoint, so the course harness offers no hosted path. The retriever runs on your laptop either way.

slide 10

State and eviction

State first. Working state is a typed object the loop owns; the model proposes a change and the loop validates it before writing, which is the same contract your tools followed in E3. Three eviction policies follow. MemGPT evicts by pressure: the harness warns the model at about seventy percent of the window and, at a hundred, flushes half the queue into a recursive summary. Retention evicts by rule: every record carries a date, and a command removes the records past their date and logs each id. Generative Agents evicts by relevance, which means nothing is ever deleted; old, low-scoring memories stop surfacing, and nobody can prove one is gone. Only the rule path yields a test the Chase can check (an id with an evict event, absent from the store, and no longer recalled), so the rule path is the one Sortie 7 flies.

The slide's wording in full
  • A typed object the loop owns: goal, step, open approvals, budget left, last verdict. The model proposes a change; the loop validates it and writes it. A prose summary does not count as state, because the loop cannot validate it.
  • At about 70% of the window, a memory-pressure warning lets the model save what matters. At 100%, about half the messages are evicted into a recursive summary. The summary loses detail by design.
  • retain_until on every record; evict removes past-date records and logs each id. The rule is deterministic and testable, so an auditor can verify each eviction.
  • Nothing is deleted. Old, unimportant memories score low and stop surfacing. Decay is cheap to build, but no test can prove that a memory is gone.
  • Sortie 7 flies the rule path: the Chase checks that each evicted id has a ledger event and is absent from the store, and that a question about it now fails.
slide 11

Retention as governance

A retention rule is where memory becomes a governance question, because each of its four answers assigns a right or a duty to someone. Who may write a memory? The answerable version lists the permitted writers (a user request, a rule, or the agent with a ledger event) and records on each item which one wrote it. How long is it kept? The answer is a clock per kind rather than 'until the store is full'. Who can delete it, and how is deletion proved? A forget command with a reason, a ledger event, and a recall test that now fails. Where did it come from? A source path and a date on the record and in the injected block. The strip shows a vendor meeting the same question. Claude's help pages state that deleting a conversation does not delete the memories generated from it. In other words, deletion of a derived store is a separate operation from deletion of its source, and your system needs that operation.

The slide's wording in full
  • Permitted writers: a user request, a rule (every sortie verdict), or the agent with a ledger event. Each record carries written_by.
  • forget <id> --reason writes a ledger event; a recall test shows the id no longer returns.
  • Source path and date on the record and in the injected block; the answer cites the id.
  • A user who deletes the source does not delete the memory. Claude's help center says this of its own memory: entries generated from a deleted chat remain until you delete them individually.
slide 12

How to measure memory: the on/off protocol

The on/off protocol is how you test the design claim. It uses four kinds of question. A recall question asks for a fact from a prior session, which is the case the design claim covers. A paraphrase question asks for the same fact in other words and tests the retriever choice. A control question is one that memory has no business changing, and it serves the falsifier 'retrieval changes an answer that should not change'. An absent question asks for a fact never stored, and it is the fabrication check. The right panel gives the discipline: a fresh session for every run, the same model id both times, every tool denied so the model cannot read your flight log and make the memory-off run look like the memory-on run, and nothing changed between runs except the memory block. You check each answer against the source file. If Big Pickle or a flash model gets the control wrong, that is a finding for the flight log; you record it, and you do not swap models to make the numbers look better.

The slide's wording in full
  • Recall. The answer is in a prior session (the model tag in Sortie 3). Memory on must be right; memory off must fail or say it does not know. / Paraphrase. The same fact in other words. This separates bag-of-words from embeddings. / Control. A question whose answer memory must not change (a fact stated in the prompt, or plain arithmetic). The answer must be identical on and off. / Absent. A fact never stored. Memory on must say 'not in memory'; a confident answer is a fabrication.
  • a fresh session for every run (opencode run starts one) / the same model id both times; record it / every tool denied, so the model cannot read the repository and contaminate the memory-off run / the memory block pasted or omitted, nothing else changed / answers saved verbatim, then checked against the source file, not against the model's confidence
  • A small free model will get some of these wrong. Record the wrong answers in the flight log, and keep the same model for the whole sortie.
slide 13

Common mistake: a stale fact recalled with confidence

The common mistake. Chapter 16 calls memory a vibing surface, by which it means a stale fact recalled as if it were current truth. The worked case is ordinary. Your Sortie 2 log records a test command; in E4 you changed it and fixed AGENTS.md, but the Sortie 2 record is still in the store. Retrieval finds the old record on an exact term, the agent runs the old command, sees that no tests ran, and reports the gate as passed. Nothing in the answer shows the age of the fact. Three fixes follow. A supersedes field lets the correction replace the original. Dates in the injected block make the age of each recall visible. The authority order from E6 ranks the repository file above the memory of that file. The failure mode is App. C #4, skipped cheap verification, since the agent trusted a recalled command instead of reading the current file. When an attacker plants the stale fact on purpose, OWASP's December 2025 list for agentic applications calls it ASI06, memory and context poisoning.

The slide's wording in full
  • Your Sortie 2 log says 'tests: uv run pytest -q'. In E4 you moved to unittest and fixed AGENTS.md. The store still holds the Sortie 2 record. / In this Evolution the agent retrieves it (exact match on 'tests'), runs pytest, sees 'no tests ran', and reports the gate as passed. Nothing in the answer says the fact is five weeks old or that a newer file disagrees.
  • Supersedes. A new record identifies the one it replaces; retrieval drops superseded ids. / Dates in the block. The model and the reader both see the age of what was recalled. / Authority order. The file in the repository beats the memory of the file. In E6 terms a memory is derived (L3); L2 > L1 > L3. / A falsifier on the card: retrieval changes an answer that should not change.
  • App. C #4, skipped cheap verification: the agent trusted a recalled command instead of reading the current file. OWASP's agentic top 10 (Dec 2025) lists the adversarial version as ASI06, memory and context poisoning.

slide 16

Teardown: RAG (Lewis et al., 2020)

RAG, read for its mechanism. The design has two memories: the weights of a BART generator, and an index of twenty-one million hundred-word Wikipedia chunks that a trained retriever searches by inner product. The design choice is that knowledge lives outside the weights, and the paper's index-swap experiment shows what that buys. With the 2016 index, the model answered seventy percent of questions about 2016 world leaders correctly; asked about 2018 leaders from the same 2016 index, it answered four percent. That is a retention result from 2020: the index held stale facts, and the stale facts were replaceable. The cost is a retriever to train and an index to keep fresh. The failure mode is fabrication (App. C #3), because the generator is free to answer beyond its passages; retrieval gives provenance only when the answer cites what it used.

The slide's wording in full
  • A BART-large generator (406M parameters) conditioned on passages that a DPR retriever finds in a dense index of the December 2018 Wikipedia dump: 21M chunks of 100 words, searched by maximum inner product (FAISS). / RAG-Sequence uses the same passages for the whole answer; RAG-Token can draw on a different passage for each token. NeurIPS 2020.
  • Choice. Knowledge lives outside the weights, so it can be replaced. The authors swapped indexes: with the 2016 index, 70% of 2016 world-leader questions right; with the 2016 index on 2018 leaders, 4%. / Cost. A retriever to train and an index to keep fresh. / Failure mode. The generator can still answer beyond its passages (App. C #3, fabrication). Retrieval gives provenance only if the answer cites what it used.
  • For your system, the index swap is the argument for retention. You can correct a store by replacing its records, and you cannot correct a fact inside model weights in the same way.
slide 17

Teardown: Generative Agents (Park et al., 2023)

Generative Agents. The mechanism is the memory stream and a retrieval score that adds three terms with equal weight: recency, importance, and relevance. Importance is the model's rating of each memory from one to ten, which costs a model call per observation. The design choice is reflection. When the importance of recent events sums past a threshold, the agent asks itself questions and stores the answers as higher-level memories that cite the observations behind them. The paper reports its own failures, and they are the two you will meet: a fact that was in memory and was not retrieved (Rajiv had 'not followed the election'), and a memory embellished with world knowledge (a neighbor whose name is Adam Smith 'authored Wealth of Nations'). The second is fabrication, App. C #3. The strip connects to E9: a reflection that carries no pointers to its evidence is a summary nobody can check.

The slide's wording in full
  • A list of memory objects, each with a description, a creation time, and a last-access time. Retrieval score = recency + importance + relevance, all weights 1. Recency decays by 0.995 per game hour since last access; importance is the model's 1–10 rating.
  • When the importance of recent events sums past 150, the agent asks itself questions and stores the answers as higher-level memories that cite their sources. Klaus picks a research partner from his reflections rather than from the count of his meetings.
  • Model calls to rate every observation and to reflect. The paper's own evaluation: agents failed to retrieve (Rajiv had 'not followed the election') and embellished (Yuriko's neighbor Adam Smith 'authored Wealth of Nations'). App. C #3.
  • Reflection is memory the model writes about itself. Store each reflection with pointers to its evidence. Without the pointers, the agent treats its own summary as evidence (summary laundering inside one agent).
slide 18

Teardown: MemGPT to Letta (2023–2026)

MemGPT to Letta in four steps. The 2023 paper splits the prompt into a read-only system part, a small working block the model edits by function call, and a message queue, with recall and archival stores outside the window. The pager warns the model at about seventy percent of the window and, at a hundred, flushes half the queue into a recursive summary. In September 2024 the project became Letta, and the authors asked that 'MemGPT' refer to the pattern and 'Letta' to the company and framework. The step that matters for this course came in February 2026, when Letta Code moved memory into files in a git repository, with each change a commit. The reference design started from the same substrate, as the reference-design section shows. The failure mode follows from the model owning its own memory: a wrong fact in the working block is read on every turn, and a correction the model does not save is lost (App. C #5).

The slide's wording in full
  • Main context: system instructions (read-only), working context (a fixed block the model edits only by function call), and a FIFO message queue. External: recall storage (all messages) and archival storage.
  • A memory-pressure warning at about 70% of the window; at 100%, about half the queue is evicted into a recursive summary. The model moves facts with function calls; interrupts return control.
  • 'MemGPT' becomes the name of the design pattern; Letta is the company and the framework (package letta). Memory blocks with labels such as 'human' and 'persona'.
  • Letta Code keeps agent memory as files in a git-backed filesystem. Each change is a commit; subagents merge memory through git; background skills reflect and defragment.
  • Three years from custom memory functions to files and commits. Failure mode: the model edits its own working context, so a wrong fact written once is read on every turn, and a correction the model does not save is lost (App. C #5).

Teardown: Reflexion (Shinn et al., 2023)

Reflexion, in the authors' own sentence. The design has three roles (an Actor, an Evaluator, and a Self-Reflection model) and a small episodic memory of one to three lessons written in words. The headline result is ninety-one percent pass@1 on HumanEval against the eighty percent reported for GPT-4 at the time. The part to read closely is the evaluator. On MBPP, 16.3 percent of those self-written tests passed wrong code, and Reflexion did worse on MBPP than on HumanEval. The memory is therefore a memory of whatever the evaluator called a failure, and it is only as reliable as that evaluator. This is App.

Teardown: assistant memory features, 2025–2026

Four shipping memory systems, read for the four retention questions. ChatGPT stores saved memories and chat history, written by you or by the model, and since May 2026 shows memory sources, which is provenance made visible to the user; logs of deleted memories are kept for up to thirty days. Claude made memory free in March 2026, keeps a separate memory per project, and documents that deleting a chat does not delete the memories generated from it. Claude Code is the system closest to your build: plain Markdown files that the agent writes per repository, with the first two hundred lines loaded each session, and excluded from the transcript cleanup sweep. The strip is the security case. In 2024 Johann Rehberger showed that a web page could write instructions into ChatGPT's memory, and the memory then carried the attack into every later session; memory makes one injection permanent. Reference design: memory in the layers of truth

Memory has a place in the layers of truth from E6. Canon (L1) is what you authored. The ledger (L2) is what happened. Derived (L3) is everything computed from the other two, and a memory store is derived, because it is built from your logs and files. For this reason the store can never block a gate and never outvote the file it came from; when the two disagree, the file wins and the memory record is superseded. The ledger beside the store makes the store auditable, since it says what the store held on any date. That is the Sortie 7 default. If you want a memory to be canon for some fact, ADR-2 has to argue the case.
