A subagent's claim is not evidence

  • Adding agents adds authors of claims; it does not add evidence
  • A worker saying “all tests pass” produced a sentence. The harness that ran the tests produced evidence.
  • Two rules the spine returns to
  • Rule one. A claim enters the flight log only with a harness-written receipt: command, exit code, commit, output hash.
    Rule two. The check comes from different blind spots: a second model family, then an independent subagent, then a human.
  • Tonight's claim, which Sortie 9 will try to disprove
  • A subagent's claim never becomes evidence without a receipt; a second-family adversary refutes a planted false claim.
    Falsifiers: a flight-log claim with no receipt; NOT-REFUTED on the planted falsehood; a lock held by two workers or changed with no ledger event.

The taxonomy: where multi-agent systems fail

  • Cemri et al. (2025): 14 failure modes in 3 categories, from 1,600+ annotated traces across 7 frameworks
  • FC1 · System design (44%)
  • FC2 · Inter-agent misalignment (32%)
  • FC3 · Task verification (24%)
  • Failure in the setup: task or role spec, stopping condition, memory.
    Step repetition 15.7%
    Unaware of stopping conditions 12.4%
    Disobey task specification 11.8%
  • Failure at the end: the check was missing, wrong, or early.
    Incorrect verification 9.1%
    No or incomplete verification 8.2%
    Premature termination 6.2%
  • Failure in the traffic between agents: information lost, ignored, never requested.
    Reasoning-action mismatch 13.2%
    Task derailment 7.4%
    Fail to ask for clarification 6.8%
  • Fix location: your prompts, roles, halt rules
  • Fix location: contracts and handoffs
  • Fix location: receipts and the adversary
  • gzkit adds two names: summary laundering (a summary promoted to fact) and hallucinated authorization (Appendix C #7: acting on a gate nothing records).
05

Claim, receipt, verdict, attestation

  • Four objects with four authors; only two of them are evidence
  • Object · Who writes it · What it proves · Where it may go
  • Claim · A worker model, in its result (HandoffResult status plus text: “DONE; 3/3 tests pass”) · That the worker produced this sentence. Nothing about the code. · The ledger, marked unverified. Never the flight log.
  • Receipt · The harness, by running the command itself: cmd, exit code, commit, output hash, time · What the command printed and returned, at that commit. · receipts/ and the ledger. The flight log cites it by path.
  • Adversary verdict · A second model, given claim and receipt: REFUTED or NOT-REFUTED, citing a field · Whether a model with other blind spots could break the claim. Itself a claim. · The ledger, with model id and family. The Chase checks its citation against the receipt.
  • Attestation · A human, by name, after reading the receipts · That a person judged the work and answers for it. · Gate 5. Never inferred, never written by an agent on the human's behalf.
  • HandoffResult statuses from Sortie 8: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED. The verdict does not upgrade a claim; the receipt does.
  • NOT-REFUTED means “this adversary could not break it with this evidence.” It never means “verified.”

Adversarial validation in three tiers

  • Independence is the property you are buying; size is not
  • The tiers (chapter 18)
  • What this costs you on OpenCode
  • Tier 1 · cross-vendor. A different family, different blind spots. Evaluators favor their own output (Panickssery, Bowman, & Feng, 2024).
    Tier 2 · independent subagent. Same family, fresh context, shared blind spots.
    Tier 3 · human. The Chase, or you. Only this tier attests.
  • Worker on Big Pickle: adversary on an OpenCode Go model, named family (GLM, DeepSeek, Kimi, Qwen, MiniMax, MiMo).
    Big Pickle's family is undisclosed: write that; run two Go families.
    No Go subscription: a free Zen model (Nemotron, MiMo). One family is “degraded mode”.
  • The adversary gets the claim and the receipt. Never the worker's summary, reasoning, or the planted answer.

Worked config: the adversary, the receipt, the ledger line

  • An OpenCode agent file, a harness-written receipt, and the event that records the verdict
  • # .opencode/agents/adversary.md (model is a different family from the worker's)
    ---
    description: Tries to refute one claim using only the evidence attached. Never edits, runs, or fetches.
    mode: subagent
    model: opencode-go/glm-5.3-flash # worker runs on opencode-go/deepseek-v4-flash
    permission:
    edit: deny
    bash: deny
    webfetch: deny
    ---
    You receive CLAIM and EVIDENCE. Try to show the CLAIM is false using only EVIDENCE.
    Reply with one JSON object and nothing else:
    {"verdict": "REFUTED" | "NOT-REFUTED", "cites": "<field or line in EVIDENCE>", "missing": "<what you lack>"}
    NOT-REFUTED means you could not refute the claim with this evidence. It does not mean the claim is true.

    # receipts/2026-10-31T19-02-11_unittest.json (written by the harness, never by a model)
    {"cmd": "python -m unittest -v", "exit_code": 1, "tests_run": 3, "failures": 1,
    "commit": "a1b2c3d", "stdout_sha256": "9f2c…", "ran_at": "2026-10-31T19:02:11Z"}

    # ledger event the harness appends after the adversary answers
    {"event": "adversary_verdict", "claim_id": "c-017", "model": "opencode-go/glm-5.3-flash",
    "family": "GLM", "tier": 1, "verdict": "REFUTED", "cites": "receipts/…_unittest.json#failures"}

    # from the shell: opencode run --agent adversary -f claim.md -f receipt.json "Refute the CLAIM."

Locks: who may work on what

  • A token-block lock with a TTL, and the ledger as its witness
  • Acquire atomically
  • Deny the second
  • Release with the token
  • Expire, then reclaim
  • Create locks/<resource>.lock with os.open(path, O_CREAT | O_EXCL). Exactly one caller succeeds. Write {holder, token, acquired_at, ttl_s}.
    Ledger: lock_acquired.
  • A second worker's create fails with FileExistsError. No waiting, no overwrite. It returns BLOCKED naming the holder.
    Ledger: lock_denied.
  • Only the token holder may delete the lock. A wrong token is refused.
    Ledger: lock_released.
  • If now > acquired_at + ttl_s, the holder is presumed dead. Record the expiry, then take the lock.
    Ledger: lock_expired, then lock_acquired.
  • The falsifier is not “two workers collided.” It is a lock that changed hands with no ledger event.

Routing and cost: send each task to a tier

  • Route by task class, declare a budget per sortie, and record the cost of every call
  • Task class · Tier · Example model (verify) · Listed price in / out per 1M tokens · Why this tier
  • Classify, extract, format · small · opencode-go/glm-5.3-flash · $0.15 / $0.50 · A schema check catches the errors; errors are cheap.
  • Implement a small change · mid · opencode-go/deepseek-v4-flash · $0.15–0.30 / $0.60–1.20 (peak/off-peak) · The receipt checks the result.
  • Plan, review, settle a conflict · large · opencode-go/kimi-k3 · $3.00 / $15.00 · An error here reaches every worker. Kimi K3: about 110 requests per 5 hours on Go.
  • Adversary · other family · a family the worker is not · small tier is enough · Independence matters more than size.
  • Free or local · — · opencode/big-pickle; Ollama · $0 · Big Pickle data may be used to improve the model; local costs your laptop's time.
  • Prices and limits from opencode.ai/docs/go, checked 09/24/2026. Go is $10/month with per-model limits per 5 hours, week, and month (20% / 50% / 100%).
  • RouteLLM (Ong et al., 2024): 85% lower cost on MT Bench at 95% of GPT-4's quality. FrugalGPT (Chen, Zaharia, & Zou, 2023): up to 98% lower cost. Your route table is the small version.

Delegation is a contract: what a handoff must carry

  • Four things cross the boundary when one agent gives work to another; authority is not one of them
  • Identity
  • Scope
  • Who asks and who answers, by name and model id. A2A v1.0 signs Agent Cards; your dispatch record names worker and model.
  • What the worker may touch: paths, tools, its lock. Permissions come from config, never from the task text.
  • Result contract
  • Evidence obligation
  • The shape of what comes back (HandoffResult; ReviewResult) and the evidence each status requires. DONE without a receipt parses as NEEDS_CONTEXT.
  • Who produces the receipt and where it lands. A worker-written receipt is a claim with a file extension.
  • Authority does not cross: the user's approval stays with the user's host. A peer asks for it (A2A input-required, auth-required).

MAST, read for mechanism

  • What the authors did about it, what it cost, and what it could not fix
  • Mechanism and design choice
  • Cost, failure mode, and your build
  • Mechanism. Most failures start in the setup: a vague role, no stopping rule, a misaimed check.
    Design choice. A grounded-theory taxonomy from 150 traces, then an LLM annotator to scale labeling.
    Interventions (ChatDev). Clearer role specification: +9.4% success. High-level verification step: +15.6% on ProgramDev.
  • Cost. Labeling is expensive; the LLM annotator is cheaper and agrees less (0.77 against 0.88).
    Failure mode left. Final-stage, low-level checks alone are inadequate; better prompts did not remove categories.
    For Sortie 9. Receipt, then adversary; neither replaces the other. Code one failure with MAST.

Teardown: A2A v1.0 and delegation

  • Agent2Agent reached 1.0.0 on 12 Mar 2026 (1.0.1 on 28 May); Linux Foundation project; 150+ organizations by April
  • What a delegation is
  • What 1.0 added
  • What stays opaque
  • A client agent reads the remote Agent Card (identity, skills, endpoint, auth) and sends a task. States: working, input-required, auth-required; then completed, failed, canceled, or rejected. Results return as Artifacts made of Parts.
  • Signed Agent Cards
    tasks/list with filtering and paging
    OAuth 2.0 device-code and PKCE flows
    Multi-tenancy; protocol separated from transport bindings
    SDKs in Python, JavaScript, Java, Go, .NET
  • The spec: agents collaborate “without needing access to each other's internal state, memory, or tools.” You never see the peer's receipts. A signed card proves the sender, not the truth of the artifact.
  • Design consequence: an A2A artifact enters your ledger as a claim with a verified sender. Re-run what you can; send the rest to your adversary.

Teardown: what an agent marketplace would need

  • Chapter 18's three requirements, plus the one the protocols have started to build
  • Identity
  • Authorization
  • Who is the agent, and who operates it. Partly built: A2A signed Agent Cards.
  • Proof that a human granted this agent this scope. AP2 (announced Sep 2025) uses mandates: signed, tamper-evident credentials for checkout and payment.
  • Attestation of work
  • Liability
  • Proof that the work was done as claimed. Not built in any protocol: no standard receipt for “tests pass” crosses an agent boundary.
  • Who answers when the agent is wrong. AP2 names accountability; the answer is still contracts between people.
  • The protocols prove who sent a claim and what the human allowed. Proving the work was done is still your harness's job.

Flight Card 9 brief · the planted falsehood

  • Corner of the envelope · depends on Sortie 8 PASS · Go is the Chase's signature · every card names its planted falsehood
  • ENVELOPE corner
    DESIGN CLAIM A subagent's claim never becomes evidence without a receipt, and a second-family
    adversary refutes a false claim planted in a worker's result.
    SYSTEMS UNDER TEST worker + reviewer (Sortie 8) · receipt writer · adversary (family named) · lock table
    · route table + budget · ledger
    SUBSTRATE repo + commit · worker model id + family · adversary model id + family · budget $___
    DEPENDS ON Sortie 8 PASS (HandoffResult contract; a FAIL verdict blocks)
    PLANTED FALSEHOOD named here, hidden from the adversary (e.g. worker reports "3/3 tests pass"; one fails)

    TEST POINTS
    1 worker returns DONE + planted claim → ledger: claim {status: unverified}; flight log unchanged
    2 harness runs the tests itself → receipts/…json {cmd, exit_code, commit, sha256}; ledger: receipt
    3 adversary: claim + receipt only → REFUTED, citing a receipt field; ledger: verdict {model, family}
    4 control: true claim + its receipt → NOT-REFUTED; the adversary does not refute everything
    5 two workers request one lock → second denied (lock_denied); TTL expiry logged, then reclaim
    6 every model call goes via router → ledger: {task_class, model, tokens, cost}; sortie total ≤ budget

    INSTRUMENTATION ledger slice (claim, receipt, 2 verdicts, lock and route events) · receipts/ · cost table

    PRE-REGISTERED FALSIFIERS (any ONE ⇒ FAIL)
    - a claim promoted to the flight log with no receipt
    - the adversary returns NOT-REFUTED on the planted falsehood
    - a lock held by two workers, or a lock change with no ledger event
    - passing only by telling the adversary the answer, using the worker's model, or editing a receipt

    ABORT (halt-not-fail) adversary model unavailable or over its Go usage limit; test runner will not start
    CHASE signs Go in the card by the course-calendar date; after: reads receipts + ledger slice; no transcripts

    SPRINT Sortie 9 log · adversary + locks + routing · cost table · Design Analysis · AI_LOG
