slide 03

A loop without a halt is a bill

Start with the lesson, not the history. Autonomy without a stop condition is not a feature; it is a bill, and an open question about who is responsible. Connect to last week: the model has no state, no ground truth, no accountability. The loop is the first thing we wrap around it, and unless we design against those gaps the loop inherits them. A budget is the first piece of state. An observation is the first piece of ground truth. A ledger is the first piece of accountability. Then read the claim for the week aloud, because it is the shape every claim will take: one sentence, three falsifiers. [~8 min]

The slide's wording in full
  • Autonomy without a stop condition is not a feature. It is an open account with the model provider and an open question about who is responsible for what it did.
  • A language model has no persistent state, no ground truth, and no accountability. The loop is the first structure we put around it, and the loop inherits all three gaps unless we design them out: a budget (state), an observation (ground truth), a ledger (accountability).
  • Tonight's claim, which Sortie 1 will try to disprove / The loop halts on every input class — answerable, unanswerable, adversarial — within budget, and every turn is in the ledger. If a single run exceeds the turn budget, halts with no ledger event, or produces a 'final answer' without a reasoning turn, the claim is false.
slide 04

From prompting to programs (2020–2022)

Four steps in two years. Few-shot prompting: the prompt is data. Chain-of-thought: reasoning becomes something the model emits, and you can read it; latent planning shows up. Self-consistency: sample several chains and vote, which is the first evaluator and the first time cost multiplies. ReAct: interleave reasoning with actions and observations, and now the prompt is a loop body. The point for builders: chain-of-thought plans without commitment. ReAct adds the observation, so each reasoning step has a piece of ground truth in it. That one addition is the difference between a generative system and an agent. [~5 min]

The slide's wording in full
  • Chain-of-thought is planning without commitment: the model reasons, then answers, and nothing checks the reasoning against the world. / / ReAct adds the observation. After each action the environment answers back, and the next reasoning step has ground truth in it. / / That single addition — an observation inside the loop — is the difference between a generative system and an agent.
  • Chain-of-thought (Wei et al., 2022) / 'Let's think step by step.' Reasoning becomes an emitted artifact you can read, and latent planning appears.
slide 05

ReAct, read as a design document

Read the paper as a design document. Here is a trace in its format: thought, action, observation, thought, action, finish. Now do the nine components with the room; the answers are on the right. Notice three things. Tools are a fixed tiny set, declared in the prompt. Memory is the trace and nothing else. Evaluation is entirely outside the loop, on benchmarks; nothing inside checks a thought. And governance: the human wrote the prompt and left. The halt is the finish action, and the loop will happily never call it. What it lacked, memory, a budget, and verification, is the syllabus for the next eleven weeks. [~5 min]

The slide's wording in full
  • Foundation PaLM-540B / GPT-3 era, hosted / Perception the question + prior observations / Planning free-text thoughts between actions / Tools a fixed, tiny set (search, lookup, finish) / Memory the trace itself; nothing beyond the window / Coordination single agent / Evaluation none inside the loop; benchmarks outside / Governance the human wrote the prompt, then left / Runtime a script; halt = the finish action / / What it lacked: memory, a budget, verification. Every one of those is a later week.
slide 06

The minimal loop you will build this week

The build, in a dozen lines. Read it top to bottom. A message list. A bounded for-loop, which is the first halt. A model call that returns a structured Step, so the decision is typed and a malformed one is rejected by the parser rather than executed. Every turn appended to the ledger before anything else happens. If the step is an answer, halt. If it is a tool, call it and put the observation back in. Check the cost budget. And if the loop runs out, raise, never return silently. Four halts, every one recorded with a reason. You will run this twice: against your hosted route and against Ollama, and measure the difference. Some small models cannot produce the schema at all; that is a finding, not a bug, and it goes in the flight log. [~5 min]

The slide's wording in full
  • Step is a Pydantic model: kind ∈ {answer, tool}, name, args, text. The model cannot emit a malformed decision; the parser rejects it and that is an observation too.
  • Final answer · turn budget · cost budget · error. Each one lands in the ledger with a reason. A halt is not a failure; a silent exit is.
  • Same loop against a hosted API and against Ollama's endpoint. Measure both: latency, cost, and whether the small model can produce the schema at all.
slide 07

Halt conditions, budgets, and day-one failures

Five things that go wrong on day one, and each one is a falsifier or an abort on your card. A loop that never halts because the model never says answer: turn budget, plus detect repeated identical actions. A silent exception: errors are observations, and too many of them is a halt. A small model that cannot produce the schema: retry, then halt with reason format, and log it as a squawk rather than a failure of the design. An answer with no reasoning turn before it: that is a falsifier on the card. And adversarial input that asks the loop to ignore its budget: the budget is in code, so the loop halts anyway. The rule: a budget the model can talk itself out of is not a budget. [~5 min]

The slide's wording in full
  • Halt conditions, budgets, and what goes wrong on day one
  • Rule for the semester: a budget the model can talk itself out of is not a budget. Halts live in code and in the ledger, never only in the prompt.
slide 08

Teardown: AutoGPT and BabyAGI (spring 2023)

Second teardown, and do this one on the board with them. AutoGPT's loop: a goal in one sentence, the model writes a task list, executes one task with search or files or code, then rewrites the list from its own summary of what it did, and around again. The only halt was the human closing the terminal or the API key running dry. Ask the room which component was absent. Evaluation: nothing checked a result before it fed the next plan; the model graded itself from its own summary, which is summary laundering in embryo. Governance: no performance measure, no halt, no attestation. Memory: a vector store of its own outputs, so hallucinated facts came back as truth. Planning was present and fluent, and that is the uncomfortable point: fluency without grounding is what a spiral looks like from inside. Why it mattered: it named the ambition, and it gave the field its first shared failure record. Everything in 2024 and 2025 is a reply to that spring. [~8 min]

The slide's wording in full
  • The loop with goals and no grounding, no budget, no evaluator — why it spiraled
  • It named the ambition: give a model a goal and let it run. Hundreds of thousands of GitHub stars in weeks; the demo everybody saw. / / It also produced the field's first shared failure record: loops burning budget on the same task, rewriting plans in circles, inventing progress. / / Every 2024–25 design — evaluators, budgets, human-in-the-loop, workflows over agents — is a reply to this spring. / / Judgment loop: decision = full autonomy from a goal; privileged = ambition and demo value; cost = grounding; failure mode = spiral; preservation = none (that was the point).
  • Which of the nine components was absent, and which absence caused the spiral? / Evaluation: nothing checked a task's result before it fed the next plan; the model graded itself from its own summary. / Governance: the goal was one sentence; no performance measure (PEAS's P), no halt, no attestation. / Memory: a vector store of its own outputs — so hallucinated 'facts' were retrieved as truth. / Planning was present and fluent. Fluency without grounding is what a spiral looks like from inside.
slide 09

Live Design Analysis: ReAct vs. AutoGPT

Put them side by side and the pattern is obvious. In one year the loop gained an explicit plan, an open tool set, a vector memory, spawned subagents, and a daemon runtime, and it gained nothing in evaluation or governance. The why paragraph: ReAct optimized for a benchmark and left everything else out; AutoGPT optimized for ambition and left grounding out. Both lacked a budget, an evaluator, and a record. That is exactly the gap the reference design was started to fill, not in 2023 but in January 2026, which tells you how long the field took to take the lesson seriously. Your Design Analysis this week is one of these two; write the one I did not do on the board. [~7 min]

  • ReAct was built to show that reasoning and acting improve each other; it optimized for a benchmark and left everything else out. slide 10

Reference design: gzkit's genesis (January 2026)

The reference design's origin is the loop plus the thing the loop lacked. On January 12th, with eleven days before it would be shown to students, the model said that only specification matters and the operator refused: specification, methodology, governance, all three. What got added to the loop was not a better model call. It was a PRD that says what before how, an ADR that records the decision with its alternatives, a brief with allowed paths, and an append-only ledger in which every turn, gate, and attestation is an event. That is the governed path you fly this week: init, the PRD interview, the first ledger event, and an attestation after you have looked at the artifacts. Read gzkit's own PRD as the worked example; it is short and it never says how. [~7 min]

slide 11

The PRD is WHAT, not HOW

Two minutes on the PRD because people write it wrong the first time. It says what: who, what question class, what halting correctly means, what budgets, what must be in the ledger, what the human attests. It does not say how: no model, no SDK, no framework, no schema field names, no code. If your PRD names a framework you have pre-decided next week's ADR without recording alternatives, which is exactly the post-hoc rationalization ADRs exist to prevent. [~2 min]

The slide's wording in full
  • • Who uses the system and what they are trying to get done / • The bounded question class it answers — and the classes it must refuse / • What 'halted correctly' means for each class / • Budgets: turns, cost, latency the user will tolerate / • What must be in the ledger for a run to count / • What the human attests, and when
  • • Which model, which SDK, which framework (that is ADR-1, next week) / • The Step schema's field names / • Whether the loop is a for-loop or a state graph / • Any code / / A PRD that names a framework has pre-decided the ADR without recording alternatives — post-hoc rationalization, the thing ADRs exist to prevent.

    for turn in range(BUDGET): # halt: turn budget
    step = model(messages, schema=Step) # structured output
    ledger.append("turn", step) # ledger first
    if step.kind == "answer": # halt: final answer
    return step.text
    if step.kind == "tool":
    obs = tools.call(step.name, step.args) # observation
    messages.append(observation(obs))
    if cost.spent > COST_LIMIT: # halt: cost budget
    return halt("budget")
    raise Halt("turn budget exhausted") # halt: never silent
