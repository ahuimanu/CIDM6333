Steer the middleThree rings, one bar, and every file you have written since E0

The model sits in the inner ring. OpenCode is the middle ring. Your harness is the outer ring, and most of it is your own version of what OpenCode already does by default.

This lecture comes first, and it takes slides 3, 6, 7, 10, 11, and 12 of the E8 deck out of order. The exercise follows at the keyboard, each student in their own repository, following the screen.

The model · inner ring

The window, the reply, and no state between calls

opencode/big-pickle (or any OpenCode Go model) reads a window of text and writes a reply, one token per pass.

The model keeps nothing between calls. The next turn starts from a window that the harness builds again.

You cannot change this ring. You can change only what the harness puts into the window and what the harness does with the reply.

What the window holds on a turn (E6):

  • a system prompt, and AGENTS.md in full
  • the tool list: name, description, schema for each
  • each skill's name and description, inside the skill tool
  • the turn history, compacted when it gets long
  • whatever memory's retriever scored above the threshold

OpenCode · middle ring

The loop you did not write

OpenCode builds the window, calls the model, parses the tool call, checks the permission, runs the tool, and loops. This is the loop you drew in E1, shipped as a product.

OpenCode ships with a default for everything you will steer:

  • built-in tools: read, edit, shell, webfetch, glob, grep
  • built-in agents: build, plan, general, explore, scout
  • built-in commands: /init, /undo, /redo, /help
  • a default system prompt
  • default permissions: most allow, with .env denied and doom_loop and external_directory set to ask
  • the skill tool, empty until you fill it
  • compaction: a summary the model writes when the window fills
  • an event bus that plugins can hook

OpenCode leaves a trace of its own in the agent name in the TUI, the tool-call line, and the permission prompt.

The bar

The bar and its three widths

Specs and planningwhat is wanted, written before the loop runs: pitch, brief, PRD, AGENTS.md, plan, handoff
Executionthe three rings
Evaluation, validation, verificationwhat checks the output: tests, reviewer, the Chase, ledger, the gate

All three rings sit inside the narrow band. The model does its work there. The human owns both wide ends: the human writes the specification at the left end and judges the result at the right end.

This bar is E0's Degradation Pattern drawn as a shape. When the wide ends shrink, the system stops being answerable, and no component in the three rings reports the shrinkage.

This Evolution's exercise walks the figure from left to right and ends with you in the right band, reading a reviewer's verdict against a diff.

E0 · E1 · E2

Human, loop, and two agents

E0. A human writes what is wanted before the loop runs, and a human judges what came back. The rings hold nothing yet.

E1. The loop is the middle ring. Its one visible trace is the tool-call line: glob, read, read, then an answer. The model did not read the files. The loop read them and put the text in the next window.

E2. Who owns the loop? OpenCode answers with two primary agents. build can edit. plan denies edits outside ~/.opencode/plan/. Tab switches. The pattern you drew in E2 is now a permission difference between two agent definitions.

In this exercise, count the tool calls on one question. Then plan hex in plan and build it in build.

E3 · E4

Tools, schemas, and the permission gate

E3. A tool is a contract that fixes its arguments, its result, and its exit codes. In this exercise the contract is the command line of codec.py, which takes arguments, exits 0 or 2, and offers --selftest as evidence. A custom tool is a ten-line .ts shim in .opencode/tools/ that declares the schema and calls the Python, so that all logic stays in Python.

"permission": {
  "edit": "ask",
  "shell": { "*": "ask",
             "git diff*": "allow",
             "python3 …/codec.py --selftest": "allow" },
  "skill": { "*": "ask" }
}

The gate is opencode.json → permission. It sets allow, ask, or deny per tool and per pattern, and the last matching rule wins.

E4. An MCP server's tools reach the model the same way. The name, description, and schema go into the window, and the permission engine checks each call.

The difference is the trust boundary (Figure 06), because the server's descriptions are text that someone else wrote. In this exercise you only locate the mcp block and record what it exposes.

The permission prompt is the trace that the gate held. In this exercise the permission file sets most tools to ask, on purpose, so that everyone in the room sees the prompt.

E7

The memory record and its date

OpenCode keeps no store between sessions. recall.py and memory.jsonl are an addition with no counterpart on the middle ring.

A record enters the window only when the retriever scores it above the threshold. The model then reads the record as fact.

At step 8 you file one record:

As of 2026-10-22 the codec supports
rot13 and base64. Hex is not implemented.

At step 9 hex exists and the record is wrong. No step in the loop compares the record with the code. The retention date and evict are the mechanism that removes a stale record, and the sentence "data, not instructions" is a request to the model that the mechanism does not enforce.

The loop does not open the drawer by itself, and it does not close the drawer by itself either.

E8 · what you build in this exercise

A reviewer that cannot edit

---
description: Reviews one diff against one spec.
  Returns one ReviewResult JSON. Never edits.
mode: subagent
temperature: 0.1
permission:
  edit: deny
  webfetch: deny
  shell:
    "*": deny
    "git diff*": allow
    "git log*": allow
    "python3 …/codec.py --selftest": allow
---
Role: reviewer. Traits … Anti-traits …
Why … Return exactly one ReviewResult.

.opencode/agents/reviewer.md is your version of a built-in agent, placed radially outside build and plan.

  • Write both lines, in this order: the deny line stops an edit at the permission engine, and the anti-trait line tells the model the reason.
  • build invokes the reviewer through the task tool, or you call it with @reviewer. It runs in its own window and returns one message.
  • The message is a typed claim with three fields: verdict, findings with a location, and checked.

The test is to ask the reviewer to fix the bug. The persona should refuse, and if it does not, the permission engine should deny the edit. An edit that goes through is the finding of this exercise.

Mechanisms in the loop, deferred

E9. E9 covers what happens when the reviewer and the worker disagree, and adds a second reviewer with a different question. The controller routes FAIL back to the worker with a bound on rounds, then sends BLOCKED to the human.

E10. E10 puts your code inside the loop for the first time:

  • .opencode/plugins/: a hook on tool.execute.before that calls a Python checker and refuses a write without a passing run
  • .opencode/commands/test.md with !`pytest -q`: the test output injected into the prompt
  • permission.doom_loop: the same call three times stops the loop

Each of the three answers the previous Evolution's Probe 3 question with a mechanism in the loop rather than a sentence in the prompt.
