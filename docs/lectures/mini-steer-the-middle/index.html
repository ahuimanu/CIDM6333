The model · inner ring

One window in, one answer out, nothing kept

opencode/big-pickle (or any OpenCode Go model) reads a window of text and writes a reply, one token per pass.

It keeps nothing between calls. The next turn starts from a window the harness builds again.

You cannot change this ring. You can only change what goes into the window and what happens to what comes out.

What the window holds on a turn (E6):

  • a system prompt, and AGENTS.md in full
  • the tool list: name, description, schema for each
  • each skill's name and description, inside the skill tool
  • the turn history, compacted when it gets long
  • whatever memory's retriever scored above the threshold

OpenCode · middle ring

The loop you did not write

OpenCode builds the window, calls the model, parses the tool call, checks the permission, runs the tool, and loops. E1's loop, shipped.

It ships with defaults for everything you will steer:

  • built-in tools: read, edit, shell, webfetch, glob, grep
  • built-in agents: build, plan, general, explore, scout
  • built-in commands: /init, /undo, /redo, /help
  • a default system prompt
  • default permissions: most allow; .env denied; doom_loop and external_directory ask
  • the skill tool, empty until you fill it
  • compaction: a summary the model writes when the window fills
  • an event bus that plugins can hook

Its trace is its own: the agent name in the TUI, the tool-call line, the permission prompt.

The bar

The widths are where the human's work is

Specs and planningwhat is wanted, written before the loop runs: pitch, brief, PRD, AGENTS.md, plan, handoff
Executionthe three rings
Evaluation, validation, verificationwhat checks the output: tests, reviewer, the Chase, ledger, the gate

All three rings sit inside the narrow band. The model's part of the work is the thin part; the human owns both wide ends.

This is E0's Degradation Pattern drawn as a shape. When the wide ends shrink, the system stops being answerable, and nothing in the rings notices.

Tonight's exercise walks the figure left to right, and ends with you in the right band, reading a reviewer's verdict against a diff.

Human, loop, and two agents

E0. A human writes what is wanted before the loop runs, and a human judges what came back. Nothing in the rings yet.

E1. The loop is the middle ring. Its one visible trace is the tool-call line: glob, read, read, then an answer. The model did not read the files; the loop did, and put the text in the next window.

E2. Who owns the loop? OpenCode answers with two primary agents. build can edit. plan denies edits outside ~/.opencode/plan/. Tab switches. The pattern you drew in E2 is now a permission difference between two agent definitions.

E3 · E4

A tool is a schema plus a gate

E3. A tool is a contract: arguments, a result, exit codes. Tonight the contract is codec.py's CLI: arguments, exit 0 or 2, --selftest as evidence. A custom tool is a ten-line .ts shim in .opencode/tools/ that declares the schema and calls the Python; all logic stays in Python.

"permission": {
  "edit": "ask",
  "shell": { "*": "ask",
             "git diff*": "allow",
             "python3 …/codec.py --selftest": "allow" },
  "skill": { "*": "ask" }
}

The gate is opencode.json → permission: allow, ask, or deny per tool and per pattern; the last matching rule wins.

E4. An MCP server's tools reach the model the same way: name, description, schema in the window; the permission engine at call time.

The difference is the trust boundary (Figure 06): the server's descriptions are someone else's text. Tonight you only locate the mcp block and record what it exposes.

The permission prompt is the trace that the gate held. Tonight most things ask, on purpose, so the room sees it.

E7

Memory is a claim with a date

OpenCode keeps no store between sessions. recall.py and memory.jsonl are an addition with no counterpart on the middle ring.

A record enters the window only when the retriever scores it above the threshold. The model reads it as fact.

Tonight you file one record at 35 minutes:

As of 2026-10-22 the codec supports
rot13 and base64. Hex is not implemented.

At 55 minutes hex exists and the record is wrong. Nothing in the loop knows. The retention date and evict are the mechanism; the sentence "data, not instructions" is a request.

The drawer does not open itself, and it does not close itself either.

E8 · the thing you build tonight

A reviewer that cannot edit

---
description: Reviews one diff against one spec.
  Returns one ReviewResult JSON. Never edits.
mode: subagent
temperature: 0.1
permission:
  edit: deny
  webfetch: deny
  shell:
    "*": deny
    "git diff*": allow
    "git log*": allow
    "python3 …/codec.py --selftest": allow
---
Role: reviewer. Traits … Anti-traits …
Why … Return exactly one ReviewResult.

.opencode/agents/reviewer.md is your version of a built-in agent, placed radially outside build and plan.

  • The deny enforces. The anti-trait explains. Both, in that order.
  • build invokes it through the task tool, or you call it with @reviewer. It runs in its own window and returns one message.
  • The message is a typed claim: verdict, findings with a location, checked.

The test: ask it to fix the bug. Refused by persona, or denied by permission. An edit that goes through is the finding of the night.

Not tonight: the mechanisms in the loop

E9. What happens when the reviewer and the worker disagree, and a second reviewer with a different question. The controller routes FAIL back with a bound on rounds, then BLOCKED to the human.

E10. Your code inside the loop for the first time:

  • .opencode/plugins/: a hook on tool.execute.before that calls a Python checker and refuses a write without a passing run
  • .opencode/commands/test.md with !`pytest -q`: the test output injected into the prompt
  • permission.doom_loop: the same call three times stops the loop

These are the answers to last week's Probe 3 question: a mechanism in the loop, not a sentence in the prompt.
