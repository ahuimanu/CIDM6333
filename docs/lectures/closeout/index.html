2 · Frame

Tell and enforce

  • Tells: text the model reads. AGENTS.md, a skill body, a persona. The model can read it and not follow it.
  • Enforces: code or config OpenCode runs. A permission rule, a hook. The model cannot get past it.
  • E8: read-only is a permission in config, enforced by the harness; a sentence in the prompt is only a request.
  • Final System: "the prompt tells it not to" is not a control.
  • Every file answers four questions: a file, a reader, a moment, a trace.

3 · Area 0 Setup

One toolchain, one source of truth

  • uv: Python version, environment, dependencies, lock file, and running. Never activate; always uv run.
  • pyproject.toml holds the configuration. uv.lock pins it. Code lives under src/.
  • ruff lints and formats. ty checks types (beta). Tests: the standard library's unittest.
  • Appendix F already installs Python through uv and adds ty as a dev dependency.

Map, not encyclopedia

5 · Step 2 · Permissions

Allow, ask, deny

  • E3: a tool is a contract; the model is an untrusted caller.
  • Read freely; write with confirmation; irreversible actions with attestation.
  • Rules match a tool and a pattern. The last match wins: broad rule first, exceptions after.
  • OpenCode V2 renamed keys (shell where older versions said bash). Use your version's format.

5 · Step 2 · Permissions

Ask puts the human at index zero

  • A test change changes what "done" means, so edits under tests/ ask.
  • Gate the shell too: an edit rule does not cover sed -i run through the shell (E3, the 08-23 incident).
  • The trap tonight: round to one decimal, the 273.15 K test fails, the model asks to edit the test. Deny it.

The map in the window, the procedure on disk

  • Set the skill permission to ask, so every load leaves a trace.

7 · Step 4 · Personas and agents

The anti-trait tells; the permission enforces

  • "Never fixes code" in the body is a request. edit: deny in the frontmatter is the control.
  • The output has a type: one JSON object, verdict PASS, FAIL, or CONCERNS, every finding with a file and line.
  • A result you cannot parse is a FAIL, not a default PASS.

8 · Step 5 · Multi-agent

Plan, do, check

  • A controller dispatches; a worker does; a reviewer checks. The same split from FIPA to LangGraph.
  • The controller never implements. It sends a brief, parses a typed result, and routes.
  • Bound the rounds: a FAIL returns to the worker at most twice; then the human decides.
CIDM 6333 · CloseoutE8
8 · Step 5 · Multi-agent

An added agent adds a claim, not evidence

  • E9: a claim is a sentence that a model wrote. A receipt is what the harness observed.
  • The worker's DONE and the reviewer's PASS are claims. Exit codes and the diff are receipts.
  • Counterpoint, Cognition: "Don't Build Multi-Agents". Split context loses decisions. Use more agents where independence is the point.

9 · Step 6 · Hooks

Before can stop; after can only record

  • A hook is code the harness runs at a moment in the loop, whatever the model wants.
  • OpenCode's blocking hook lives in a plugin, and plugins are TypeScript or JavaScript. Ours is a thin shim: no logic, it calls Python.
  • The after-edit check uses the formatter setting: OpenCode runs a Python command after every write, edit, or patch.

9 · Step 6 · Hooks

Presence is not procedure

  • E3 and E9: a marker file once licensed work no hook had checked (the 08-21 incident).
  • A hook earns trust only after you have seen it block.
  • E11: black box over narrative. One JSON receipt line per tool call: time, tool, path, decision.
