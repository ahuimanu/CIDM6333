Steps 7 and 8, up close · Flight Card 5, test point 0 · the E5 lab

One description, one pinned hash

At install, the pin script hashes what the model will see: sha256(json.dumps({name, description, inputSchema}, sort_keys=True)). The pin goes into tool-pins.json in the repo. On every start the harness lists the tools again, hashes them the same way, and compares. Edit the description below. This page computes SHA-256 with the browser's SubtleCrypto over the same canonical JSON that Python's json.dumps writes with its default settings.

What the model sees in its tool list

A pin tells you the description changed since a human approved it. It catches the rug pull. It cannot catch a description that was already poisoned when you pinned it, so a human reads every description in full before the first pin. Re-pin the canary and the poison becomes the baseline.

The deck's division of labor: a permission rule limits what a poisoned description can make happen; a pinned hash tells you the description changed. You need both. None of the three harnesses the deck checked (Claude Code, Codex, OpenCode 1.18.32) documents description pinning, so your sortie supplies it.

Step 5, up close · test points 1–3

The server's checks, run in order

This follows the deck's scope_gate.py sketch: one SCOPES table maps read_note to notes:read and write_note to notes:write. Set the token, pick a tool, and add a forged claim. The forged claim never changes the result.

    What never counts as authority: a scope field in the body or arguments, a header the client wrote, a token issued for another server, a state handle, or the model's statement that the user approved. The status for a failed verification is not in the deck's sketch; this panel shows 401, the usual answer for an invalid bearer token.

    What the figure leaves out

    • Cross-server shadowing, the deck's fourth mechanism: one server's description rewrites how the model uses another server's tools. The defense scopes descriptions to their own server and keeps the fewest servers per session.
    • The stdio transport. There the trust boundary is the operating system, and the spec says stdio servers SHOULD NOT use the OAuth flow.
    • Supply-chain attacks such as postmark-mcp (Sep 2025). A description pin does nothing against a server that is honest to the model and lies to you; pin the package version and hash too.
    • A2A. A peer returns an assertion, and authority does not cross to it.
    • Token refresh, expiry handling, and the exact HTTP shapes of each request. The sequence keeps the five steps the deck names.
    • The page's hash uses the deck's canonical form. A real pin.py may differ in detail; what matters is that install and start hash the same way.
